# WinPool 文档瘦身计划

## 1. 背景

WinPool 当前已经形成稳定的长期文档结构：

```text
README.md
README.zh-CN.md
AGENTS.md
AGENTS.zh-CN.md

docs/
  Product.md
  Product.zh-CN.md
  Development.md
  Development.zh-CN.md
  Quality.md
  Quality.zh-CN.md
  Plan.md
  CHANGELOG.md
  CHANGELOG.zh-CN.md
  Reference/
  Archive/
```

本轮**不修改文档架构，不增加新的长期文档，不调整目录职责的大方向**。

当前主要问题不是文件结构，而是长期开发后逐渐出现：

* AI 每次任务默认读取过多长期文档；
* 当前版本、当前阶段、测试状态在多个文件重复保存；
* AGENTS 混入阶段性和历史状态；
* README 逐渐承担项目状态报告职责；
* Product 和 Development 混入当前版本实施状态；
* CHANGELOG 同时承担结果记录、测试报告、授权记录和 Git 流水；
* Plan 容易承担施工日志职责；
* 完整测试能力逐渐变成普通修改的默认工作流；
* Archive 和 Reference 虽然不是当前权威，但仍可能被过度读取；
* 同一事实存在多个副本，导致同步成本和上下文成本不断上升。

本轮目标是**收紧现有文档的内容准入规则、读取规则、写入规则和验证触发规则**，而不是再次设计一套新的文档系统。

---

# 2. 核心目标

本轮完成后，应满足以下原则。

## 2.1 最小默认上下文

`AGENTS.md` 是 AI 每次任务唯一默认必读的项目文档。

其他文档全部按任务需要读取。

不得为了“完整理解项目”“恢复全部项目背景”而默认全文读取 README、Product、Development、Quality、CHANGELOG、Reference 或 Archive。

`docs/Plan.md` 只有在开发者明确要求执行、继续、检查或验收当前计划时才读取。

`docs/Archive/` 永远不是默认上下文。

---

## 2.2 一个事实一个主要来源

同一长期事实原则上只保留一个主要来源：

```text
AI / 安全 / 权限 / Git 操作规则 → AGENTS.md
项目入口和基本使用              → README.md
长期产品目标和产品边界          → Product.md
长期工程与架构约束              → Development.md
当前正式开发计划                → Plan.md
长期测试和验收制度              → Quality.md
正式版本的重要最终变化          → CHANGELOG.md
历史状态和历史计划              → Archive/
非权威研究和方法                → Reference/
具体开发施工过程                → Git history
```

其他文件如需要引用相同信息，只保留必要的一句话摘要和链接，不重复完整规则。

允许 `AGENTS.md` 对真正高风险、不可逆的安全边界保留少量必要重复，但不得因此复制普通产品、架构或阶段细节。

---

## 2.3 Git 保存过程，文档保存规则和结果

Git 是默认施工日志。

以下内容原则上不再进入长期文档：

* 每次 commit；
* 每轮修改；
* 每次 review；
* 每次修复过程；
* 每轮测试数字；
* 临时中间方案；
* 可以从 Git history 直接恢复的开发轨迹。

长期文档只保存 Git 不适合承担的信息：

* 长期产品规则；
* 长期工程约束；
* 当前明确批准的正式计划；
* 正式版本的重要最终结果；
* 重要兼容性变化；
* 需要长期保留的历史决策背景。

---

## 2.4 正式流程只用于真正的正式阶段

普通修改和正式阶段必须区分。

普通任务默认工作流：

```text
读取 AGENTS
→ 理解当前任务
→ 按需读取少量相关文档
→ 实现
→ 必要时执行最小相关检查
→ Git 保存过程
→ 完成
```

正式计划任务：

```text
开发者明确要求执行 Plan
→ 读取 AGENTS + Plan
→ 按需读取 Product / Development / Quality
→ 实施
→ 阶段实现完成
→ 由开发者决定是否进入正式测试和验收
→ 记录最终结果
→ 归档 Plan
```

不得因为一次普通 UI 调整、局部修复、小规模重构或单项功能开发自动建立新的正式阶段。

---

# 3. 本轮明确不做的事情

为避免“文档瘦身”再次发展成大型文档重构，本轮明确不做：

* 不修改现有 docs 目录结构；
* 不新增 `Current.md`、`Status.md`、`Architecture.md` 等长期文档；
* 不拆分 Product、Development、Quality；
* 不重新设计版本制度；
* 不重新整理整个 Archive；
* 不统一全部历史 Archive 格式；
* 不重写所有历史 Plan；
* 不要求把整个 CHANGELOG 重写成新格式；
* 不为了减少文件大小而删除仍然有效的产品、安全或架构约束；
* 不修改产品、API、数据库、IPC 或现有功能行为；
* 不顺带重构源码；
* 不因为文档修改自动执行完整代码测试、原生测试或人工验收；
* 不以文档总 KB 或行数作为完成标准。

---

# 4. 文档读取规则

## 4.1 默认读取

每次任务只强制读取：

```text
AGENTS.md
```

如当前工作目录存在更具体的局部 Agent 规则，则同时遵守对应局部规则。

---

## 4.2 按需读取

根据任务性质查询对应文档：

### README.md

仅在需要了解：

* 项目基本定位；
* 用户入口；
* 构建或启动入口；
* 用户可见限制；
* 其他文档导航；

时读取。

### Product.md

仅在任务涉及：

* 产品目标；
* 产品边界；
* 当前需求是否属于产品范围；
* 长期路线；
* 用户能力和非目标；

时读取。

### Development.md

仅在任务涉及：

* 架构；
* 模块职责；
* 进程边界；
* 数据所有权；
* 持久化；
* IPC；
* 构建；
* staging；
* 版本规则；
* 长期工程约束；

时读取。

### Quality.md

仅在任务涉及：

* 测试；
* 正式验收；
* 结果词汇；
* 测试层级；
* 人工或设备验证；
* 是否需要执行某类质量门；

时读取。

### Plan.md

只有开发者明确要求：

* 执行 Plan；
* 继续 Plan；
* 检查 Plan；
* 验收 Plan；
* 修改当前正式 Plan；

时读取。

不得因为 `Plan.md` 存在就自动读取。

### CHANGELOG.md

仅在需要：

* 查询某版本最终变化；
* 判断重要兼容性变化；
* 调查已经形成的正式结果；

时读取。

不得为了了解实现过程而优先读取 CHANGELOG。

### Archive/

只有在调查明确的历史问题时读取具体文件。

例如：

* 某项设计为什么采用当前方案；
* 某个历史版本做过什么；
* 某个旧 Plan 最终状态；
* 某项被替代决策的原始背景。

不得一次性读取整个 Archive。

### Reference/

只有任务确实需要对应方法、研究或延期技术观察时读取具体文件。

Reference 不定义当前项目要求。

---

# 5. AGENTS.md 瘦身规则

## 5.1 定位

`AGENTS.md` 是：

> AI 工作入口和最高优先级的仓库执行规则。

它的目标是让 AI 在开工前首先知道**不能越过什么边界**，而不是知道整个项目的所有历史和当前状态。

---

## 5.2 保留

保留：

* 工作范围；
* 环境硬约束；
* 高风险操作边界；
* 数据保护和脱敏规则；
* 真实存储修改的默认拒绝原则；
* 精确授权要求；
* 文件删除和移动原则；
* Git push / tag / release / deployment 权限规则；
* 保护已有用户修改的规则；
* 文档读取规则；
* 文档写入规则；
* 测试和验收触发规则；
* 双语权威关系；
* Archive 和 Reference 的使用原则。

---

## 5.3 删除或迁出

从 AGENTS 删除：

* 当前产品版本；
* 当前开发阶段；
* 当前测试数量；
* 当前构建结果；
* 当前 Plan 实施状态；
* 已归档版本的具体实施说明；
* 某个历史阶段的 commit / push / tag 状态；
* 已经完成的一次性本地重置授权；
* 历史重构的特殊临时授权；
* 具体模块实现说明；
* Product 已经完整定义的普通产品路线；
* Development 已经完整定义的架构细节；
* Quality 已经完整定义的测试命令和验收矩阵。

---

## 5.4 高风险规则处理

真正高风险的安全边界不得因为瘦身而丢失。

但应优先抽象为跨版本长期规则。

例如：

```text
真实存储结构修改默认拒绝。

只有当前已批准的产品边界或正式 Plan 明确允许，
并且针对准确操作和准确目标取得所要求的显式授权后，
才允许执行。

UAC 提权或 Real 模式本身不构成授权。
```

具体“从哪个版本开始允许什么能力”由 Product 或当前 Plan 管理。

---

# 6. README.md 瘦身规则

## 6.1 定位

`README.md` 是：

> 用户和开发者进入 WinPool 的项目入口。

---

## 6.2 保留

保留：

* WinPool 是什么；
* 当前主要用户能力；
* 最重要的用户安全限制；
* 最基本的构建和运行方式；
* 当前正式产品版本的简短标识，如确有必要；
* 主要文档入口；
* License / Rights 等用户需要直接知道的信息。

---

## 6.3 删除或改为链接

删除：

* 当前测试通过数量；
* failed / skipped 数量；
* 当前 warning 数量；
* dependency audit 当前结果；
* 当前 staging 验证报告；
* 当前 schema / IPC 状态的详细展开；
* 历史 architecture hardening 说明；
* 当前 Plan 的施工结果；
* 历史版本实施过程；
* 详细架构说明；
* 完整验收矩阵；
* 与 AGENTS 重复的 Agent 工作规则。

原则：

> README 能通过链接说明的内容，不重复展开维护。

---

# 7. Product.md 瘦身规则

## 7.1 定位

`Product.md` 是：

> WinPool 的长期产品定义。

---

## 7.2 保留

保留：

* 产品目标；
* 产品原则；
* 用户长期能力；
* 产品边界；
* 长期非目标；
* 真实操作长期安全原则；
* 模拟和只读能力定位；
* 外部工具边界；
* 长期产品路线；
* Portable / MSIX / Store 等长期产品路线。

---

## 7.3 删除

删除：

* 当前本地实施版本；
* 当前开发阶段状态；
* 某阶段已经完成什么；
* 当前测试数字；
* 当前自动门结果；
* 当前人工验证状态；
* 当前 Plan 实施状态；
* Git、tag、Release 当前状态；
* 只对某一次迭代有效的临时实现说明。

判断标准：

> 如果一条内容只对当前版本、当前阶段或一次实施有效，就不应进入 Product。

# 8. Development.md 瘦身规则

## 8.1 定位

`Development.md` 是：

> WinPool 长期工程和架构约束。

核心判断：

> Development 描述“以后也必须这样开发”，而不是“这一次是怎么开发出来的”。

---

## 8.2 保留

保留：

* 技术栈；
* 四进程职责；
* 模块所有权；
* 依赖方向；
* IPC 长期原则；
* 数据和持久化所有权；
* Agent 单写入者原则；
* App / Agent / Worker / Broker 长期生命周期原则；
* 外部工具适配原则；
* 默认拒绝执行原则；
* staging 长期布局原则；
* 构建和发布脚本入口；
* 项目版本体系；
* Git 长期流程；
* 文档生命周期和事实所有权原则；
* 受控资源和本地资源的长期规则。

---

## 8.3 删除或迁出

删除：

* 当前 V0.41 实施状态；
* 当前 schema 号的阶段性迁移叙述；
* 上一个 schema 如何被淘汰的施工过程；
* 某一次本地 reset 的具体授权和路径；
* 某阶段刚刚删除了哪些表或文件；
* 当前版本测试结果；
* 当前 staging 结果；
* 某次重构采用过的中间方案；
* 已完成阶段的施工说明；
* 与 Quality 重复的完整测试制度；
* 与 AGENTS 重复的 AI 操作规则。

如某项 schema、IPC 或兼容性变化属于重要正式结果，应记录在 CHANGELOG，而不是长期保留完整施工过程。

---

# 9. Quality.md 瘦身规则

## 9.1 定位

`Quality.md` 是：

> WinPool 长期测试和验收制度。

---

## 9.2 保留

保留：

* `passed`、`failed`、`unverified` 等结果词汇；
* 静态和结构检查类别；
* 自动测试层级；
* native integration gate；
* human/device gate；
* 正式验收原则；
* 什么结果不能被写成 passed；
* 哪类事实需要人工证据；
* 真实硬件操作的长期验证约束；
* 正式验收时应执行的长期命令和方法。

---

## 9.3 删除或迁出

删除：

* 当前版本固定测试目录；
* V0.41 专属手工测试路径；
* 当前版本测试通过数量；
* 某轮测试结果；
* 当前哪些页面已经人工检查；
* 某个具体版本的验收现场状态；
* 某次 staging 的具体结果。

具体阶段的测试目录、专项矩阵和验收结果进入当前 Plan 或历史 Archive。

---

# 10. 测试和校验触发规则

文档瘦身必须同步修改验证工作流，否则测试结果仍会持续制造文档负担。

新的默认规则：

```text
纯文档修改：
默认不执行代码、native、device 或视觉测试。

普通小修改：
默认不执行完整质量门。

普通功能开发：
默认不执行完整测试。

开发者明确要求某项测试：
执行开发者指定范围。

AI 判断存在明显局部风险：
可以执行与当前修改直接相关的最小检查，
但不得自动升级为完整验证流程。

正式阶段实现完成：
不自动开始正式完整验收。

AI 应提示开发者决定是否进入正式测试与验收阶段。

正式版本 / 正式验收：
开发者确认后，按 Quality.md 执行完整流程。
```

有完整测试能力，不代表每次修改都应该执行全部测试。

---

# 11. Plan.md 瘦身规则

## 11.1 定位

`docs/Plan.md` 是：

> 开发者明确批准并要求执行的唯一当前正式计划。

同一时间最多只有一个活动 Plan。

无正式阶段时允许不存在。

---

## 11.2 Plan 可以详细

Plan 不需要为了“瘦身”强制缩成短文。

允许详细描述：

* 背景；
* 目标；
* 范围；
* 非目标；
* 必须遵守的约束；
* 架构决定；
* 具体任务；
* 风险；
* 预期结果；
* 验收条件。

---

## 11.3 Plan 不再承担施工日志

禁止持续向 Plan 添加：

* 每次 commit；
* 每轮修改完成状态；
* 每轮 review 流水；
* 每轮测试数字；
* 每次重新验证；
* “刚刚修复了什么”；
* 临时施工记录；
* Git 已经完整保存的信息。

推荐基本结构：

```text
背景
目标
范围
非目标
约束
实施任务
验收条件
```

阶段完成后，将最终状态冻结进入 Archive。

Plan 归档后不再作为当前事实来源。

---

# 12. CHANGELOG.md 瘦身规则

## 12.1 定位

`CHANGELOG.md` 是：

> 已形成的重要最终变化记录。

从本轮开始采用“结果记录”，不再采用“过程记录”。

---

## 12.2 新条目建议结构

每个正式版本或重要阶段主要使用：

```markdown
## Vx.x

### Added
- ...

### Changed
- ...

### Fixed
- ...

### Removed
- ...

### Compatibility
- ...

### Known Limitations
- ...
```

没有内容的类别可以省略。

---

## 12.3 不再记录

以后 CHANGELOG 不再保存：

* 第一次实现；
* review 又发现什么；
* 第二轮修复；
* 又跑了一轮测试；
* 再次视觉确认；
* 每一轮测试具体数量；
* staging 临时目录；
* 每个 commit SHA；
* commit 范围；
* 本地 checkpoint 流水；
* 可以从 Git history 恢复的施工轨迹；
* 与 Archive 重复的完整阶段验收记录。

正式版本如确有必要，可以简短记录：

* 是否存在重要未验证限制；
* 是否发生 breaking change；
* 是否改变数据库 / IPC / 数据兼容性；
* 正式发布是否形成。

但不应将 CHANGELOG 重新变成完整测试报告或发布审计日志。

---

## 12.4 历史处理

本轮不要求重写整个历史 CHANGELOG。

处理原则：

1. 新条目立即使用新规则；
2. 优先压缩最近仍频繁维护、重复最严重的部分；
3. 较旧历史若无实际维护价值，可保持原状；
4. 不为了格式一致性大规模改写历史事实；
5. 不删除仍具有重要审计价值的历史纠正说明。

---

# 13. Archive 使用规则

## 13.1 定位

`docs/Archive/` 是：

> 冻结的历史冷数据。

现有 Archive 结构原则上不调整。

---

## 13.2 使用原则

* Archive 不定义当前项目要求；
* Archive 永远不是默认 AI 阅读范围；
* 只有调查明确历史问题时读取具体文件；
* 不为了“了解 WinPool 历史”批量读取 Archive；
* 已冻结内容原则上保持只读；
* 不为了统一格式批量重写旧版本；
* 不把旧 Plan 的详细内容重新复制进当前长期文档。

# 14. Reference 使用规则

`docs/Reference/` 保持现有目录和文件。

原则：

* Reference 是非权威资料；
* Reference 永远不是默认上下文；
* 当前用户决定和项目正式文档优先于 Reference；
* 只有任务明确需要对应方法、研究或延期技术观察时读取；
* Reference 中的建议不得自动升级为当前要求；
* 不因为 Reference 内容详细就复制进入 Product、Development 或 AGENTS。

# 16. 内容删除判断标准

清理每一段现有内容时，按以下顺序判断。

## 第一问：这是长期规则吗？

如果半年后或下一个产品阶段仍然需要直接遵守，保留在对应长期文档。

如果只对一个版本或当前阶段有效，检查是否属于 Plan、CHANGELOG 或 Archive。

---

## 第二问：Git 是否已经保存了这件事？

如果只是：

* 某次改了什么；
* 某天修复了什么；
* 某次测试跑了多少；
* 某次 review 如何进行；
* 某个中间方案如何演进；

优先删除，让 Git 保存。

---

## 第三问：其他文档是否已经有唯一来源？

如果其他文档已经完整定义该规则：

* 当前文件删除详细副本；
* 最多保留必要摘要；
* 加入链接。

---

## 第四问：下一阶段还会有效吗？

如果下一阶段大概率失效，它通常不应该留在：

* AGENTS；
* Product；
* Development；
* Quality；
* README。

---

## 第五问：删除后是否会损失安全、产品或架构约束？

如果会，保留。

涉及安全、数据、不可逆操作、权限和重要兼容性的内容，优先保守处理。

# 19. 完成标准

本轮完成后应满足：

* 每次普通任务默认只读取 `AGENTS.md`；
* README、Product、Development、Quality 均按需读取；
* Plan 不再因为存在而默认读取；
* Archive 和 Reference 永远不是默认上下文；
* AGENTS 不再保存当前版本和历史阶段施工状态；
* README 不再充当测试和阶段状态报告；
* Product 主要保存长期产品定义；
* Development 主要保存长期工程和架构规则；
* Quality 主要保存长期测试与验收制度；
* Plan 不再承担施工日志职责；
* CHANGELOG 不再复制 Git 流水和每轮测试流水；
* 同一长期规则原则上只有一个主要来源；
* Git 成为默认施工过程记录；
* 普通修改默认不触发完整质量门；
* 大阶段完成后由开发者决定是否正式验收；
* Archive 保持历史冷数据性质；
* 中文副本不增加额外权威来源；
* 文档修改成本不再随着版本数量线性增加。

本轮不以任何固定文件大小、总行数或压缩比例作为完成标准。

# 20. 判断瘦身是否真正成功

以后判断 WinPool 文档体系是否健康，不主要看：

* 文档有多少文件；
* 每个文件多少 KB；
* Archive 有多少版本；
* CHANGELOG 有多少行。

更重要的是两个指标：

> 一个普通任务开始前，AI 默认需要读取多少与当前任务无关的信息？

以及：

> 一个普通修改完成后，会产生多少不必要的测试、状态同步和文档记录？

健康状态应该接近：

```text
普通任务
→ 读取 AGENTS
→ 查询 0～2 个直接相关文档
→ 实现
→ 最小必要检查
→ Git
→ 完成
```

如果以后再次出现：

```text
每次任务全文读取多个长期文档
每次小修改都建立 Plan
每次修改都执行完整测试
每轮测试都写入多个文件
同一状态同时写入 README / AGENTS / Product / Development
```

则说明文档系统已经重新开始膨胀。

# 21. 后续长期维护原则

文档瘦身完成后，不需要周期性再次进行大型文档重构。

日常只长期执行以下四条原则：

## 1. 默认上下文最小化

AI 默认只读取 AGENTS。

其他事实需要时再查询。

## 2. 一个事实一个主要来源

不为了保险在多个长期文档复制普通规则。

## 3. Git 保存过程，文档保存规则和结果

施工流水默认不进入长期文档。

## 4. 正式流程只用于真正的正式阶段

普通开发不自动触发 Plan、完整测试、正式验收、Archive 和大量状态同步。

最终目标不是让 WinPool 的文档变得尽可能短。

最终目标是：

> 在不损失安全、产品和工程长期约束的前提下，让开发者和 AI 只在需要时读取需要的信息，并且只为真正值得长期保存的事实付出文档维护成本。
