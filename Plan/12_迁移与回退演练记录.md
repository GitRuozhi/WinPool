# WinPool V0.2 迁移与回退演练记录

## 1. 范围与结论

2026-08-01 已在测试专用临时目录完成第一轮自动化迁移演练。演练没有读取、复制或改写
用户现有 WinPool 数据，也没有切换当前机器的数据位置指针。

本轮证明了迁移核心具备以下能力：

- Plan 阶段生成来源文件数、总字节数和规范化目录清单 SHA-256；
- 每个来源文件保存长度、最后写入时间和 SHA-256，Apply 前在写入静止租约内重新计算；
- 即使文件内容变化后恢复为相同长度和原时间戳，仍因 SHA-256 不同拒绝旧计划；
- 复制后逐文件重新核对长度和 SHA-256，验证通过前不提交活动位置指针；
- 对真实 `winpool.db` 执行只读 `PRAGMA quick_check`、schema 版本、逐表行数、主键列和
  主键摘要对照；读取逐行进行，不把整张表加载到内存；
- 目标指针使用同目录临时文件和原子替换；失败时保留原指针和来源数据；
- 标准位置与便携位置均保留，迁移采用复制而非移动或删除；
- App 与打包 Agent 能共同解析数字旧指针和字符串新指针；Agent 从主程序产品根解析
  `Data`，不会误用 `Agent\Data`；
- Settings 已改走受控生产路径：先停止 Agent、监控和测试并等待端点撤销，再 Plan、二次确认、
  Apply；迁移期间持有与 Agent 相同的当前用户命名互斥体，阻止 Agent 被并发重启；成功后
  通过进程交接参数重启 App，取消或提交前失败会释放互斥体并重新启动旧位置 Agent；
- 目标中若存在不属于来源快照的 `winpool.db-wal`、`-shm` 或 `-journal`，迁移会拒绝，
  不复用可能污染目标数据库的旧 SQLite sidecar。

## 2. 自动化场景

| 场景 | 证据 | 结果 |
| --- | --- | --- |
| 数据库与附件 Plan→Apply | 文件数、字节数、来源保留、目标内容、指针状态 | 通过 |
| 同长度且恢复时间戳的内容变化 | Apply 前重新计算 SHA-256 | 正确拒绝 |
| 来源在 Plan 后新增文件 | 静止后重新快照 | 正确拒绝 |
| 伪造或非本 Manager 签发的计划 | issued-plan 与根目录绑定 | 正确拒绝 |
| 指针提交失败 | 原指针仍活动、来源和已复制目标均保留 | 通过 |
| reparse point 与不可写目标 | 逐级路径复核 | 正确拒绝 |
| 真实 SQLite 迁移 | quick_check、schema、行数、主键摘要、文件哈希 | 通过 |
| 相同行数但不同主键 | 主键摘要对照 | 正确识别不一致 |
| 旧数字指针/新字符串指针 | App/Agent 共用解析规则 | 通过 |
| StorageLocationSwitch 退出 | 停止 Agent 但不关闭迁移中的主界面 | 通过 |
| App 单实例重启交接 | 新进程等待旧 PID 退出后再认领实例键 | 通过 |
| 目标残留 SQLite sidecar | 指针提交前检查数据库文件族 | 正确拒绝 |
| Settings 架构门禁 | 禁止回用旧 `SetModeAsync` 直接复制入口 | 通过 |

最新 Release 全量基线为 448/448；构建零警告、零错误，`git diff --check` 通过。

## 3. 生产接线状态与剩余验收

Settings 生产接线已经完成，不再调用 V0.13 `StorageDataLocations.SetModeAsync`。当前实现：

1. 第一次弹窗警告会停止托盘 Agent、后台监控及活动测试；
2. Agent 使用专用 `StorageLocationSwitch` 退出原因，flush SQLite、恢复临时系统状态并退出，
   但不关闭承担迁移操作的当前主界面；
3. App 等待 Agent 端点撤销后才创建静止租约，显示文件数、字节数、两侧路径和清单摘要；
4. 第二次确认后执行文件与 SQLite 审计，最后原子提交指针；
5. 新 App 等待旧 App PID 退出后再认领单实例键，并由新 App 启动读取新位置的 Agent；
6. 第二次确认取消或提交前失败时，强制丢弃旧命名管道传输并按旧指针重启 Agent。

仍未完成的是在用户明确选择的测试副本上执行标准→便携→标准实机回退、观察托盘和 GUI
状态，以及记录大数据量迁移耗时。未执行当前机器真实位置切换，因此不得把 WP7 人工验收列为完成。
