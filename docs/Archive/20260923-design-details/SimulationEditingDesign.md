# 模拟系统编辑细节

状态：2026-09-23 当前模拟编辑设计；格式方式的类型化计划与预览已有定点回归，未对真实设备执行格式化。本文解释用户动作怎样进入规则、预览和提交，方便开发者核对具体行为；产品范围以 [Product](Product.md)为准，数据所有权以 [Development](Development.md)为准，界面反馈见 [InteractionDesign](InteractionDesign.md)。本文不授权真实存储写入。

## 系统、事实与编辑意图

本机系统来自固定只读采集；它的来源事实、读取状态和对象关联要如实保留。内置模拟、导入模拟和从本机转换得到的模拟系统都可在支持范围内编辑。显示用模拟池/模拟层仅为派生投影，没有来源字段、容量或可修改目标身份，不能被当作真实存储对象提交。

分区和卷是不同来源实体：分区保存磁盘范围、偏移和类型，卷保存文件系统、容量和访问路径；管理界面的“分区”联合体把可靠关联的事实组合展示。无卷分区合法。模拟编辑仍用 `StorageSnapshot` 建模，在保存前生成明确标记 `FactOrigin.Simulation` 的 Windows 形态来源事实。名称、盘符和列表顺序不代替稳定 ID；导入或转换后也不能凭名称重连对象。

UI 产生 `SimulationEditRequest`，`StorageEditRules` 根据来源证据和目标状态给出允许、拒绝或信息不足。预览和提交沿用同一类型化步骤，不从解释性 PowerShell 文本反推执行。App 先对候选模拟文档校验；Agent 只做封闭请求、格式/哈希、修订和提交对账等持久化保护，不重新执行真实 Windows 存储命令。失败不能留下部分模拟提交；传输中断后按 CommitId 查询，不能把未知结果说成成功或失败。

## 格式化方式与参数

分区页在“快速格式化”下方显示“完整格式化”开关。两项表达一个格式化方式：选择快速会关闭完整，选择完整会关闭快速；任一时刻恰有一个选中。既有默认方式为快速。恢复建议值将方式恢复为快速，并同步两个开关及变化指示。切换选择本身不修改模拟系统，只有确认格式化后才提交。

格式化请求要携带所选方式，类型化计划和命令预览也应区分快速/完整。两种方式在当前模拟模型中生成相同的卷结果字段；“完整”是提交的操作意图，不表示 WinPool 做了真实的逐扇区扫描、坏扇区检测或 Windows `Format-Volume` 实测。结果卡准确写明所选模拟方式，不能仅用不同文案掩盖请求中丢失的方式。导出系统为可读 `.json` 文本；既有导入 JSON 结构的兼容判断独立于扩展名。

| 条件 | 规则与表现 |
| --- | --- |
| 目标 | 仅当前可编辑模拟系统中普通 Primary/BasicData 分区；Boot、System、EFI、MSR、恢复分区拒绝格式化 |
| 文件系统 | NTFS、ReFS、exFAT；NTFS 为默认，ReFS 提交前提示其长期测试证据限制 |
| 容量与分配单元 | 使用分区容量和当前选择的合法分配单元；缺失/冲突来源不得静默补成可写 |
| 数据与确认 | 已有已用数据时先确认模拟清除；取消则不提交、不显示成功 |
| 模式 | 默认快速；完整与快速互斥；模式进入操作意图、预览及结果反馈 |
| 真实设备 | 当前所有格式化均为模拟，不执行真实磁盘写入 |

## 其他已支持规则的边界

| 操作 | 当前判定 |
| --- | --- |
| 删除分区 | 只按所选分区自身的 Boot/System 标记拒绝；同盘另有系统分区、所选分区类型或所属系统盘身份不单独禁止删除。格式化的资格仍更窄 |
| 扩展/压缩 | 普通 Primary/BasicData 模拟分区可按目标总容量编辑，输入整数 MiB、目标按 1 MiB 对齐；扩展需右侧连续空间，压缩需保留建模的已用容量。NTFS 可双向、ReFS 仅扩展、RAW/未格式化按当前建模规则；exFAT 不支持。此范围不是 Windows 支持容量实测 |
| 创建分区 | 仅当前四种固定 GPT 类型；新建 MBR、自定义分区 GUID 等未实现 |
| 磁盘与池 | 脱机、转换、成员和用途变化都按所选模拟对象的来源、身份、布局与风险规则判定；不能因本机可查看就放开本机写入 |
| 池、层与虚拟磁盘 | 新建池允许空池；每池至多新建一个虚拟磁盘；现有多虚拟磁盘如实显示。MAX 与容量估算按现有整数规则，不能把估算标成 Windows 实测 |
| 优化 | 现有模拟 Optimize 操作是明确的 no-op，不宣称实际测量或真实优化完成 |

未知、未采集、读取失败、不支持、否、零与空集合各自保留含义。缺少目标身份或必要容量、偏移、文件系统证据时返回具体原因，不能由 UI 控件的启用状态代替规则服务判定。暂时不完整的输入可留在表单，但不能成为合法模拟文档。

## 操作顺序与人工核对

1. 选择模拟系统和目标对象；页面显示适用按钮、悬停用途或具体禁用原因。
2. 改动参数后预检查 `StorageEditRules`；需要确认数据损失或 ReFS 风险时先弹确认，不在取消后生成提交。
3. 生成并审阅类型化步骤；格式化方式、文件系统、分配单元和目标稳定 ID 在请求/预览中一致。
4. Agent 按修订、哈希与 CommitId 保护提交；成功后从已保存文档刷新页面，失败保留原文档，未知结果进入对账。
5. 用固定输入检查快速/完整互斥、切换与重置、预览差异、JSON 导出/导入往返、受保护分区拒绝和失败后无部分提交。原生界面/设备验证按 [Quality](Quality.md)如实标注，不以自动测试代替。
