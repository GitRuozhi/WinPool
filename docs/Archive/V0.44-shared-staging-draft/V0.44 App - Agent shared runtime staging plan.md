# V0.44 App / Agent shared runtime staging plan

[English](V0.44-App-Agent-shared-runtime-staging.md) | [简体中文（仅供阅读）](V0.44-App-Agent-shared-runtime-staging.zh-CN.md)

## Status

- **Kind:** V0.44 follow-up implementation plan
- **Goal:** remove duplicated App / Agent self-contained runtime files
- **Architecture:** two processes, one portable dependency union
- **Precondition:** runtime alignment experiment completed successfully

The experiment confirmed that after `WinPool.App` references the WindowsDesktop WindowsForms framework profile:

- same-name identical files: `207 → 288`
- same-name different files: `5 → 0`
- Agent-only files: `83 → 7`

The five previous runtime collisions are resolved.

---

## 1. Decision

V0.44 will keep:

```text
WinPool.App.exe
WinPool.Agent.exe
```

as separate processes.

Their project dependency graphs remain different:

```text
App
├── shared .NET / WindowsDesktop runtime baseline
├── WinUI / Windows App SDK
└── App-specific dependencies

Agent
├── shared .NET / WindowsDesktop runtime baseline
├── WinForms
└── Agent-specific dependencies
```

The final portable distribution will contain the **safe union** of both self-contained publish trees.

Shared byte-identical files are stored once.

App-only and Agent-only files remain.

Any same-relative-path file with different contents causes staging to fail.

---

## 2. Runtime alignment

Keep the App framework reference:

```xml
<FrameworkReference Include="Microsoft.WindowsDesktop.App.WindowsForms" />
```

Do not enable:

```xml
<UseWindowsForms>true</UseWindowsForms>
```

`WinPool.App` remains a WinUI application and must not introduce WinForms UI code.

Add a comment explaining that this reference exists only to align App and Agent self-contained WindowsDesktop runtime asset selection.

Add an architecture test that:

- requires the alignment FrameworkReference;
- forbids `System.Windows.Forms` usage in App source.

---

## 3. Publishing model

App and Agent must first publish independently into temporary directories:

```text
temp/
├── App/
└── Agent/
```

Both remain:

```text
win-x64
self-contained
PublishTrimmed=false
```

Do not publish Agent directly into the App output directory.

Do not rely on copy order or overwrite behavior.

---

## 4. Merge algorithm

Create the final staging directory from an empty location.

For every relative file path in both publish trees:

### App-only

Copy the App file.

### Agent-only

Copy the Agent file.

### Same path, same SHA-256

Copy one physical file.

### Same path, different SHA-256

Fail staging immediately.

Example:

```text
App/System.Drawing.dll
Agent/System.Drawing.dll

same hash
→ one System.Drawing.dll

different hash
→ staging failed
```

There must be no last-writer-wins behavior.

---

## 5. Final layout

Target:

```text
WinPool/
├── WinPool.App.exe
├── WinPool.App.dll
├── WinPool.App.deps.json
├── WinPool.App.runtimeconfig.json
│
├── WinPool.Agent.exe
├── WinPool.Agent.dll
├── WinPool.Agent.deps.json
├── WinPool.Agent.runtimeconfig.json
│
├── shared .NET runtime
├── shared WindowsDesktop runtime
├── App-only WinUI / Windows App SDK files
├── Agent-only files
├── Assets/
├── PRI
└── XBF
```

The old full runtime tree under:

```text
Agent/
```

is removed.

---

## 6. Agent path update

Update App code that currently expects:

```text
Agent/WinPool.Agent.exe
```

to use:

```text
WinPool.Agent.exe
```

This includes at least:

- Agent process launching;
- startup registration;
- staging validation;
- architecture tests;
- documentation describing the portable layout.

Do not change IPC protocol or process ownership.

---

## 7. Permanent collision gate

The zero-collision assumption must never become an undocumented permanent assumption.

Every staging build must recalculate:

```text
relative path + SHA-256
```

for both publish trees.

A future upgrade of:

- .NET;
- WindowsDesktop runtime;
- Windows SDK / TFM;
- Windows App SDK;
- WinForms;
- related framework dependencies;

must pass the same merge gate again.

If a future upgrade introduces a collision:

```text
same path + different hash
```

the package build fails until the cause is reviewed.

Do not silently choose either copy.

---

## 8. Upgrade policy

The shared runtime layout does not require App and Agent to have identical dependency graphs.

Only the shared runtime baseline must remain compatible enough to produce a collision-free union.

Future dependencies may remain:

```text
App-only
Agent-only
```

without issue.

A new unique file is acceptable.

A new same-name different-content file is not.

If a future framework upgrade cannot be aligned safely, the fallback is to restore isolated App / Agent runtime directories for that release rather than introduce unsupported probing or manual DLL replacement.

Fallback must be an explicit developer decision, not automatic packaging behavior.

---

## 9. Validation

After implementing flat staging, run:

```powershell
dotnet restore WinPool.slnx
dotnet test WinPool.slnx -c Release --no-restore --maxcpucount:1 -m:1
dotnet build WinPool.slnx -c Release --no-restore -m:1
```

Then publish App and Agent and verify:

- collision count = `0`;
- shared files are stored once;
- App-only files remain;
- Agent-only files remain;
- Release contains no PDB;
- PRI and XBF remain present;
- `PublishTrimmed=false`;
- no runtime file is deleted manually after publish.

## 12. Non-goals

This work does not:

- merge App and Agent processes;
- make their full dependency graphs identical;
- remove WinForms;
- add WinForms UI to App;
- remove WinUI;
- enable trimming;
- enable NativeAOT;
- use framework-dependent deployment;
- introduce custom `AssemblyLoadContext`;
- introduce custom probing paths;
- manually replace framework DLLs;
- change images;
- add new product features.

---

## 13. Implementation order

1. Keep and document the App WindowsDesktop alignment reference.
2. Add architecture guard against WinForms UI use in App.
3. Publish App and Agent into separate temporary directories.
4. Implement deterministic SHA-256 union merge.
5. Require zero same-name/different-content collisions.
6. Move Agent executable to the staging root.
7. Update Agent launch and startup registration paths.
8. Update staging and architecture tests.
9. Run full automated tests.
10. Run final merged-directory smoke tests.
11. Record final size and file-count results.
12. Archive the runtime-collision and alignment-experiment notes after the result is confirmed.

---

## 14. Completion

This work is complete when:

1. App and Agent remain separate processes.
2. App and Agent publish independently.
3. Their final portable dependency union contains no same-name hash collisions.
4. Shared runtime files exist only once.
5. App-only and Agent-only dependencies remain intact.
6. Both executables run from the same staging root.
7. Agent launch and startup registration use the new root path.
8. Future collisions are permanently blocked by staging.
9. Automated tests pass.
10. Final merged staging passes runtime smoke tests.

The resulting architecture is:

> **Two independent WinPool processes with separate dependency descriptions, a deliberately aligned shared runtime baseline, and one collision-checked portable dependency union.**
