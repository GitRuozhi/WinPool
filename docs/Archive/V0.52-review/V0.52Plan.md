## 3. WinPool 数据体系

### 3.1 三类职责，不是三个串行转换层

| 分类 | 权威内容 | 更新与保存约定 |
| --- | --- | --- |
| **来源事实** | 来源对象、原始属性、实际关联、读取状态、来源和时间。原值可来自真实采集、独立导入或模拟产生 | 当前事实由对应采集或模拟操作更新；保留必要证据，敏感内容按既有边界脱敏 |
| **统一模型** | `WinPool…` 存储/硬件对象、选定字段、派生属性和显示分组，以及到来源对象的引用 | 由事实、统一规则和身份对应记录生成；可缓存但可重建，不接受独立业务写入 |
| **应用数据** | 内部身份与对应关系、文档修订、偏好、选择、编辑意图、操作计划、提交与执行记录等 | 按用户操作和运行过程更新；不能要求全部从 Windows 事实推导，也不能丢掉这些记录后声称统一模型可以无损重建 |

同一系统、对象、字段与事实版本只有一个当前权威解释。原始来源证据不是第二个当前值编辑入口；不同历史版本可以保留，不是需要互相同步的副本。

正式数据流为：

```text
真实只读采集 / 新格式导入 / 模拟操作结果
                    ↓
              来源事实及修订
                    ↓ 统一来源选择、对象关联、派生规则
              WinPool 统一模型
                    ↓
         管理页 / 硬件页 / 编辑页 / 报告

用户输入 → 编辑意图 → 类型化计划 → 规则与预检查
                                      ↓
                              本版仅模拟执行器
                                      ↓
                          候选事实 → Agent 原子保存
                                      ↓
                         切换当前事实并重建统一模型
```

前端只消费统一模型及统一服务提供的来源详情；不自己访问原始接口、跨来源配对、选择最终值或重新计算显示分组。编辑器、报告、导出和必要的监控接线不保留另一套相同事实的解释。

### 3.2 草稿和预览不能反向修改事实

未提交输入归应用数据。编辑会话由已提交事实和意图产生隔离的候选事实/候选统一视图，供既有拖放预览与净差异面板使用；不改变已提交文档、当前真实采集或数据库。

允许表单暂时不完整。只有满足规则的候选文档才能模拟提交。撤销和放弃清理相应意图，不用“先改当前事实再想办法还原”实现。即时改名成功后的基线和草稿更新由同一编辑会话处理。

### 3.3 命名、类型与对象身份

统一模型中的业务对象统一使用 `WinPool` 前缀，如 `WinPoolDisk`、`WinPoolStoragePool`、`WinPoolStorageTier`、`WinPoolPartition`、`WinPoolVolume`、`WinPoolProcessor`、`WinPoolMemoryModule`、`WinPoolDisplayGroup`。具体后缀由执行者在既有项目内确定，不为重命名扩散到无关类型，也不给每个属性重复加前缀。

来源对象保留接口、命名空间/类、原始属性名与类型标识。序列化中提供明确对象类型及格式版本；不能仅靠 C# 名称或字符串前缀猜测内容，也不能根据外部类型名动态加载任意 CLR 类型。

软件选择和关联使用一个内部对象引用，复用或演进既有身份机制。每个统一对象可引用多个可靠匹配的来源对象；Windows `UniqueId`、`ObjectId` 等保留为来源定位/关联信息，不直接冒充应用主键，也不展示内部 ID 给普通用户。

身份和关系必须满足：

- 先核对系统与提供程序上下文，再关联同一对象的多个视角；名称、盘符、数组位置、DiskNumber/PartitionNumber 不单独构成持久身份。
- 内部身份及其来源对应记录在刷新、改名、重载和统一模型缓存重建后保持一致；不得每次投影随机分配新 ID。
- 关联不可靠时保留来源对象与不确定状态；不强行合并，不为了绘图捏造引用。临时身份不能被升级为稳定身份。
- 区分“同一对象的来源视角”和“对象之间的包含/支撑关系”；多块物理盘与池上虚拟磁盘不能合并成同一身份。
- 来源事实保留合法的多重关联与关联查询完整性；不能把单一父节点的显示需要反写成原始关系限制。聚合容量不重复计数。

### 3.4 统一磁盘和显示分组

| 来源事实 | 统一模型行为 |
| --- | --- |
| 可靠关联的 PhysicalDisk 及其 OS Disk 视角 | 可组成一个物理类型 `WinPoolDisk`，保留各来源引用和字段归属 |
| VirtualDisk 及其关联 OS Disk 视角 | 可组成一个虚拟类型 `WinPoolDisk`；不能与支撑它的物理盘合并 |
| 仅发现 OS Disk 或关联尚未确认 | 保留可查看的磁盘，明确未分类/关联不足；“其他磁盘”只是归类结果，不是新硬件种类 |
| Partition 与 Volume | 保留独立身份、容量和生命周期；前端组合展示，不能把缺卷、未查询到卷、卷查询失败混为一谈 |
| StoragePool 与 StorageTier | 保留独立对象与实际关联；真实层、层模板、无层对象不得因页面需求被合并或补造 |
| Usage、实际池/层关联 | 派生热备、退役、未划层等 `WinPoolDisplayGroup`；它们不是 `MSFT_StorageTier` |

统一磁盘不是无类型的大属性袋。公共显示属性可复用，特有信息保留明确来源/子字段组；操作按类型路由到正确的来源对象。出现多个关联 OS Disk 时保留全部可靠关系，不任取第一项而丢弃其余。

`IsHotSpare` 等由 Usage 推导，不成为独立可写事实；Usage 未知时不能推导为明确的 false。用户拖入热备分组时提交“设置用途”意图，成功后重建分组。不独立保存一套可修改的假层成员清单；折叠、可见性等保存为应用偏好。

“未划层”必须建立在已知关联上；读取失败不等于没有层关联，也不等于磁盘没有已分配空间。

### 3.5 字段值、状态与来源

原始事实保留类型语义、精度、单位、数组、枚举原码和 null。标准字段按“来源类＋属性”定义，不能因为同名就合并不同对象含义。类型转换只做明确、无损的承载，不把所有值先格式化成字符串再供业务读取。

字段读取采用统一的最小元数据约定：`Value`、`ReadState`、可选 `ReasonCode`、`SourceRef`；时间与来源上下文可以集中记录并引用，不在每个字段复制完整证据。具体代码结构可调整，不新增通用框架。

| 状态 | 约定 |
| --- | --- |
| `Returned` | 返回值有效，包括 `0`、`false`、空数组、空字符串或 null；null/哨兵值的意义按该字段定义解释 |
| `NotCollected` | 本次未查询；不能表示“Windows 不提供” |
| `Unavailable` | 有证据表明接口不提供或当前对象不适用，以原因区分 |
| `Failed` | 已查询但失败，保留拒绝访问、超时、设备消失等原因 |

成功返回“Unknown”枚举时仍为 `Returned`，保留原码。多来源无法合理选择时在统合结果记录冲突/信息不足，不覆盖各来源的读取状态，也不简单取最大、平均或最后一个值。

示意序列化结构如下；它说明契约，不要求所有应用字段都采用同样包装：

```json
{
  "Size": { "Value": 1000000000000, "ReadState": "Returned", "SourceRef": "capture-1" },
  "IsReadOnly": { "Value": null, "ReadState": "Failed", "ReasonCode": "AccessDenied", "SourceRef": "capture-1" }
}
```

脱敏不等于未采集或查询失败。需要遮蔽的值在持久化/导出时清理，并带可区分的脱敏标记；敏感原值不得由来源详情、命令预览或复制功能泄漏。

对 UInt64 等类型，JSON、IPC 和 SQLite 往返须保留原类型信息与精度，不经浮点中转。现有运算范围不能处理的值仍可只读保留，编辑返回明确不支持，不溢出或伪造零值。

## 4. 采集升级与覆盖范围

### 4.1 本版对象和接口边界

主要范围是现有本地 Windows Storage Management CIM/Storage cmdlet、现有 Win32/WMI 补充来源及已实现的原生只读读取。可以增加这些来源中、下表对象内的固定只读属性查询，以补齐遗漏；不引入新提供程序家族、远程管理或任意查询入口。

| 对象范围 | 本版要求 |
| --- | --- |
| Computer/OS 最小上下文 | 保留系统身份、版本/Build，以及现有操作判定所需的 OS/SKU、提供程序和角色上下文；不以本机上下文替代导入系统 |
| StorageSubsystem、StoragePool、StorageTier | 独立采集与识别；保留身份、容量、只读/状态、布局/预配及实际关联等可读属性 |
| PhysicalDisk、VirtualDisk、Disk | 保留各自身份、类型、状态、容量、扇区、用途与关联；多视角由统一规则组合 |
| Partition、Volume | 独立采集几何/类型和文件系统/卷容量，保留无盘符、无卷分区、挂载路径和可获得的保护状态 |
| 网络磁盘/共享映射 | 维持已有只读覆盖，按原对象含义保留；不伪装成本地物理盘，不新增编辑 |
| 其他既有硬件来源 | 保留现有有效的主板、CPU、内存、分页、GPU、显示器、网络、电池等采集能力；新增页正确展示即可，不承诺解决全部空项 |

存储范围内尽量保留可读标准属性，包括当前尚未用于编辑的低成本属性。高成本、需新权限/新接口或无当前用途的额外查询不默认为必做；在覆盖记录中说明，不以“尽量完善”无限扩张任务。

设备或接口缺失时，可以没有数值，但必须正确表达原因。集合查询成功且为空，与集合查询失败、部分结果、未查询必须可区分，避免把读取失败解释成对象被删除。

### 4.2 必须核对并贯通的字段问题

下列为本轮代码审查发现的优先核对项；实施时重新定位，不假定本地新代码仍有同样缺陷。已修正的项目转为防回归用例。

| 项目 | 目标结果 |
| --- | --- |
| Partition 类型 | 保留分区自身 Guid、GptType、MbrType 的不同含义；原始类型标识不因分类为 Unknown 而丢失，也不留在 Raw 后停止传递 |
| Volume 容量 | 独立获取卷 Size/SizeRemaining；不从 Partition.Size 直接代填 Volume.Size；容量含义不同，不统合成一个值 |
| 原生卷分类 | 修正原生挂载卷被表示为 Partition 的路径，与统一 Partition/Volume 事实定义一致 |
| DeviceId 与状态 | DeviceId 保留来源字符串语义，磁盘编号另存；状态数组和原因数组不压成无类型单字符串，未知枚举原码保留 |
| 磁盘身份稳定性 | OS Disk 等来源回退身份不得丢失不稳定标记；重命名和枚举顺序变化不产生错误合并或无依据重配 |
| 只读与脱机 | 补齐 Disk、Partition、Pool 等目标可获得的相关状态和原因；未读到不默认可写，模拟操作保持已有保护范围 |
| VirtualDisk 参数 | 将已采到的副本数、冗余、分配/池占用等信息贯通，不只留在某条提供程序的属性字典 |
| 卷路径与关系 | 保留可靠关联及全部有效挂载路径；不从格式化文字、盘符顺序或重复名称反推身份 |
| 物理/逻辑容量 | 明确 Size、AllocatedSize、FootprintOnPool、SizeRemaining 及估算来源；仅在语义相同的来源间进行选择 |
| 硬件报告 | 存储相关值引用同一统一模型；多设备值按对象引用对应，不按不同项目数组的第 N 项配对 |

来源一旦新增或修正，必须贯通：固定只读采集 → 原始字段与读取状态 → 对象关联/统合规则 → 持久化与 IPC → 消费者 → 往返与缺失值测试。仅新增 record 属性不算完成。

### 4.3 复用已有统合规则

先审查现有脚本、`RawSnapshotProjector`、`HardwareReportFactory`、原生提供程序和比较器中的来源选择、备用值与对象匹配规则，保留合理实现，集中到单一维护位置。不能只新增一套规则，让旧报告和旧页面继续自行解释。

经核对有效的原生/PowerShell 备用采集属于本版来源策略，可以继续保留。本计划要求移除的是旧数据格式、旧业务模型和重复权威的兼容回退，不是把有必要的多来源采集一并删掉。

规则至少能追溯：字段定义、首选来源、备用条件、匹配依据、单位/换算和冲突处理。只对确实需要统合的字段产生 WinPool 派生结果，单一同义来源可以直接引用。

新增完整来源保留不得把已有整理后的 `FinalValue` 再写成某个接口的 `RawValue`。无逐接口计时时，不伪造每字段耗时；只有总耗时时明确记录为总耗时。

### 4.4 快慢读取与刷新

落实“存储刷新”和“完整硬件刷新”两个明确用途。复用 runner 和合理查询代码，先拆行为与契约，不为目录整齐进行大规模搬家。

- 启动优先读缓存并呈现管理页，再发起只读存储刷新；常规存储刷新不强制读取 CPU/GPU/显示器/电池等无关信息。
- 硬件页按需完整刷新，不阻塞首屏；完整硬件动作需要的共同存储事实复用同一关联和统合规则，允许有限重复读取，不建立两个字段解释体系。
- 由 Agent 协调采集、缓存和文档提交；页面不直接启动 PowerShell。仅保持两个清晰动作，不新增复杂通用调度平台。
- 默认复用串行采集门并合并重复刷新请求，明确取消与超时；是否进一步并行只能基于测量。串行排队不冻结 UI，较慢结果不能回退较新事实。
- 分别记录存储与硬件采集时间及完整性，不能用文档更新时间冒充全部数据同时刷新。局部成功与旧缓存可同时展示，但必须标明来源时间和失败状态。
- 正常本机刷新不覆盖模拟副本；任何迟到结果均按系统/请求上下文路由，不能更新用户已切换到的另一个系统。

保留固定只读脚本、程序集内嵌、stdin 与原有安全策略；不发布外置可修改 inventory `.ps1`，不开放任意 WQL/CIM 方法或用户输入脚本。继续使用现有 PowerShell 5.1 采集基线，除非用户另行决定运行时升级。

## 5. 硬件页与统一查看

### 5.1 内容与交互

新增原生 WinUI 硬件页，接入现有导航、系统选择、语言与主题。页面只读取所选系统的统一硬件/存储对象，不反向从旧存储属性字典拼装整台电脑，也不维持第二份当前存储报告。

采用分类导航、对象选择/多实例列表、属性列表与来源详情。存储池和存储层独立组织；物理、虚拟、OS 磁盘按统一磁盘视图和来源详情表达；分区与卷可以组合展示但字段归属明确。分类数和项目数不作为固定验收条件。

每个字段至少能看到友好名称、标准项名、值和状态。标准项名含必要的来源类/对象归属；派生字段明确标为 WinPool 派生并可查看依据。内部对象 ID 不作为普通用户内容；来源详情和复制遵守脱敏规则。

页面显示最后采集时间、缓存/当前状态、刷新状态和可获得的实际耗时。错误、Unavailable、NotCollected 不隐藏为“正常空值”；多设备按对象身份显示，不能只给数列让用户猜测对应关系。非存储对象即使只读，也使用一致的 WinPool 对象命名与来源约定。

本机允许只读刷新；模拟/导入系统不使用本机采集覆盖自身。仅有存储数据的模拟系统中，CPU/内存等可以显示无记录或未采集，不伪造非存储硬件。复制携带的非存储硬件只读展示，不参与模拟运算或编辑。

### 5.2 旧硬件目录的处理

旧 13 类、154 项只作“有效信息不得无故丢失”的盘点基线。旧项目可以拆分、合并、改归属和名称；重复信息可以合并展示；错误或无意义项目可以纠正或退出，但必须有简短理由。

在本计划执行记录或相关代码定义旁维护一次覆盖核对：旧有效信息 → 新对象/字段或明确处理理由。不要把这张核对表发展为另一份永久字段权威，更不能写测试强制永久保留旧数量。已采到的数据不能因页面未设计位置而静默丢弃。

共用字段必须由管理页与硬件页引用同一统一结果。页面需要不同单位、翻译或组合显示时只做呈现，不重新选源、估算或修改值。

## 6. 独立模拟系统、编辑会话与规则

### 6.1 复制后完全独立

真实系统或模拟系统复制得到新的独立模拟系统。新系统有独立系统身份、应用对象引用和修订；必要时重建内部引用，所有引用仍指向副本内部，不共用可变集合、缓存、计划或写入目标。

副本保留复制时有用的事实和只读硬件信息，但原系统后续刷新、编辑、删除均不影响它；副本操作也不回写原系统。来源说明可记录“复制自某系统”，但不得形成运行时同步或加载依赖。

模拟操作只改变当前副本的来源事实；新值标为模拟。复制时的原始采集证据若保留，只是不可变来源说明，不能在统合时重新覆盖模拟的新值。无需新增双报告切换、追随原系统或复杂历史版本功能。

管理页、硬件页及编辑页中的当前存储信息均来自副本的统一模型。不能一页显示当前模拟值，另一页读取复制时独立保存的报告正文作为当前值。

内置模拟系统、已有独立模拟创建/复制/重置/导入导出路径应适配新格式。保留仍有产品价值的场景，不强制每个样例支持全部编辑；展示样例、编辑回归、规模测试可使用同一模型下的不同固定数据。新格式中的已有超出编辑范围的结构仍可只读保留。

### 6.2 编辑会话从页面职责中收口

把页面中分散的基线、草稿意图、每池创建参数、MAX 模式、撤销/重做、当前计划、改名状态及结果未知状态集中到可独立测试的编辑会话；优先迁移现有实现，不增加一套与旧状态并行运行的新框架。

- MAX 是容量意图，不是 TextBox 中的特殊字符串或舍入数值。选择切换、延迟事件、格式化显示不能改变未被用户修改的意图。
- 已提交值与显示值分开；读取并重新显示一个字段不能制造净差异或将 null 参数替换为默认参数。
- 即时改名成功后按内部对象引用更新基线、当前草稿与历史中的名称引用；撤销/放弃只作用于其负责的结构意图。
- 创建、删除、解散与用途调整合并为有依赖顺序的净差异；删除覆盖无意义属性修改，用户移动目标不丢失，新对象身份在计划生成时分配并稳定复用。
- 拒绝时保留可修正的草稿与原因；修订冲突不覆盖其他提交；结果未知按既有 CommitId 对账，不把传输失败一律解释为没有保存。
- 当前页面关闭、切换系统或重载时保持既有明确行为，不静默丢弃草稿。不得以状态重构为由另增跨重启草稿恢复产品功能。

### 6.3 继续使用统一规则入口

保留现有规则入口及允许/拒绝/信息不足结果，内部可按对象与操作整理。区分规则依据是事实完整性、WinPool 当前范围、目标能力或风险警告，但不引入多个规则引擎或规则语言。

存储事实缺失时不能默认允许；与本次操作无关的未知对象不应阻断只读展示。既有产品限制不能被描述成 Windows 的普遍限制；模拟估算和来源实测值不能互相冒充。

合法性规则、风险原因、控件可用状态和提交预检查使用同一服务。模拟执行前验证相关规则，执行后验证候选结构完整性；把现有关系校验、几何/盘符/介质审计中适用的不变量收口，避免只校验引用就遗漏分区重叠等问题。

容量继续以整数 bytes 计算且检查溢出，保留十进制物理标称与 GiB 等输入/显示边界；原始容量、逻辑容量、物理占用和剩余容量分别表达。保留本版基线的 MAX 向下 4 GiB 对齐等模拟策略，不把它宣称为 Windows 通用规则，也不恢复旧 1% 余量算法。

规则和模型可以保存已获得的能力证据，但不在本版新建全面 Windows 能力探测平台，不因相关 API 存在而开放扩缩容等新操作。未来真实执行所需的实际状态重查与写入验证留到下一阶段。

## 7. 操作步骤与 PowerShell 命令预览

### 7.1 唯一计划来源

结构批量操作和分区/改名等即时操作都形成类型化计划；单项操作可以使用只有一个步骤的计划。复用既有规划、操作、执行保护和提交结果，减少相近请求之间易漏传的手工转换。

计划至少包含稳定步骤标识、操作种类、内部目标引用、类型化参数、依赖/顺序、基线修订及原因/风险。相关身份一次分配；预览、规则、模拟执行和命令生成消费同一份计划，不在点击应用时重新拼出不同步骤。

命令文本是派生输出，不进入自由脚本执行路径，不由文本反推模拟动作。不使用一个多用途字符串字段同时表达对象名称、目标池身份和用途等互不相同含义；按现有有限操作收紧参数，不新建通用命令平台。

### 7.2 本版输出约定

| 情况 | 预览结果 |
| --- | --- |
| 有明确对应 cmdlet 和参数的步骤 | 显示命令、已知参数和目标引用说明；参数从计划产生 |
| 真实目标尚未绑定 | 使用明确的未绑定目标变量/标记并说明；不把 WinPool ID、脱敏哈希或模拟 ID 填进 Windows UniqueId 参数 |
| 一步需要多条命令 | 保留为同一步下的有序命令块，标明关联；不强求步骤与 cmdlet 一对一 |
| 应用内部动作、假层显示变化或明确模拟 no-op | 显示内部/派生/模拟说明；不编造不存在的 PowerShell 命令 |
| 空池规划或目标平台前提不足 | 保留相应模拟产品行为，并显示“无可直接对应命令/前提未满足”的原因；不宣称可在 Windows 创建 |
| 无法可靠生成某参数 | 明确标记未生成/待目标验证；不得用一个看似精确的默认值掩盖 |

在既有动作面板及操作结果的必要详情中提供逐步命令查看/复制，保持原有操作入口，不新增终端、执行脚本按钮或另一个计划编辑器。显示标准标签“命令预览”，不得写“已在 Windows 执行成功”。

生成器针对已支持操作使用真实 cmdlet/参数名，正确处理名称、路径、引号、Unicode、换行等参数转义；标准名称是显示或参数值，不被用于猜测操作身份。注明预览采用的 PowerShell/Storage 模块假设，不把“pwsh”简称等同于已迁移 PowerShell 7。

命令预览不保证当前机器可执行。本版不生成完整目标解析脚本、不实现异步 Windows 作业处理、真实重试、回滚或全套失败恢复。解析语法、验证参数映射和快照测试属于自动验收；执行真实修改命令不属于本版验收。

## 8. 持久化、格式断代与安全

### 8.1 保持现有 SQLite＋JSON 路线

继续使用一个活动数据根和现有 SQLite 所有权。来源事实、必要应用数据采用带格式版本的类型化文档保存；身份、修订、提交记录、关系/查询索引等按实际查询需要由表管理。不存在必须新增两份文件或为三类数据创建三个数据库的要求。

统一模型可以只在内存生成；确有缓存必要时可保存，但须关联事实修订和投影/规则版本，失效后重建。内部身份对应记录不是可随意丢弃的缓存。保留的对象表或关系表如果是查询投影，应由权威内容重建并在事务中更新，不能成为第二个可写业务来源。

不用本版全面改造 EAV/每字段一行数据库，也不强制把全部 JSON 拆成 SQL 列。不新建 JSON 文件与数据库之间的双向同步。

### 8.2 新格式与旧数据

执行者在完成契约影响核对后，一次确定新 SQLite schema、IPC、文档及事实格式版本；对实际不兼容的协议/文档明确递增，不让旧版本号包住新语义。无需为旧程序、旧文档或旧 App–Agent 组合保留运行时兼容。新编号在 Development 中记录，不在产品版本号中混用。

旧格式读取必须明确拒绝并说明需重建或开发期转换；这属于格式识别，不是迁移兼容功能。严禁打开失败后静默清空数据库、用默认值覆盖原件、自动递归删除数据根。

仅对明确选定且有保留价值的 WinPool 开发数据做一次性人工转换；内置样例优先重建。一旦需要临时转换脚本，它只能在开发期手动使用，不能进入产品运行、构建依赖或发布目录；完成后按 AGENTS 放入适当的 Old/Rubbish，不能保留成隐性启动迁移器。未选定的数据不擅自处理。

新格式仍须完整支持本版的保存、加载、已有导入导出和复制往返。不兼容历史数据不是放弃新数据一致性、数据恢复或提交对账的理由。

### 8.3 保留的安全保护

保留 App＋每用户托盘 Agent、类型化命名管道、Agent 单 SQLite 写入者、写租约、原子提交、修订冲突、哈希与 CommitId 对账。模拟系统的 Windows 状态验证继续按既有含义标记跳过，但文档、身份、类型、大小、修订和提交安全检查不能跳过。

真实修改拒绝须覆盖页面、应用用例、IPC 和 Agent 边界；不存在可通过改系统标志或构造消息进入的真实写入路径。本版新增的代码仅能采集或修改 WinPool 自身的模拟/应用数据，不能对目标磁盘创建、删除、初始化、格式化、调整、修复或优化。

来源事实、扩展属性、导入内容、报告、日志、错误信息、复制与命令预览均进入同一隐私边界。保存后的源身份可用一致的安全表示保留关联；不能为了支持未来真实执行而把未脱敏硬件标识全部永久入库。未来真实目标重新绑定不在本版实现。

保留标准 `%LocalAppData%/WinPool` 与现有显式便携模式、设置所有权、单实例、运行树和资源规则。只做新格式适配，不另改数据位置产品功能。

## 11. 验证与验收

### 11.1 验证授权与记录方式

本计划批准并授权执行后，本节指定的自动回归、只读本机采集与原生界面检查属于实施范围。所有写入仅限隔离的 WinPool 应用/模拟数据，禁止真实存储变更。计划编制阶段不执行这些检查。

进度使用“未开始、实施中、已实现待验证、已验证、受阻”；验证结果使用项目约定的 `passed`、`failed`、`unverified`、`not_required`、`deferred_by_user`。结果记录命令或动作、实际基线、环境、证据及限制。缺少 Windows/设备时不能报通过；自动测试不替代原生事件、视觉或设备实测。

验收编号是风险覆盖组，不要求一个编号等于一个测试函数，也不以旧测试总数或目录项目数量作为成功标准。

### 11.4 自动门与性能记录

按项目环境和 `global.json`，在批准后的实际 Windows 工作树中执行：

```powershell
dotnet restore WinPool.slnx
dotnet test WinPool.slnx -c Release --no-restore --maxcpucount:1 -m:1
dotnet build WinPool.slnx -c Release --no-restore -m:1
dotnet list WinPool.slnx package --vulnerable --include-transitive
```

日常改动先运行直接相关测试，阶段收口运行上述自动门。实际命令按仓库当时 SDK 能力核对并记录，不顺便升级依赖。审计服务不可达不等于“没有漏洞”，记录为未完成并说明；新增构建警告逐项处理。

S8 移出旧运行路径及最终版本/文档调整后，应在最终交付基线上重跑受影响回归并完成最终自动门，不能用退出旧代码前的中间结果代替最终版本证据。

保留运行中的用户会话和输出树，使用隔离输出/数据。普通验证不默认调用会停止程序和清理输出的重建脚本。

性能记录至少包含：冷启动到管理可用、管理存储刷新、完整硬件刷新、采集进程、解析/统合以及保存的实际耗时。采用同一机器和可比输入，注明缓存条件；比较旧版与新版，不预设无依据毫秒承诺。必须证明常规存储刷新没有完整硬件查询/报告构造的强制依赖，且没有可解释之外的严重回退。进一步并行或原生化以测量为依据，不扩成另一个优化项目。

5. 编辑会话及计划行为通过直接测试，原生事件与关键闭环按 §11.3 取得证据；不是只验证纯函数而遗漏真实页面路径。
6. 命令与计划步骤/参数一致，有目标/前提说明，不提供执行路径；不把生成文本的正确性当作真实存储修改证据。
7. 新格式往返、旧格式拒绝、隐私、事务、租约、修订及 CommitId 对账有效；数据处置没有越界。
8. §11 必需自动检查无未解决失败；真实执行未发生；证据与限制按项目状态词记录。
9. 旧重复权威、旧格式回退、重复选源和假层实体写入路径退出正常构建/运行；归档不成为运行依赖。
10. 版本、文档事实归属、现有计划归档与待验证项一致，交付可在新的隔离数据根启动。

达到上述条件后停止本阶段，不继续追加“再多支持一种布局”“再补一个厂商接口”或“顺手开启真实写入”。下一阶段真实操作的目标绑定、授权、平台能力重查、执行后采集和失败恢复需要独立确认。

### 13.2 提交与交付

单人仓库按现有规定在 `main` 本地提交，不自行创建分支或 PR。只提交本任务文件，代码/重构、功能、文档及视觉资源按可审查的合理单元组织；不混入用户已有改动、采集原件、数据库、日志或产物。

推送需要单独明确请求；推送前 fetch、核对上游祖先和待推送提交，不强推。五个未推送提交时按项目规定提醒。版本 tag、Release、二进制上传、签名和部署不包含在计划实施授权中。

阶段完成交付：实际实现基线、变化摘要、验证命令和结果、指定原生/只读设备证据、新格式与开发数据处置说明、未验证/延期项及下一阶段边界。无新阶段时按项目规则归档完成的活动 Plan。
