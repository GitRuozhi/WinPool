## 1. 必须保留的行为

| 项目 | 固定边界 |
| --- | --- |
| 两页提交 | 结构页所有修改先进入草稿，一次应用；“保存池属性修改”仅合并草稿。分区页保持每项立即提交，不加入结构动作队列 |
| App/Agent | App 调用 Application/Domain 内置规则及模拟服务；Agent 模拟跳过 Windows 系统检查，保留格式、身份、哈希、修订、事务、单写入方及 CommitId 对账保护，不重跑第二套业务规则 |
| 容量 | MAX 为理想可用逻辑容量向下取 4 GiB 整数倍；Simple/Mirror/Parity 分别折算，不恢复旧 1% 余量。所有软件生成容量使用二进制单位，内部仍存整数 bytes |
| MAX | 单图标切换；显示 `MAX(196GiB)`；再次点击或手动输入数字退出；成员/布局变化时重新估算。手动值不被偷偷改小；未知条件不冒充零或成功 |
| 预配与布局 | 预配类型仍为下拉框，当前仅 Fixed；两个编辑页左下控件固定 DIP 大小、宽度不足换行；不重做拓扑布局引擎 |
| 动作窗口 | 页内只读、显示净差异、子动作默认折叠；A→B→C 合并为 A→C，回 A 清除。无逐条编辑/删除/排序/应用，无持久化历史 |
| 数据与删除 | 改名不格式化、不重算无关容量。模拟任意已有分区可删除，包含 EFI/MSR/恢复，但格式化限制不因此取消；NTFS/ReFS/exFAT 与现有 ReFS 提示保持 |
| 失败与清空 | 成功应用或明确放弃才清空；普通失败保留草稿及原因；未知结果按原 CommitId 对账，禁止盲目重试；冲突不覆盖持久化文档 |

## 2. 九项修复

### F1 [P1] 仅改池名称会触发模拟格式化

- 结果：已修复。池更新不再消费文件系统参数，格式化和卷重命名由独立计划步骤表达。

- 定位：[StorageStructurePage.xaml.cs](../src/WinPool.App/StorageStructurePage.xaml.cs) `EnrichPlanIntent` 无条件附加 FileSystem；[StorageSystems.cs](../src/WinPool.Application/StorageSystems.cs) `UpdateStoragePool` 只要收到该字段就调用 `FormatPartition`。结果重置首个主分区卷的已用空间，可能改卷标，动作却仅显示更新池。
- 修复：名称/层属性更新不再隐含格式化。只有明确的格式化意图产生独立 `FormatPartition` 步骤，经自己的规则和数据确认执行；已有分区卷标仅变化时使用 Rename。检查建池内的初始化格式化仍正常，不机械删除创建所需参数。
- 验收：对有数据的 NTFS/ReFS 卷，仅改池名/虚拟磁盘名，卷身份、文件系统、簇大小、卷标、SizeRemaining、挂载路径均保持；计划无 FormatPartition。明确格式化仍可按既有规则执行并显示风险。

### F2 [P1] 默认“创建存储池”被零容量草稿挡住

- 结果：已修复。未完成草稿允许零容量 VD 占位，规则预检查和实际应用仍拒绝无成员或零容量。

- 定位：页面 `CreateDraftPoolAndSelect` 在空池草稿中立即调用 [EditWorkspace.cs](../src/WinPool.Application/EditWorkspace.cs) `InsertDraftVirtualDisk`；该方法新增的 `placeholderSize <= 0` 检查使默认自动建虚拟磁盘流程失败。
- 修复：区分未完成草稿与可保存文档。允许空草稿及其虚拟磁盘占位，容量未定时以待配置表示；成员补齐后再计算。实际应用继续拒绝零容量或非法布局，不能为创建占位放宽持久化规则。
- 验收：默认自动建 VD 开启时，点“创建存储池”能出现空草稿；尚无成员时应用被具体原因阻止；拖入合法成员后可继续配置/应用。自动建 VD 关闭也可建池草稿。

### F3 [P1] 缩小层容量会留下超出 OS 磁盘边界的分区

- 结果：已修复。规则与模拟保存边界都以 checked 加法检查全部受影响分区，恰好贴边允许、越界一字节拒绝。

- 定位：`UpdateStoragePool` 更新 VirtualDisk/OS Disk.Size，却不检查已有分区的 Offset + Size；[StorageRelationshipProjector.cs](../src/WinPool.Application/StorageRelationshipProjector.cs) 的 ID/关联校验不能发现几何越界。
- 修复：在共享规则中检查受影响 OS 磁盘上的全部分区（含无卷、MSR 等），缩小后任一分区越界即拒绝，原因包括分区和最低所需容量。使用 checked 整数加法。**本版不自动移动/缩小/删除分区，不用格式化解决越界。** 后续模拟应用也不能保存不满足该条件的结果。
- 验收：有约 100 GiB 分区但无已用数据的磁盘，改层总量至 80 GiB 被拒绝且文档不变；无越界的允许修改成功；分区恰好结束于磁盘边界允许，超过一个字节拒绝。

### F4 [P1] 新建虚拟磁盘仍使用修改层容量之前的旧大小

- 结果：已修复。新建 VD 使用最终有效层容量；已有空池在同批处理中先更新层，再创建 VD。

- 定位：页面 `ApplyFormToWorking` 只改 StorageTier.Size；[SimulationDraftPlanner.cs](../src/WinPool.Application/SimulationDraftPlanner.cs) 创建步骤继续传 `SizeBytes: vdisk.Size`，`CreateVirtualDisk` 与最终层容量比较后拒绝。
- 修复：新建/占位 VD 的派生大小随当前最终层容量更新，创建计划使用同一次估算结果；已有 VD 的容量修改走 F3，不把所有对象无条件重置为层总量。已有空池本批建 VD 时，先落实相关层参数，再创建 VD/分区；不得先创建旧大小分区再缩盘。
- 验收：新池草稿和已有空池两条路径分别覆盖：生成占位 → 减小层容量 → 应用；最终 VD 大小、OS Disk 大小及新分区边界符合最终层设置。手动/MAX 都覆盖，多介质层分别折算后相加。

### F5 [P1] 创建参数依赖当前选中池，切换选择后丢失

- 结果：已修复。创建/分区意图按池稳定 ID 保存在页面内存状态，三类层容量由草稿事实传递，切换选择不会改写其他池语义。

- 定位：`EnrichPlanIntent` 只从当前控件补充被选中池的参数；基础 `CreateTieredPool` 计划遗漏 CapacitySizeBytes，并继续用“有无草稿分区对象”推断自动分区。
- 修复：按稳定对象 ID 把必要编辑意图存入本页草稿状态：自动创建 VD/分区、文件系统/簇、各层手动容量/MAX 模式。控件读取/写入该状态，规划器对所有待应用对象独立读取，**选择变化不能改变计划语义**。补齐 SSD/HDD/SCM 的对应容量参数；不复制整套事实模型，也不新增持久化草稿库。
- 验收：配置池 A 的自动分区、文件系统、HDD 手动容量和 MAX 后，选择池 B/原始池再应用，A 的结果与直接应用一致。再切回 A，输入模式/参数不丢失；自动分区关闭不创建卷，开启产生正确对象关系。

### F6 [P1] 解散池强制移回原始池，覆盖草稿中的最终目标

- 结果：已修复。每个原成员从最终草稿解析目标并只生成一次移动；目标无效会在预检查中直接阻止。

- 定位：规划器解散时对原成员全部生成 MovePhysicalDisk→primordial，后续移动循环又跳过原属被解散池的成员。
- 修复：对每个原成员从最终草稿解析目标。仍待释放的成员移回原始池；用户已安排去其他池的，保留最终目标，移动只执行一次并列在解散子动作内。保证目标池已存在、删除空池在所有成员移出后执行；不通过追加第二次移动掩盖错误，不引入通用依赖调度框架。
- 验收：A 解散后把其中磁盘拖到已有 B；以及先从 A 拖到 B 再解散 A。窗口均显示最终目标 B，实际落入 B，A 被删除，原始池/两池成员列表无重复。若目标还未建立，先满足已有创建步骤依赖；不支持的目标应明确阻止，不默默退回原始池。

### F7 [P2] Interleave 回填仍使用旧单位文本

- 结果：已修复。回填和解析共用 KiB token；超出编辑范围的采集值原样显示并禁用编辑。

- 定位：`SetInterleave` 生成 `128K`，下拉项已是 `128 KiB`，匹配失败后回落至 `64 KiB`。
- 修复：回填、显示、解析统一使用同一个数值映射/转换入口，支持现有 16/32/64/128/256 KiB。读取超出编辑范围的值时保留原值并说明限制，不默认改成 64 KiB。不改变真实 bytes 或 PowerShell 合法单位语法。
- 验收：每个支持值经过选中、切换对象、改名、保存加载保持不变；仅改名不出现隐含 Interleave 修改或布局拒绝。

### F8 [P2] 动作缺少对象、数据提示与完整父原因

- 结果：已修复。动作包含对象与移动目标，数据风险按实际已用量计算；解散父项聚合全部不同阻塞原因，依赖步骤显示前置失败。

- 定位：页面 `ActionText` 忽略具体目标与 CausesDataLoss；`DescribePlanStep` 多数只写“移动物理磁盘/删除分区”；规划器父项只复制第一个阻塞原因。
- 修复：动作显示对象名称及必要定位（如磁盘号/盘符），移动显示“对象：A → B”，属性动作显示实际变化及值；对象即将删除时从基线保留可读名称，不把内部 ID 当唯一文案。父子都直接显示数据损失/拒绝/信息不足原因；父项汇总全部不同原因及涉及对象，文字换行，不依赖展开/悬停。保持中英界面。
- 规则服务统一提供拒绝及数据影响信息；依据相关卷的实际已用/未知状态，不能把所有 Delete 都标为已有数据。预检查后保留原删除风险，不因候选状态已删对象而抹去提示。运行期冲突/通信失败是提交原因，不伪造规则结论。
- 解散显示一个父项，子项按分区/卷 → VD/派生关系 → 成员移动 → 空池删除排列；默认折叠。多个问题同时发生时逐项说明；前置失败的依赖步骤说明前置原因，不能伪报新目标不存在。
- 验收：两个待移动磁盘能区分各自来源和目标；两个有数据的删除对象能看到各自风险；两个不同阻塞原因在父项折叠时均可读。用户允许的数据删除保留确认，合法动作不标红。预览/确认/应用使用同一计划与同一对象 ID。

### F9 [P2] MAX 模式不在撤销/重做状态中

- 结果：已修复。撤销状态同时保存结构快照、按池意图和 MAX 模式；成员及 MAX/手动切换可共同恢复。

- 定位：`_undoStack/_redoStack` 仅保存 StorageSnapshot，而 `_maximumSizeFields` 独立保存模式，切换 MAX 本身也未形成对应可撤销状态。
- 修复：利用 F5 的最小草稿意图状态，使一次撤销/重做同时恢复结构与模式/数值；不记录每个输入字符，不新增回放系统。恢复控件时屏蔽程序赋值触发的用户编辑事件；MAX 依恢复后的成员/布局重算，手动值原样恢复。
- 验收：手动 80 GiB → MAX → 手动 60 GiB，按现有字段确认粒度撤销/重做，模式、值、动作和规则原因一致；MAX 后增减成员再撤销同样一致。成功应用/放弃清空待办并回到已保存数值；切换对象不丢失模式。
