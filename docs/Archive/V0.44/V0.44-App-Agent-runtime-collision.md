## What the V0.44 plan already assumed

The V0.44 plan treated App/Agent runtime duplication as the main structural
size problem. It expected a large set of **identical** self-contained files:

- two processes remain: `WinPool.App.exe` and `WinPool.Agent.exe`
- each process keeps its own apphost, `.deps.json`, `.runtimeconfig.json`
- shared files that are the same bytes are stored once
- same name and different bytes must fail the staging merge
- last-writer-wins is forbidden
- processes must not be merged, WinForms must not be removed, trimming must
  not be enabled to force a smaller tree

That assumption was not wrong. The merge found a large identical set. It
stopped because a small same-name set was **not** identical.

## Why one product can emit two files of the same name

WinPool ships as one portable directory, but restore/publish still builds
**two self-contained closures**:

```text
WinPool.App.exe
    WinUI, Microsoft.NETCore.App, Windows App SDK

WinPool.Agent.exe
    WinForms, Microsoft.NETCore.App, Microsoft.WindowsDesktop.App
```

Each `dotnet publish` copies the framework files that **that process** needs.
The two shared frameworks both install some historical names
(`System.Drawing.dll`, `Microsoft.VisualBasic.dll`, and others). The names
match; the payloads do not:

- App often gets a small compatibility/facade assembly
- Agent often gets the full Windows Desktop implementation WinForms loads

This is not a WinPool project referencing two NuGet versions of the same
package. It is two executables, two framework packs, one output filename.

A single-process app would have to pick one assembly at compile time. The
dual-process, dual-publish layout defers the clash until the two output
directories are merged.

## What V0.44 did and did not do

Did:

- keep two processes
- keep WinForms tray
- keep `PublishTrimmed=false`
- fail the flat merge
- keep `WinPool.App.exe` + `Agent\WinPool.Agent.exe`

Did not:

- overwrite the five files
- merge App and Agent into one process
- delete WinForms
- enable trimming
- change images

V0.44 portable staging after the other slimming work: 779 files, 338.40 MiB,
versus the V0.43 baseline 853 files / 380.44 MiB. The identical 207-file /
~81 MiB duplicate set remains on disk because the five collisions blocked a
single shared directory.

## Open questions for this analysis

These are questions, not decisions:

1. Are the five Agent copies strictly required for WinForms tray, EventLog, or
   drawing, and are the App copies strictly required for WinUI?
2. Can the two processes load different implementations if they stay in
   separate probe paths, and is a hybrid layout (shared identical files, plus
   a small Agent-only folder for collisions only) acceptable?
3. Is replacing WinForms later cheaper than carrying ~81 MiB of duplicate
   identical runtime files?
4. Would publishing Agent as framework-dependent, or App and Agent against
   one shared framework pack, change the five collisions, and would that
   break the current unpackaged self-contained portable promise?

No implementation follows from this document until the developer confirms a
later Plan.
