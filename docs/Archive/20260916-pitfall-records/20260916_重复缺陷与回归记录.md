## 反复出现的问题

| 问题 | 历史表现与追溯 |
| --- | --- |
| 采集对象持续多出 | 人工确认某项应有 7 个对象，却出现几十个。补过滤仍无效，因为旧结果继续参与合并；又补合并筛选，最后才改为同来源替换。`5951703` → `00dee27` → `12add48`。这是同一问题连续未收口，7 不是通用数量限制。 |

| 结果未知与提交对账 | V0.39 已修过“请求发出后回复丢失不能算明确失败”（`e9f799f`）；到 V0.53，模拟提交仍需补 CommitId 绑定和不可变回执（`0473f64`）。旧路径处理过的可靠性问题，在后续路径仍有缺口；不是同一行代码已证实回退。 |
| Agent 身份与生命周期 | Local 身份、进程实例、陈旧 endpoint 和关闭终态先后补救：`ab83458`、`e57093d`、`b0945a8`、`d1868f0`。这些是同类边界问题在不同路径暴露，不能仅凭多次修复就认定全部是复发。 |
| 监控数据链路不完整 | 指标在模型中存在，不代表写库、读取和 CSV 都有保存。`0473f64` 补全 14 类指标并区分缺失与零。这属于长期漏覆盖；尚无证据证明是“完整修好后又被改坏”。 |

## 为什么补测试仍不够

- 实现与测试可能共享错误预期；全绿只能证明二者一致，不能证明需求理解正确。
- 只修一个入口或一段转换，旧缓存、其他入口、延迟事件和导出仍可能保留旧行为。
- 已有统一层，处理逻辑却继续向上下游分叉；人工反例出现后仍叠加局部补丁，把查错和纠偏成本留给用户。

采集案例详见[原始复盘](20260916_Codex采集器统一层踩坑记录.md)。不能把当时的“替换”“过滤”固化成所有需求的死规则，也不能把普通实现判断不断上交用户。

## 本轮补测的实际边界

`e81c116` 只补了采集事实写库/重载/报告、监控双写入路径与 CSV、即时/草稿提交对账测试；相关三个项目 196 项通过。没有改业务实现，没有验证真实 Windows 采集过滤、原生 UI 事件或完整进程重启，也没有消除重复实现路径。

因此，本轮补测不能宣称已解决重复踩坑。后续排查仍需用具体反例追踪完整结果来源，并以旧代码、原始数据和已确认结果交叉核对；只有找到实际原因，才能判断该改代码、补测试还是修正预期。
