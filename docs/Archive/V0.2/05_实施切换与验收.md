# V0.2 实施、切换与验收

## 1. 实施原则

- 在独立重写分支中完成，不在 `main` 上边写边替换。
- 当前 V0.13 保持可构建和可回退。
- 新旧架构不要求共享数据库或内部 DTO。
- 可以使用一次性迁移工具，但不为旧格式承担长期兼容。
- 每个阶段都持续测试；只有最终切换是一次性的。
- 不提交、推送、打标签或发布，除非用户明确要求。

## 5. 性能验收

在开发机器使用模拟、只读数据和明确测试目录：

- UI 线程不执行数据库批量写入、文件哈希或采集解析。
- Monitor 在最高配置采样率下保持交互响应。
- 数据库批量写入队列有界，并可观察 backlog 和丢样。
- 百万级监控样本的分页查询不一次性载入内存。
- Test 历史和比较使用分页、范围和聚合查询。
- 启动先加载上次快照，不等待完整本机扫描。
- 外部工具运行和解析不在 UI 进程。
- Agent 长时间运行时内存、句柄和写入 backlog 有界。

具体毫秒阈值在新架构首个可运行版本上测量后冻结；在冻结前不得编造跨硬件通用数字。

## 6. 手工迁移策略

V0.2 不保证自动读取所有旧内部格式。

迁移步骤：

1. 保留原 `%LocalAppData%\WinPool` 和便携 `Data`。
2. 生成文件清单、大小和 SHA-256。
3. 只选择确有价值的模拟系统、监控 CSV 和设置。
4. 通过一次性导入器写入新数据库。
5. 比较系统数量、会话数量、样本数量和附件哈希。
6. 导出新格式并抽样复核。
7. 旧数据继续保留，不直接删除。

不迁移：

- 可重新生成的缓存；
- 已损坏或 schema 不明的临时状态；
- 未脱敏且无必要保留的数据；
- 仅用于旧实现内部的 UI 状态。

## 7. 切换步骤

1. 停止功能开发，只接受阻断缺陷。
2. 完成 Release x64 构建和全部自动测试。
3. 完成人工 UI 与安全验收。
4. 在模拟环境运行完整测试工作流。
5. 在当前机器验证采集、托盘监控和文件型测试。
6. 证明全部存储结构修改被拒绝，测试文件路径不能逃逸。
7. 验证 Flush、TRIM/Optimize、调度和临时电源计划的警告、审计及恢复。
8. 完成必要数据的手工迁移演练。
9. 将 V0.2 架构里程碑映射到产品显示版本 V0.21；schema、算法和 IPC 版本保持独立。
10. 一次性将新架构切换为活动实现。
11. 保留 V0.13 源码、发布包和数据备份作为回退。

## 8. 回退原则

- 回退是恢复 V0.13 发布包和原数据副本，不做双向数据库同步。
- V0.2 数据不会自动写回 V0.13 格式。
- 切换失败时保存 V0.2 数据库、日志和崩溃证据。
- 不直接删除失败实现；按项目规则移动到项目根 `Old` 或 `Rubbish`。
- Git 历史、标签和发布动作必须由用户另行明确授权。
