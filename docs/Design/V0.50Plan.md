## 2. 六个 BUG：修复边界与验证场景

### B1：已有空池创建虚拟磁盘时，草稿容量与执行上限不一致

- 入口：[EditWorkspace.cs](../../src/WinPool.Application/EditWorkspace.cs) 的 `InsertDraftVirtualDisk`、[SimulationDraftPlanner.cs](../../src/WinPool.Application/SimulationDraftPlanner.cs)、[StorageSystems.cs](../../src/WinPool.Application/StorageSystems.cs) 的 `CreateVirtualDisk`。
- 现状：草稿把池物理剩余量当作虚拟磁盘逻辑大小；提交又按副本与旧 1% 余量估算，导致页面默认创建值被执行端拒绝。
- 要求：草稿默认值、MAX、预检查、实际模拟应用使用同一容量计算入口；区分物理剩余与逻辑可用量，不靠放宽执行校验解决。分层磁盘按各层自身布局计算，不能将 SSD/HDD 合并后取全体最小盘容量。
- 验证：合法已有空池创建默认虚拟磁盘成功；Mirror 不使用物理容量作逻辑大小；超出上限明确拒绝；创建与预览的容量一致。

### B2：解散池后又删除其子对象，整批应用失败

- 入口：`SimulationDraftPlanner.Build`、`AppendPartitionAndVolumeSteps`、模拟解散/删除服务。
- 现状：先执行级联解散，后续计划仍含该池虚拟磁盘等删除动作，因目标已不存在而失败。
- 要求：采用 §5 的解散父动作与有序子动作。一个对象只删除一次；解散父动作负责分组，执行子动作后不得再调用一次会重复删除的旧级联路径。单独删除虚拟磁盘也要避免与分区清理重复。
- 验证：空池、只有成员的池、有虚拟磁盘/分区/卷的池都能在规则允许及必要确认后解散；无悬空关系、重复删除、误报目标不存在；任何阻塞都不部分保存。

### B3：Parity 容量按副本数 1 计算，漏算校验占用

- 入口：[StorageCapacity.cs](../../src/WinPool.Domain/StorageCapacity.cs)、`BuildTier`、虚拟磁盘与草稿容量调用方。
- 要求：计算显式区分 Simple、Mirror、Parity；Parity 使用列数与校验冗余，不用 `copies = 1` 代替算法。只支持规则已有依据的布局，不顺便开放新冗余家族。MAX 和手动容量上限共同使用修复结果。
- 验证：三块各 100 GiB、三列单校验的理想逻辑量是 200 GiB，MAX 为 200 GiB；两块各 100 GiB 的两副本 Mirror 为 100 GiB。非法列数/副本/成员数量和信息不足有具体原因，热备及退役盘不贡献数据容量。

### B4：修改已有池参数可以绕过布局与容量规则

- 入口：[StorageEditRules.cs](../../src/WinPool.Application/StorageEditRules.cs) 的 `EvaluateUpdatePool`、`UpdateStoragePool`、`PatchTier`。
- 现状：修改操作的规则检查过浅，执行直接写入布局/副本/容量字段，图关系正确不等于存储语义合法。
- 要求：App 内置规则针对修改后的受影响池/层校验成员、布局、容量和已有数据限制；规则作用于全部相关入口，不仅页面按钮。参数改变时更新受影响估算及来源，失效的采集能力证据不能继续当作有效值；只改名称不重算容量。
- 验证：单盘 Simple 改为不合法 Mirror 被拒绝；超容量被拒绝；有数据且禁止改层参数时显示具体原因；合法修改成功；失败原文档不变；无关对象不因未知字段被全面封禁。

### B5：新池创建计划丢失层容量和自动分区意图

- 入口：`ApplyFormToWorking`、`InsertDraftVirtualDisk`、`SimulationDraftPlanner.Build` 的 `CreateTieredPool` 参数及对应模拟创建链路。
- 现状：计划没有完整传递层容量；自动分区开关未可靠变成草稿中的分区/卷，因此创建时可能忽略容量输入、文件系统参数及自动分区选择。
- 要求：将表单意图完整带到本次计划：层容量、MAX/手动选择、自动创建虚拟磁盘/分区、文件系统与分配单元等。SCM 有对应容量字段时也完整贯通；不靠“草稿恰好已有 Partition”推断开关。复用类型化参数，不从显示文本反推意图。
- 验证：新池手动层容量与 MAX 各正确应用；自动分区开启后建立正确 VD → OS Disk → Partition → Volume 关系，关闭后不偷偷创建分区；文件系统/簇参数正确；没有重复 ID 或悬空引用。

### B6：目录挂载路径被误认为盘符，改盘符时遭删除

- 入口：[StorageModels.cs](../../src/WinPool.Application/StorageModels.cs) 的 `VolumeInfo.DriveLetter`、`IsDriveLetterAccessPath` 及其调用方。
- 现状：凡以字母加冒号开头都被认作盘符，`C:\Mount\Data\` 既可能被显示成 C:，也会在改盘符时被移除。
- 要求：用同一识别函数区分完整盘符根路径、目录挂载路径和卷 GUID 路径。只把完整的 `X:` / `X:\` 识别为盘符访问路径；兼容内部独立字母值时仅接受整个值就是一个字母，不使用路径前缀判断。
- 验证：只有目录挂载的卷显示为无盘符；更换/清除盘符只改变盘符访问路径，原目录挂载和卷 GUID 路径逐项保留；保存加载后相同。

## 3. MAX、容量单位与预配类型

### 3.1 MAX 交互

- 在池属性区每个可编辑层容量输入框后增加一个固定大小的**单图标按钮**；提示文字中英分别为“使用最大容量” / `UseMaximumSize`，有可访问名称。现有只读容量字段不变成可编辑字段。
- 默认数字模式。点击按钮进入 MAX 模式，输入框显示 `MAX(196GiB)` 这样的文本，其中数值是当前推测最大值。不能只在提示中写 MAX，也不能把 `MAX(...)` 当作普通数字解析。
- 再次点击退出 MAX，显示当前推测值对应的普通数字；用户输入数字时也退出 MAX，保留用户输入。允许正常清空、粘贴、修正输入；无效输入显示原因，不静默恢复 MAX。
- MAX 模式下，成员、布局、副本/校验、可用量等影响容量的条件改变，自动更新括号内数值；手动模式保留数字，若超过新上限则显示规则原因，不偷偷改小。
- 表单的 MAX 状态必须随选中对象、草稿撤销/重做正确保留；应用成功或放弃后按已保存对象重新显示普通数字。MAX 表示本次编辑意图，不是 Windows 采集事实。
- 复用现有输入控件和绑定，必要时以可解析的文本输入替换 `NumberBox`，不为 MAX 单独引入通用控件库。所有入口通过同一个“模式 + bytes”转换，不依赖显示字符串存储业务状态。

### 3.2 本版最大值算法

```text
GiB = 1,073,741,824 bytes
粒度 = 4 × GiB
推测最大值 = (理想可用逻辑容量 bytes / 粒度的整数商) × 粒度
```

- 示例：199.86 GiB → 196 GiB；200 GiB → 200 GiB；不足 4 GiB → 0，此时不得创建零容量对象，显示无可创建容量的原因。
- 理想可用逻辑容量来自 B1/B3 的统一计算：先排除非数据成员、已被其他对象占用的空间，再按目标布局折算；同一层调整时可计入该层已有分配，不能把自己的容量再扣一遍。不得以池 `Size - AllocatedSize` 直接代替逻辑容量。
- 对成员空间均衡且布局合法的已支持配置：Simple 理想效率 1；Mirror 为 `1 / 副本数`；常规 Parity 为 `(总列数 - 校验列数) / 总列数`。列数不自动等于全池磁盘数。混合介质按层分别计算；不等容量成员仍需按已支持布局的可分配空间约束，不能仅乘容量效率放行。
- 所需列数、成员可分配空间或布局依据不足，规则返回信息不足，不编造 MAX 数值。采用已有明确的受支持默认值时，该默认值必须成为可见配置并参与后续检查，不在执行阶段悄悄另选。
- **MAX 路径不再扣旧 1% 规划余量，也不以 Interleave 代替 4 GiB 取整。** 本版模拟容量上限、默认创建值与手动输入的上限校验统一到新估算，避免 MAX 在提交时被旧算法拒绝。手动数字不因此一律强制取 4 GiB 倍数，仍检查其适用的合法粒度及范围。
- 全程使用整数 bytes 和溢出检查，显示舍入不参与业务运算。保持物理占用与逻辑容量的区别，Mirror/Parity 的池占用不能只增加逻辑大小。
- 4 GiB 是**本版模拟估算策略**，不是所有 Windows 配置的真实分配粒度，也不保证真实创建成功。采集值不得被该公式改写，模拟结果标记 `SimulatedEstimate`。
- 未来保留 `UseMaximumSize` 语义：真实非分层创建可映射到适用的 `-UseMaximumSize`；分层创建需按 Windows 支持的层大小接口及参数组合处理，不承诺逐层直接套用该开关。本版不执行或新增真实写入适配器，不因预留意图先扩展 IPC/数据库。

### 3.3 软件容量单位

- 范围为软件生成的全部容量数字：两页表单、拓扑、属性、对比、硬件报告、监控中的空间容量、设置中的文件大小、动作与错误文字、复制/导出的人类可读容量。两种界面语言都改。
- 容量输入统一标出 GiB；小单位如分配单元/Interleave 显示 KiB，不能继续用含糊的 GB 或 64K 表示容量。仍按原始 bytes 存储、采集和 IPC 传输。
- 已经是 GiB 等正确单位的格式化函数直接复用，只改错误或分散入口，不重写整个显示系统。原来除以 1024 却写 GB 的只改单位；原来除以 1000 的需改换算。不能机械替换源码中的所有 `GB`。
- 不改用户自定义名称、硬件原始型号、微软 API/命令字面量或历史证据。PowerShell 的合法 `GB` 语法不能改成不存在的 `GiB` 后缀；解释文字使用 GiB，命令参数使用 bytes 或原合法语法。JSON 字段名及原始 bytes 不因显示单位改名。
- 本条针对容量；网络 Gbps 等速率不当作容量改写。磁盘吞吐若本已按 1024 换算，单位应如实标 MiB/s，不把位速率改成字节容量。

### 3.4 预配类型

- 池属性层表格中的预配类型使用 `ComboBox`，替代当前只读文本值；即使只有 `Fixed` 一个受支持值也显示下拉框。
- 值来自当前受支持范围，不以增加下拉框为由开放 Thin。仅有 Fixed 时保持 Fixed；未知或只读采集值如实显示并禁用编辑，不静默改成 Fixed。
- 选择仍属于结构草稿；切换选中对象、更新草稿、放弃、应用均保持正确，不成为立即提交入口。

## 4. App 与 Agent 校验分工

```text
App：内置规则检查 → 生成合法模拟结果 / 类型化真实操作意图
  ↓
Agent
  ├─ 模拟：系统检查标记为跳过 → 提交保护 → 保存模拟结果
  └─ 真实（未来）：查询 Windows → 检查实际条件 → 执行 → 重新采集
```

- 内置存储规则与算法继续在 Domain/Application，不写入 XAML 事件中的另一套条件。App 进程调用该服务用于编辑反馈、动作预检查和最终模拟应用。
- Agent 模拟提交不重新调用完整内置规则/模拟操作服务。系统检查结果明确为“模拟模式跳过/不适用”，不能冒充“Windows 验证通过”。不新增一套总是返回成功的系统规则框架。
- Agent 保留封闭请求、调用方/目标模式检查、数据格式与哈希、修订冲突、CommitId 对账、单写入方、事务和脱敏等既有提交保护；“跳过系统检查”不等于直接接收任意请求。
- 接受明确取舍：模拟结构合法性由 App 的业务服务负责，规则遗漏不能指望 Agent 兜底，因此 B1–B5 必须修正。
- 真实模式在本版仍只读并拒绝写入。未来 Agent 不能凭 App 的“已通过”执行，需重新确认目标身份、实际状态、能力/支持容量及授权；预检查通过也不保证执行成功。
- 实施时调整 Development、Product 和相关断言，替换“Agent 提交前重跑内置规则”的旧要求，保留真正的 IPC/数据库边界测试。该旧审查项是架构决定调整，**不作为第七个 BUG 要求重复校验**。

## 5. 只读结构编辑动作窗口

### 5.1 位置与内容

- 名称“待应用动作” / `Pending actions`，作为存储结构页内的只读面板，位于拓扑下方、左下操作控件上方；右侧池属性区保持。内容多时内部滚动，不另开独立原生窗口，不改拓扑布局算法。
- 默认可见，空时显示“暂无待应用动作”。支持展开/折叠子动作，默认折叠；无动作删除、编辑、排序、勾选执行、恢复、历史搜索等控件。
- 拓扑拖拽和结构按钮产生的实际修改立即更新；只有选中、显示开关、取消确认、被拒绝且未改变草稿的操作不增加动作。池属性草稿变化也反映进列表，不能存在会在应用时执行但窗口遗漏的修改。
- 列表不是点击流水账，不记录时间历史或撤销事件。以已保存基线与当前草稿的净差异生成，必要的 MAX/自动分区意图附属于草稿。

### 5.2 合并与清空

- 同一磁盘 A → B → C，保留一条 A → C；回到 A 后移除移动动作。改名 A → B → C 同理；新建后又删除且最终无其他差异，不保留空操作。
- 撤销/重做更新草稿及其动作列表。动作显示、规则结果和 MAX 意图必须同步，不能保留已经撤销的旧原因。
- “放弃结构修改”恢复基线并清空全部动作；“应用结构修改”执行当前可见动作计划，成功后刷新基线并清空。普通校验或提交失败保留草稿、动作及原因。
- 结果未知时保留动作并标“结果待确认”，禁止盲目重复提交；现有 CommitId 对账确认已提交则刷新并清空，确认未提交才允许按有效基线重试。修订冲突明确显示，不覆盖别人的状态，也不自动清掉用户草稿。
- 页面重建、切换系统和分区页立即提交导致结构基线变化时，不得套用旧列表：沿用已有草稿处理方式并使计划失效重建；无持久化草稿历史，不为此引入自动合并框架。

### 5.3 解散池父子动作

```text
▸ 解散 Pool01                         [直接显示汇总原因/数据影响]

展开：
▾ 解散 Pool01                         [同上]
    删除分区 D: 及其卷                [该子动作原因/数据影响]
    删除分区 E: 及其卷                [该子动作原因/数据影响]
    删除虚拟磁盘 VD01                 [该子动作原因/数据影响]
    将 Disk01 移回原始池              [该子动作原因]
    将 Disk02 移回原始池              [该子动作原因]
    删除空池 Pool01                   [该子动作原因]
```

- 删除所有相关分区/卷 → 删除虚拟磁盘及派生 OS Disk/层关系 → 移回全部成员（包括热备/退役） → 删除空池。多个虚拟磁盘同样枚举，已有无卷分区也列出；不把“只允许新建单 VD”误用于禁止解散已有多 VD 池。
- 子动作是本次实际执行步骤，不是虚构说明。父动作为一次解散的分组，不重复执行级联删除；派生关系清理由对应对象删除步骤一次完成，不把每条内部关系都画成子动作。
- 已包含于解散的删除/移动，不再在顶层重复列出。成员曾在草稿中移到别池时，以最终归属为准保留一次移动；留在被解散池的成员回原始池。分组不能悄悄覆盖用户已明确的最终归属。
- 删除空池的最后一步必须确认池已空、无子对象。可在现有类型化模拟操作中补一个仅删除空池的动作，不建立通用依赖调度框架。
- 数据删除经一次现有应用确认，清楚列出影响对象；不为每个子动作再弹一轮确认。

### 5.4 规则标记：父动作折叠时就能知道原因

- **原因由内置规则服务提供，UI 只翻译、组合和显示。** 复用稳定规则 Code、对象 ID、参数和现有 Allow/Deny/InsufficientInfo；数据影响提示由同一服务基于相关对象生成，不在页面另写容量或数据占用规则。
- 每个动作/子动作直接显示具体原因文本，不只显示红点、感叹号或鼠标悬停提示。名称后文本可换行；不能省略到必须展开才能知道原因。
- 父动作汇总所有不同的子动作原因，附上受影响对象/数量，重复原因合并；不能只写“有 N 个错误，请展开”。子动作仍显示各自原因。
- 区分“将删除已有数据，可确认执行”和“无法应用：已有数据，不允许修改层布局”等阻塞。数据存在不一律拒绝，也不降低已有禁止条件。
- 容量不足、成员不足、布局不支持、信息不足等使用同样方式；存在 Deny 或当前无法解决的 InsufficientInfo 时禁用应用，原因就在窗口内。
- 按最终执行顺序在内存候选状态上检查：删除分区之后，后续步骤应看到删除后的状态，不能把所有步骤都对原始快照检查。阻塞步骤不得假装成功；其依赖步骤显示“前置动作未通过：具体原因”，独立动作继续检查，不产生虚假的后续“目标不存在”。
- 预检查不保存、不增加修订、不生成真实提交记录；没有 I/O 写入。修改草稿后重算原因，信息恢复时清掉旧标记。

### 5.5 与执行共用一份计划

- 扩展现有 `SimulationDraftPlanner` / `SimulationDraftPlan`，用最小父子分组信息表达窗口，不另造动作日志模型和一套执行路径。
- 草稿改变后生成并持有本次不可变计划；动作面板、应用确认、规则检查和最终执行引用这一份计划。实际执行展平其中的有序子步骤，每步最多一次。
- 修复当前应用前后多次 `Build` 导致 PlanId/新对象 ID 重新分配的问题；确认期间若草稿或基线改变，该确认失效并重新显示计划，不能静默提交另一份。
- 尽量沿用现有一次模拟提交的原子保存。动作窗口本身不要求修改 SQLite schema 或存储完整历史；格式号仅在真实的持久契约不兼容时调整，不机械跟随产品版本升级。

本次只做文档检查，不运行测试、构建、WinUI 或真实设备操作。以下为批准实施后的验证场景，不是已完成证据；若后续用户仍限定“不跑测试”，必须遵守并把相应项标为 unverified，不能以计划验收为由绕过限制。

- **六个 BUG**：分别完成 §2 的正例/反例；使用真实应用服务验证结果，不以仅匹配源码字符串代替行为。
- **MAX**：首次/再次点击、手输/粘贴、切换对象、成员变化、撤销重做、无容量和信息不足；199.86→196、200→200、<4→拒绝；创建/更新与显示一致，Parity/Mirror 不套原始容量。

- **动作**：A→B→C 只剩 A→C；移回 A 清除；创建后删除不残留；放弃清空；成功应用清空；普通失败保留；撤销/重做同步。
- **解散**：父项默认折叠，删除分区/VD/成员/空池的子步骤齐全且不重复；已有数据提示明确；父子原因均直接可见；同一计划预览与执行一致。
