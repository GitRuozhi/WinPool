## 0. 文档状态

* **目标版本**：V0.34
* **版本迭代**：`c=4`
* **基线版本**：V0.33
* **基线提交**：`de6bae8ee530829e1e341896b7786167e23d132f`
* **性质**：V0.33 后续缺陷修复与一致性硬化
* **功能扩展**：不包含
* **架构扩张**：不包含
* **remote_gate**：`not_required`
* **Push / Tag / GitHub Release / Binary Upload**：未经新的明确授权不得执行
* **V0.33 历史记录**：保持冻结，不回写归档内容
* **V0.33 native/manual 状态**：继续保持原有 `unverified`，不得因为 V0.34 自动测试通过而改写

本计划只处理 V0.33 静态复核发现的高优先级代码缺陷，不新增产品能力，不改变 V0.3 的安全边界，不启用任何真实存储拓扑修改能力。

# 1. V0.34 目标

V0.34 必须完成以下目标：

1. 消除 Worker/Broker 在 callback 异常或卡死时产生孤儿进程的可能。
2. 彻底完成 `ProcessInstanceId` 语义，禁止 Main App 生命周期重新退化为 PID identity。
3. 建立唯一、稳定的 Local `SystemId`，禁止一次库存采集产生两套 system identity。
4. 修复 storage migration 在 pointer 已提交后仍返回 `Failed` 的 commit-boundary 错误。
5. 建立 Simulation revision 的唯一 authority。
6. 将 event reconnect 从“transport 恢复”提升为“客户端状态完整恢复”。
7. 消除 event queue `DropOldest` 造成的静默 event gap。
8. 修复 live tool progress 中 stdout/stderr 文本状态串流以及 EOF decoder 未 flush。
9. 将 `ShutdownPending` 提升为明确、可观察、可重试的 Agent 生命周期状态。
10. 为上述问题补充确定性的 regression tests，并完成完整 Release 自动验收。

---

# 2. 非目标

V0.34 不做以下工作：

* 不增加新的项目。
* 不引入 Actor framework、service bus、通用消息框架或新的 dependency injection framework。
* 不重新设计整个 Agent runtime。
* 不继续拆分 `DesktopAgentRuntime`，除非修复本计划缺陷需要极小范围移动。
* 不继续进行纯粹为了“架构纯洁度”的 Application/Presentation 清理。
* 不重构 `CommandLog`、`GlobalNotificationService` 等非 blocker 架构债。
* 不增加 durable event replay。
* 不增加跨版本 IPC compatibility adapter。
* 不重新引入 `WinPool.Core`。
* 不修改真实磁盘、分区、卷、Storage Pool、Storage Tier、Virtual Disk。
* 不把 V0.33 已冻结的归档 Plan 改写成“当时已经解决这些问题”。

# 3. V0.34 必须满足的系统不变量

## INV-01 Child process ownership

一旦 `Process.Start` 成功：

> child process 必须立即进入一个 guaranteed cleanup ownership scope。

之后发生的任何：

* callback exception
* cancellation
* IPC failure
* persistence failure
* scheduling restoration failure
* completion callback timeout

都不得绕过最终：

* graceful exit grace
* process-tree termination
* bounded final wait
* terminal registry update

不得产生孤儿 Worker/Broker。

---

## INV-02 Local system identity

对于同一台机器上的当前 Local storage system：

```text
StorageSystemDocument.SystemId
==
InventorySnapshot.SystemId
==
systems.system_id
==
comparison/local-history SystemId
```

连续刷新、关闭 App、重新打开 App、Agent 重启均不得产生新的逻辑 Local `SystemId`。

Local → Simulation 时：

```text
Simulation.SystemId != Local.SystemId
```

如需记录来源：

```text
Simulation.SourceSystemId = Local.SystemId
```

来源信息只能作为 provenance，不能作为 Simulation identity。

---

## INV-03 Process incarnation

```text
PID != ProcessInstanceId
```

PID 只能作为 live operating-system lookup key。

必须能够正确区分：

```text
same process + reconnect
```

与：

```text
old process exited
Windows reused PID
new process started
```

任何 shutdown/terminate 行为执行前，都必须重新验证目标 PID 对应的实际 WinPool process incarnation。

---

## INV-04 Storage migration commit point

Pointer commit 是不可逆的逻辑提交点：

```text
before pointer commit
    failure => Failed / Cancelled / rollback

after pointer commit
    cleanup failure != migration failure
```

一旦 pointer 成功切换：

* 当前 active location 必须报告为 target。
* API 不得返回“切换失败且仍在 source”的语义。
* staging/rollback cleanup 失败只能变为 cleanup warning / partial completion。
* cleanup 可以随后安全重试。

---

## INV-05 Simulation revision

必须只有一个 revision authority。

要求始终成立：

```text
StorageSystemDocument.Revision
==
SimulationDocumentPayload.Revision
==
simulation_documents.revision
==
sanitized_json.Revision
```

不能依赖 Decode 阶段覆盖 JSON revision 来隐藏持久化不一致。

---

## INV-06 Event recovery

发生 event pipe disconnect、overflow 或 event gap 后：

> 客户端必须重新获得当前 authoritative Agent state。

Reconnect 成功不能只意味着 named pipe 又连上。

必须完成：

```text
Reconnect
→ authoritative snapshot
→ state reseed
→ observers/UI replace stale state
→ normal event processing resumes
```

---

## INV-07 Event loss must be observable

禁止：

```text
BoundedChannelFullMode.DropOldest
+
consumer unaware
```

造成静默 event loss。

如果 slow consumer 导致队列无法继续：

* 要么安全 coalesce telemetry；
* 要么断开该 event subscription；
* 客户端进入 reconnect + snapshot reseed。

正确性优先于维持一个已经丢失状态的“Connected”连接。

---

## INV-08 Tool stream isolation

每个 external process 至少需要：

```text
stdout decoder
stdout text buffer

stderr decoder
stderr text buffer
```

两条流不得共享可组成 progress token 的文本 buffer。

Process EOF 时必须 flush decoder state。

Raw bytes 仍然是最终 evidence authority。

---

## INV-09 Shutdown observability

Agent 必须存在明确的外部状态：

```text
Running
ShuttingDown
ShutdownPending
Stopped
```

其中：

* `ShuttingDown`：当前 shutdown workflow 正在执行。
* `ShutdownPending`：上一轮 shutdown 已结束但不完整，可以观察并重试。
* `Stopped`：control transport 可以关闭。

`ShutdownPending` 期间至少允许：

```text
GetAgentSnapshot
RequestAgentShutdown
```

其他会创建新工作的请求必须拒绝。

# 5. V34-P1-04 — 修复 Local `SystemId` authority

## 5.1 当前问题

当前 Manage capture 调用路径会由 App/Infrastructure 生成新的：

```csharp
SystemId.New()
```

并通过 Agent request 传入。

Agent 随后将该 request `SystemId` 用于生成和持久化 `InventorySnapshot`。

与此同时，实际 Local `StorageSystemDocument` 又有自己的 `SystemId`。

这会导致同一次 capture 中：

```text
Local document SystemId = A
persisted snapshot SystemId = B
```

下一次 refresh 又可能变成：

```text
Local document SystemId = A
persisted snapshot SystemId = C
```

这是持久化 identity corruption，应作为 V0.34 第一优先级修复。

## 5.2 修复原则

Local `SystemId` 必须由 Agent-owned Local inventory identity 决定。

App/client 不得为 Local capture mint `SystemId`。

## 5.3 实施

### Step 1

删除 Local Manage capture request 中由调用方提供的 `SystemId`。

类似：

```text
CaptureAgentManageInventoryRequest(
    CorrelationId)
```

而不是：

```text
CaptureAgentManageInventoryRequest(
    SystemId,
    CorrelationId)
```

### Step 2

Agent capture 完成后，以 canonical Local document：

```text
sanitized.SystemId
```

作为 snapshot projection 的 `SystemId`。

禁止继续使用 caller-provided random ID。

### Step 3

检查 `CaptureAgentInventoryRequest` / comparison capture。

如果该 request 表达的是当前 Local machine inventory，则同样不得由 App mint system identity。

Native、legacy 和 Manage inventory 必须使用同一个 Local `SystemId`。

### Step 4

Local identity 的 restart 行为必须固定。

首选：

* 从已经持久化的 Local document/identity 获取已有 `SystemId`；
* machine identity 一致时复用；
* 第一次初始化时才创建；
* machine binding 明确不一致时才建立新的 Local system identity。

不得只依赖每次 capture 时临时 `Guid.NewGuid()`。

### Step 5

添加 invariant validation。

保存 Local snapshot 前：

```text
document.SystemId == snapshot.SystemId
```

不满足时 fail closed，不允许写入两套 identity。

## 5.4 Regression tests

至少增加：

### V34-T-ID-01

连续执行 10 次 Local Manage capture：

```text
all document.SystemId equal
all InventorySnapshot.SystemId equal
```

### V34-T-ID-02

Agent restart 后再次 capture：

```text
SystemId unchanged
```

### V34-T-ID-03

Native/legacy comparison：

```text
native.SystemId
==
legacy.SystemId
==
canonical Local SystemId
```

### V34-T-ID-04

Local → Simulation：

```text
simulation.SystemId != local.SystemId
```

并验证 provenance 正确。

### V34-T-ID-05

SQLite `systems` 中不得因为重复刷新产生多个代表同一 Local machine 的 system row。

# 6. V34-P1-05 — 修复 Storage migration commit boundary

## 6.1 当前问题

当前顺序大致为：

```text
replace target
verify
commit pointer
pointerCommitted = true
return success
finally:
    delete staging
    delete rollback
```

C# 在真正 return 前仍会执行 `finally`。

因此 pointer 已成功提交后，如果：

```text
DeleteDirectoryTree(...)
```

失败，异常可能覆盖原本的 success 并被外层 catch 转换为：

```text
storage.location.apply_failed
```

但 active pointer 已经指向 target。

客户端看到“失败”，实际系统已经成功切换。

## 6.2 修复原则

明确分成：

```text
PRE-COMMIT
COMMITTED
POST-COMMIT-CLEANUP
```

三阶段。

## 6.3 实施

### PRE-COMMIT

任何错误仍允许：

* rollback target
* `Failed`
* `Cancelled`
* `Rejected`

### COMMITTED

只有：

```text
pointerCommitter.CommitAsync()
```

成功以后才进入。

一旦进入：

```text
pointerCommitted = true
```

之后不得再转换为 pre-commit failure。

### POST-COMMIT-CLEANUP

staging / rollback cleanup：

* best effort
* bounded
* independently reported

建议语义：

```text
Succeeded
```

或：

```text
PartiallyCompleted
code = storage.location.cleanup_pending
```

但绝不能报告：

```text
active location remains source
```

### Cleanup retry

允许下一次 StorageLocationManager 初始化或下一次切换时安全删除已知 migration temporary roots。

必须继续：

* 校验 configured root
* 拒绝 reparse point
* 禁止任意路径删除

## 6.4 Tests

### V34-T-MIG-01

Pointer commit 成功后，让 rollback cleanup 故意抛 `IOException`。

验证：

```text
current mode == target
result != Failed
pointer == target
```

### V34-T-MIG-02

Pointer 成功后 staging cleanup 失败，同样不得返回 pre-commit error。

### V34-T-MIG-03

Pointer commit 之前 cleanup/verification failure：

```text
old pointer retained
previous target restored
result == Failed
```

### V34-T-MIG-04

遗留 post-commit temporary root 可以在后续安全清理。

### V34-T-MIG-05

Standard → Portable → Standard roundtrip 仍保持 exact manifest。

# 7. V34-P1-01 / P1-02 — 统一 Worker/Broker child ownership

这两个问题作为一个 implementation package 修复，但保留两个 defect ID。

---

## 7.1 TestWorker

### 当前问题

Worker 已经：

```text
Process.Start
```

之后，`workerStarted` callback 仍可能发生在真正 cleanup `try/finally` 之外。

如果 callback 抛异常：

* Worker 已存在；
* cleanup policy 尚未获得 ownership；
* 方法退出；
* Worker 可能继续运行。

另外 `workerCompleting` 可能执行：

* scheduling restore
* audit
* recovery persistence

且部分调用使用 `CancellationToken.None`。

如果这些 callback 自己永久阻塞，则 bounded Worker exit policy 永远无法开始。

## 7.2 修复结构

必须改成：

```text
StartWorker
↓
immediately enter outer try/finally
    workerStarted
    connect/auth
    execute
    workerCompleting
finally
    bounded reap
```

不允许：

```text
StartWorker
workerStarted
try/finally
```

## 7.3 Callback timeout

对：

```text
workerStarted
workerCompleting
```

建立明确 timeout。

callback timeout 时：

1. 记录 callback failure。
2. scheduling/recovery entry 保留。
3. 继续 terminate Worker process tree。
4. bounded final wait。
5. 返回原始 failure + cleanup diagnostic。

不能为了等待 restoration 而无限保留运行中的 Worker。

## 7.4 ElevatedBroker

Broker 使用完全相同的 invariant：

```text
StartBroker succeeded
=> outer cleanup ownership already established
```

`brokerStarted` 必须移动到 cleanup scope 内。

Broker completion callback 同样必须 bounded。

## 7.5 不建立大型 abstraction

允许建立一个很小的 internal helper 来执行：

```text
bounded callback
+
bounded process reap
```

但不得为了 Worker/Broker 两个 host 引入：

* generic process orchestration framework
* actor abstraction
* service bus
* 新项目

## 7.6 Tests

### V34-T-WRK-01

`workerStarted` 立即抛异常。

验证 Worker 最终退出。

### V34-T-WRK-02

`workerStarted` cancellation。

验证 Worker 最终退出。

### V34-T-WRK-03

`workerCompleting` 永不完成。

验证 callback timeout 后 Worker 被 terminate。

### V34-T-WRK-04

completion callback failure 不覆盖“process successfully reaped”事实。

### V34-T-WRK-05

Worker 返回 Completed 但 process 不退出：

继续验证现有 bounded kill 行为。

### V34-T-BRK-01

`brokerStarted` 抛异常。

Broker 不得残留。

### V34-T-BRK-02

Broker completion callback 阻塞。

必须 timeout + reap。

# 8. V34-P1-03 — 完成 Main App process incarnation identity

## 8.1 当前问题

Registry 已使用：

```text
ProcessInstanceId
```

作为 primary identity。

但 Main App control handshake 每次连接时由 Agent 新建 `ProcessInstanceId`，如果 PID 已存在，又把连接解释为原 registration heartbeat。

结果仍存在：

```text
same PID => same process
```

的隐式假设。

Windows PID reuse 后可能误把一个新 App process 当成旧 incarnation。

## 8.2 新合同

Main App 自己必须在 process lifetime 开始时创建：

```text
ClientProcessInstanceId
```

同一个 App process 的所有 reconnect 必须携带同一 ID。

下一次全新 App process 使用新的 ID。

## 8.3 Handshake

Agent handshake 增加：

```text
ProcessInstanceId
```

Agent 不再为 Main Application connection 临时生成新 process incarnation ID。

## 8.4 判定规则

### 同一 ProcessInstanceId + 同一 PID

解释为：

```text
same process reconnect
```

允许恢复 connection/heartbeat。

### 同一 ProcessInstanceId + 不同 PID

拒绝：

```text
process_instance_pid_mismatch
```

### 不同 ProcessInstanceId + 同一 PID

视为可能发生 PID reuse。

必须先确认原 registration 已 stale，并验证新 client：

* current named-pipe client PID
* expected executable path
* OS process start identity

然后 terminalize 旧 registration，再注册新的 instance。

### 不同 ProcessInstanceId + 不同 PID

正常新 process registration。

## 8.5 PID anti-reuse witness

仅使用 PID + executable path 仍不足以证明 incarnation。

建议在首次 handshake 时由 Agent 捕获：

```text
Process.StartTime UTC
```

并作为 OS-level process birth witness 存入 registration。

任何 shutdown/terminate 前重新检查：

```text
PID
expected image
process start time
```

不匹配则：

```text
old registration = stale
```

禁止向该 PID 发送终止操作。

## 8.6 Connection 与 process lifetime 分离

Control pipe disconnect 不等于 process exit。

不得仅因为 event/control pipe EOF 就立即声明 App process 已退出。

但是：

* reconnect
* heartbeat sweep
* shutdown

必须有 stale reconciliation。

## 8.7 Tests

覆盖以下 matrix：

| Existing                               | Incoming                     | Expected                   |
| -------------------------------------- | ---------------------------- | -------------------------- |
| same instance / same PID               | reconnect                    | accepted                   |
| same instance / different PID          | invalid                      | rejected                   |
| different instance / same reused PID   | stale old + new registration | accepted                   |
| stale PID now belongs to unrelated exe | shutdown                     | never terminate            |
| stale PID now has different start time | shutdown                     | never treat as old process |

# 9. V34-P2-01 — Simulation revision 单一 authority

## 9.1 当前问题

SQLite update 当前会：

```sql
revision = revision + 1
```

同时又接受已经序列化的：

```text
sanitized_json
sha256
```

JSON 内部也包含 Revision。

如果调用者 JSON revision 与数据库 next revision 不一致：

```text
DB revision = 8
JSON Revision = 7
```

仍可能被保存。

Decode 再覆盖 revision，会隐藏这一事实。

## 9.2 决策

V0.34 采用：

> 编码后的 typed document/payload 提供目标 revision，SQLite repository 验证 revision 连续性并原样持久化。

## 9.3 新规则

新建 document：

```text
payload.Revision == 1
JSON.Revision == 1
```

更新：

```text
payload.Revision == databaseRevision + 1
```

同时：

```text
JSON.Revision == payload.Revision
```

SQLite UPDATE 必须同时校验：

```text
expectedPreviousSha256
expected previous revision
```

## 9.4 SQL 语义

禁止简单：

```sql
revision = revision + 1
```

而不验证 caller payload。

改为类似：

```text
SET revision = $revision
WHERE
    document_id = $id
    AND sha256 = $expectedSha
    AND revision = $revision - 1
```

## 9.5 Decode

Decode 不再使用：

```text
with { Revision = payload.Revision }
```

来修正一个错误 JSON。

不一致直接：

```text
InvalidDataException
```

## 9.6 Tests

* create revision 1 success
* create revision 0/2 rejected
* update 1 → 2 success
* jump 1 → 3 rejected
* stale SHA rejected
* JSON revision != payload revision rejected
* database revision != payload expected predecessor rejected
* save/reload exact roundtrip

# 10. V34-P2-05 — `ShutdownPending` 外部状态合同

该项应在 event recovery 之前完成，因为 snapshot reseed 必须知道真实 Agent lifecycle。

## 10.1 Application contract

不要让 Application 引用 Agent implementation enum。

新增稳定合同，例如：

```text
AgentLifecycleState
    Running
    ShuttingDown
    ShutdownPending
```

`Stopped` 可以保留为协议状态，但正常 connected snapshot 很少能观察到。

## 10.2 Shutdown snapshot

建议增加：

```text
AgentShutdownStatus
{
    State
    LastAttemptAtUtc
    FailedSteps
    RemainingProcessIds
    CanRetry
}
```

并放入：

```text
AgentSnapshot
```

## 10.3 Request policy

### Running

正常 request 全部按现有策略处理。

### ShuttingDown

允许：

```text
GetAgentSnapshot
```

重复 shutdown request 不得启动第二套并发 workflow。

### ShutdownPending

仅允许恢复类请求，例如：

```text
GetAgentSnapshot
RequestAgentShutdown
```

禁止：

```text
StartTest
StartMonitoring
Inventory mutation-like workflow
Support action
```

## 10.4 Retry serialization

保持单一 shutdown-operation gate。

不能出现：

```text
retry A
retry B
```

并发执行两个 shutdown workflow。

## 10.5 Tray

Tray 不应通过自己的：

```text
bool shuttingDown
```

猜测 Agent authority。

Incomplete shutdown 后必须读取 authoritative snapshot：

```text
ShutdownPending
```

再决定：

* tray label
* retry availability
* blocked commands

## 10.6 Tests

* Running → ShuttingDown
* successful → Stopped
* incomplete → ShutdownPending
* Pending snapshot contains failed steps
* Pending normal request rejected
* Pending shutdown retry accepted
* two concurrent retry requests only执行一个 workflow
* successful retry → Stopped

# 11. V34-P2-02 / P2-03 — Event recovery 与 backpressure

两个问题一起完成。

---

## 11.1 Reconnect 后完整 snapshot reseed

当前 reconnect 不得只恢复 process list。

定义一个明确的 reseed boundary。

Reconnect 成功：

```text
open control channel
open event channel
GetAgentSnapshot
Project snapshot to complete client state
publish one reseed notification
resume normal event processing
```

Reseed 至少覆盖当前 snapshot 可以表达的：

* Agent lifecycle
* active test
* active monitoring session
* managed process state
* current tool state
* latest relevant monitoring state
* shutdown state

消费者应：

```text
replace state
```

而不是把 snapshot 当成几条普通 delta event。

## 11.2 Slow subscriber 策略

V0.34 不实现 durable replay。

同时取消静默：

```text
DropOldest
```

最小、可靠的策略：

```text
BoundedChannelFullMode.Wait
+
Publish TryWrite fails
=> complete/drop that subscriber
=> event pipe closes
=> client reconnects
=> full snapshot reseed
```

这样 overflow 会变成一个明确 recovery boundary，而不是 silent corruption。

## 11.3 Telemetry optimization

Monitor sample coalescing 可以以后优化。

V0.34 先确保：

> 慢 consumer 最坏只是 reconnect，不允许 Connected-but-missing-state。

# 12. V34-P2-04 — Tool live progress stream isolation

## 12.1 当前问题

当前 native progress 已经具有独立：

```text
stdout Decoder
stderr Decoder
```

但两条流的 decode text 仍可能写入同一个 progress text buffer。

例如：

```text
stdout: "4"
stderr: "2%"
```

不能组合成：

```text
42%
```

另外 process exit 时必须 flush decoder 尾部状态。

## 12.2 State 模型

每个 running tool process：

```text
ToolProgressParseState
{
    StdoutDecoder
    StdoutBuffer

    StderrDecoder
    StderrBuffer
}
```

禁止共享 line/token builder。

## 12.3 EOF

`Complete()` 改为真正完成两条 decoder：

```text
decoder.Convert(... flush: true)
```

所有剩余字符：

* 分别进入对应 stream buffer
* 完成最后一轮 progress parse
* 再销毁 parser state

如果 `Complete()` 当前无法返回 progress event，则调整接口让 projector 能在 process-exited event 之前或同时消费 EOF parse result。

## 12.4 Evidence

继续保持：

```text
raw bytes = authoritative evidence
```

live progress parser failure 不得修改 raw evidence。

# 23. V0.34 最终验收重点

最终 review 不以“代码已经改了”为标准，而以以下五个问题为核心：

### 1. Identity

同一个东西是否从头到尾仍然是同一个 identity？

重点：

```text
Local SystemId
ProcessInstanceId
Simulation Revision
```

### 2. Commit boundary

系统是否能明确回答：

```text
操作到底有没有生效？
```

重点：

```text
StorageLocation pointer commit
Simulation revision commit
```

### 3. Process ownership

任何 child process 启动后，是否一定有人负责把它最终 reap？

重点：

```text
TestWorker
ElevatedBroker
```

### 4. Recovery

断线、队列满、shutdown incomplete 后，系统是否能重新回到一个 authoritative known state？

重点：

```text
event reconnect
snapshot reseed
ShutdownPending
```

### 5. Evidence

输出解析、manual case、automatic gate 是否都只报告真实证据？

重点：

```text
encoding
raw output
test results
manual status
version status
```

如果这五个方面全部成立，V0.34 才可以视为真正完成 V0.33 的缺陷收口。
