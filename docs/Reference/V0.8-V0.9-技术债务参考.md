## 1. 为什么延期

原草案同时覆盖 Test、Development、Settings、Manage、Monitor、单实例、恢复、
Broker、关机、诊断和测试基础设施。多数观察有技术价值，但把它们全部塞入 V0.39
会制造新的统一抽象和跨层耦合，扩大 `c=9` 的范围，并延迟已经确认的 V0.4 路线。

V0.3 最终修正只保留命名管道超时隔离及 TestPage Start/Cancel 对账。其余内容在
这里保存，待产品功能和内部契约更稳定后再处理。

## 2. 重新启用规则

未来计划引用本文时必须逐项完成以下动作：

1. 在当时的代码中重新定位并复现，不依赖本文中的旧行号或旧实现假设。
2. 判断问题是否仍有用户可见影响、安全影响、数据一致性影响或可维护性收益。
3. 记录“保留、已自然消失、已由其他设计替代、接受风险、纳入当前 Plan”之一。
4. 每个实施批次只选择一个清晰主题，避免再次形成全项目万能 Guard。
5. 对副作用操作先定义提交边界、取消语义、幂等性和权威对账方式，再设置 timeout。
6. 自动证据、原生人工证据和设备证据分别记录；未执行项保持 `unverified`。

建议优先级：

- **R1**：可能导致重复副作用、错误状态、数据损坏或恢复失真；
- **R2**：可能造成无界等待、静默失败或明显用户阻断；
- **R3**：主要影响诊断、可测试性或维护效率。

优先级只是重新评估的起点，不代表已经批准。

## 3. 通用设计原则

### 3.1 不建立万能操作 Guard

查询、Agent 副作用命令、本地文件操作、外部安装器和安全恢复的取消语义不同，不能
由一个通用方法假设为相同行为。未来如需共享机制，应先按以下类别建模：

| 类别 | timeout 后含义 | 重试要求 |
| --- | --- | --- |
| 纯查询 | 本次等待结束；没有产品副作用 | 可在阻止并发重入后重试 |
| 可权威对账的副作用命令 | 结果可能未知 | 对账确认后才允许下一操作 |
| 不可权威对账的副作用命令 | 保持 Unknown | 禁止自动重试，要求额外确认或稳定检测 |
| 本地可取消长任务 | 尝试真正取消底层工作 | 先确认临时产物和回滚状态 |
| 安全恢复/rollback | 不继承页面取消 | 独立完成并记录恢复结果 |

共享代码只应包含已经稳定的结果类型、状态转换和传输安全规则。页面文案、按钮和
业务对账仍由具体用例决定。

### 3.2 timeout 不等于失败或未执行

任何已经越过提交边界的命令，客户端 timeout 只能表示“未在等待时间内拿到确定
结果”。UI 不得据此显示操作未发生、恢复危险按钮或自动发送第二次命令。

### 3.3 页面 cancellation 与后台取消分离

页面离开通常只表示 UI 不再等待或显示结果。它可能会：

- 真正取消尚未提交的查询；
- 使客户端脱离已经提交的 Agent 操作；
- 真正取消可安全终止的本地任务；
- 不得中断必须继续执行的 rollback。

实现必须明确属于哪一种，不能只把 `CancellationToken.None` 批量替换成页面 token。

### 3.4 诊断与用户提示分离

用户消息应短、稳定、可操作；开发诊断可以更具体，但必须结构化、脱敏、有界，并且
诊断写入失败不能改变主操作结果。

## 4. V0.8 候选技术债务

### TD-801：全局异步操作分类与结果模型

- **建议优先级**：R2
- **历史观察**：多个页面直接使用 `CancellationToken.None`，但各调用的副作用和
  取消含义不同。
- **未来工作**：盘点所有 App 到 Agent、本地服务和外部工具的异步边界；按第 3.1
  节分类；只为至少两个真实调用方共享稳定的纯结果模型。
- **不应做**：全局机械替换 token；用一个 Guard 吞掉所有异常；把 timeout 都标成
  `OutcomeUnknown`。
- **证据**：分类表、调用点静态检查、每类代表性自动测试和目标化人工验证。

### TD-802：DevelopmentPage 生命周期和并发刷新

- **建议优先级**：R2
- **历史观察**：自动刷新已有页面 cancellation，但手动刷新和采集对照曾使用独立
  token；取消与 timeout 的提示可能混淆。
- **未来工作**：统一同页操作的防重入和页面生命周期；区分导航取消、用户取消、
  timeout、Agent rejection 和协议失败；离页后不再更新控件。
- **证据**：纯状态转换测试，以及正常、断开、慢响应和离页人工案例。

### TD-803：Settings 工具检测与安装状态机

- **建议优先级**：R1
- **历史观察**：检测、路径配置、portable install、MSI prepare/install 存在多种
  无界等待或调用方取消路径。
- **未来工作**：分别定义检测、下载、准备、提权启动、安装、验证和回滚的提交点；
  安装 timeout 后不能仅因立即检测为“未安装”就允许重试，因为安装器可能仍在运行。
- **权威状态**：优先使用进程/安装事务终态、稳定注册信息和已验证文件身份；无法
  权威对账时保持 Unknown。
- **证据**：重复安装防护、下载取消、UAC 拒绝、安装器慢退出、部分安装和重启后
  检测案例。

### TD-804：Manage 导入导出的原子性和生命周期

- **建议优先级**：R1
- **历史观察**：调用链支持 cancellation，但页面调用曾未传入生命周期 token；导出
  直接创建目标文件，timeout 或取消可能留下部分 JSON/CSV。
- **未来工作**：先写同目录临时文件、完成序列化和验证后原子替换目标；取消或失败时
  保留原目标并安全处置临时产物。导入应先完整读取、验证和脱敏，再更新 workspace。
- **证据**：中途取消、磁盘写满、目标已存在、无权限、无效 JSON/CSV 和离页案例。

### TD-805：扫描结果持久化可观测性

- **建议优先级**：R2
- **历史观察**：本地扫描完成后，记录扫描结果的 IO/权限失败可能被静默忽略，用户
  只能看到当前内存结果，无法知道历史没有保存。
- **未来工作**：区分“采集失败”和“采集成功但持久化失败”；保留当前只读结果，
  发布非破坏性提示，并写入脱敏诊断。
- **证据**：只读数据库、磁盘满、目录权限变化和 Agent writer 不可用案例。

### TD-806：历史记录的 Empty、Unavailable 与 Stale 语义

- **建议优先级**：R2
- **历史观察**：空历史、读取失败、Agent 不可用和旧缓存可能在 UI 中显示为相似状态。
- **未来工作**：用明确状态区分真正为空、暂不可用、读取失败和陈旧缓存；不能用旧数据
  冒充实时数据，也不能把失败显示为零记录。
- **证据**：状态投影单元测试和数据库/Agent 故障人工案例。

### TD-807：MonitorPage 单一生命周期所有者

- **建议优先级**：R2
- **历史观察**：`Unloaded`、`OnNavigatedFrom` 和其他停止路径可能重复触发停止；轮询、
  实时会话和导出有不同生命周期。
- **未来工作**：建立幂等的页面会话所有者，明确开始、暂停、停止、离页和 App shutdown
  顺序；导出不应依赖正在销毁的页面。
- **证据**：重复停止、快速切页、窗口关闭、Agent 断开和长时间监控人工案例。

### TD-808：System Support 命令的权威对账

- **建议优先级**：R1
- **历史观察**：review/execute 有 audit 和 recovery 信息，但 App 未必拥有按计划或
  correlation 查询最终执行结果的统一端点。
- **未来工作**：在不开放自由命令的前提下，为每种 R3 typed action 定义操作身份、
  接收/执行/恢复终态和查询方式。若需要修改 IPC，必须由当时计划单独批准并评估兼容性。
- **证据**：ACK 丢失、Broker 启动失败、UAC 拒绝、操作成功但响应丢失、恢复失败和
  重启后审计恢复案例。

### TD-809：恢复和 rollback 诊断完整性

- **建议优先级**：R1
- **历史观察**：恢复通常正确地使用独立 `CancellationToken.None`，但宽 catch 可能
  把执行和恢复异常压缩成单一失败结果，丢失定位信息。
- **未来工作**：继续保证 rollback 不受页面取消影响；分别记录主操作、每个恢复步骤、
  最终恢复状态和待处理 receipt。失败 receipt 不得在未恢复时被误删或标记完成。
- **证据**：每个恢复步骤的故障注入、进程中止后恢复和敏感数据脱敏检查。

### TD-810：单实例重定向与窗口激活诊断

- **建议优先级**：R2
- **历史观察**：等待、重定向发送、前台激活和窗口句柄恢复的部分返回值或异常缺少
  可见诊断；后台 redirect task 需要保证异常被观察。
- **未来工作**：抽取可测试的协调逻辑和操作端口；记录阶段化、脱敏结果；区分已有
  实例未响应、发送失败、窗口不存在和 Windows 拒绝前台激活。
- **证据**：正常重定向、旧实例退出竞态、超时、无窗口、权限边界和 UAC handoff。

### TD-811：应用、Agent、Worker 与 Broker 的有界关闭

- **建议优先级**：R2
- **历史观察**：部分 shutdown、fire-and-forget 和事件停止路径可能只做最佳努力；
  异常是否被观察以及最终所有者需继续核对。
- **未来工作**：为每个进程建立明确 shutdown 顺序、最长等待、子进程处理、持久化
  flush 和诊断结果；不要用页面生命周期替代进程生命周期。
- **证据**：正常退出、托盘退出、窗口关闭、Worker 活动中退出、Broker 活动中退出和
  Agent 异常终止案例。

### TD-812：统一但有界的内部诊断通道

- **建议优先级**：R3；若阻塞现场诊断可提升为 R2
- **历史观察**：App crash log、monitor debug log、通知和 Agent audit 各自存在，缺少
  明确统一的所有权、保留和脱敏规则。
- **未来工作**：先定义事件模型和所有者，再决定文件、SQLite 或 Agent sink；规定
  大小上限、轮换、保留期、并发写入、portable/standard data root 和写入失败行为。
- **禁止记录**：自由命令、完整参数、未脱敏硬件身份、用户路径、密钥、pipe secret、
  原始 inventory 或可能包含敏感数据的完整异常文本。
- **证据**：红action测试、容量上限、日志轮换、路径切换、只读目录和诊断 sink 故障。

### TD-813：WinUI 行为的可测试逻辑抽取

- **建议优先级**：R3
- **历史观察**：现有测试项目主要覆盖非 WinUI 组件，页面按钮、导航和状态文字不能
  直接依赖普通单元测试验证。
- **未来工作**：只把复杂状态机、重试决策和生命周期协调抽到 Application 或专用
  可测试组件；XAML、Dispatcher、picker、UAC 和窗口激活仍使用原生人工验证。
- **不应做**：为了测试而把整个 App 引用进跨平台测试项目，或创建与产品结构重复的
  presenter 层。
- **证据**：抽取逻辑的确定性测试和对应薄页面的目标化人工案例。

## 5. V0.9 候选验证债务

V0.9 的主要任务是支持矩阵内测和修复测试发现，不应预先宣称以下项目通过。

### TD-901：支持平台矩阵

计划必须明确：

- Windows 版本、edition、build 和架构；
- Windows App SDK/.NET runtime 或自包含部署条件；
- 标准用户、管理员手动启动和 UAC handoff；
- 单屏、多屏、DPI、缩放、主题、高对比度和键盘操作；
- SATA、NVMe、USB、Storage Spaces、网络存储和缺失/离线设备覆盖；
- standard 与 portable data root；
- 外部工具已安装、未安装、错误版本、路径失效和执行失败。

每个格子必须记录 `passed`、`failed`、`unverified`、`not_required` 或
`deferred_by_user`，不能用自动测试替代原生或设备证据。

### TD-902：长时间与故障注入测试

候选场景包括：

- 长时间监控、测试运行、历史增长和日志轮换；
- Agent/Worker/Broker/App 分别崩溃或被终止；
- 管道断开、迟到响应、数据库锁定、磁盘满和权限变化；
- suspend/resume、用户注销、系统重启和设备热插拔；
- 外部工具无输出、输出损坏、非零退出和超时。

故障注入不得修改真实存储结构，不得访问未注册测试目录，不得绕过 typed adapter。

### TD-903：恢复与数据位置回归

覆盖：

- schema 打开和拒绝旧 schema；
- standard/portable 切换和失败回滚；
- recovery receipt 重启后处理；
- 导入、导出、历史和 evidence 的脱敏；
- 旧数据保留与目标验证；
- Agent SQLite 单写者边界。

### TD-904：V1.0 发布准备证据

V0.9 结束时才评估：

- 所有 release-blocking 缺陷是否关闭；
- 剩余技术债务是否有明确接受者、风险和延期理由；
- 自动门、原生门、设备门和长期测试是否达到当时批准的标准；
- 发布包布局、签名、许可、隐私、更新入口和回滚说明是否就绪。

即使 V0.9 验收通过，也不自动授权 tag、GitHub Release、二进制上传或部署。

## 6. 建议的未来分批方式

不要把本文整体复制到一个 Plan。较安全的批次示例：

1. **操作状态一致性**：TD-801、TD-803、TD-808，只选择实际仍存在的命令。
2. **页面生命周期**：TD-802、TD-807，并限制为最多两个页面。
3. **数据原子性与历史语义**：TD-804、TD-805、TD-806。
4. **恢复与进程关闭**：TD-809、TD-811。
5. **诊断与可测试性**：TD-810、TD-812、TD-813。
6. **平台内测**：TD-901 至 TD-904，按设备和系统矩阵逐批记录证据。

每批应有独立活动 Plan、停止条件、自动证据、人工证据和实际 changelog；不得因为
本文列出了某项，就把它视为默认范围。

## 7. 永久安全边界

无论未来是否处理这些债务，都必须遵守当时 Product、AGENTS 和活动 Plan。尤其：

- 不添加自由形式 storage mutation 命令；
- V0.5 以后真实 mutation 仍需要 typed operation、精确目标验证、preview、audit 和
  明确授权；
- elevation 或 Real mode 本身不是产品用户的 mutation 授权；
- 文件测试仅限明确注册目录中的 run-owned 文件；
- DiskSpd、fio、Dite、RoboCopy 和 RAMMap 保持外部安装和 typed adapter；
- inventory、日志、导入导出和 evidence 必须通过批准的脱敏边界。
