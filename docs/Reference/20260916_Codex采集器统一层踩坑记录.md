# Codex 采集器统一层踩坑记录：Astra 计划，Sol 执行

> 日期：2026-09-16
> 性质：Reference 文档，非当前产品规范或活动计划
> 主题：采集器对象集合、替换语义与统一层职责

## 事件经过

- Astra 制定计划，Sol 执行。实现过程没有报错，自动化测试全部通过，真实图形界面
  检查也能正常运行。
- 开发者人工检查时发现，某个分类按机器事实应只有 7 个对象，实际却采出了几十个。
  计划示例中原本只有少量正确对象，但 AI 没有把这个结果识别为验收不变量。
- AI 把几个采集器的结果合并到同一对象列表，没有复现参考旧代码已有的过滤。原本
  只应补充字段的来源，也获得了创建业务对象的权力。
- 开发者要求修正后，AI 增加了过滤；再次检查，仍然有几十个对象。
- 继续追查发现，AI 保留了“旧显示 + 新显示”的合并路径。开发者再次指出问题后，
  AI 仍在合并结果上继续增加筛选，没有先判断合并本身是否错误。
- 开发者最终明确要求采用替换方案：统一结果成为唯一显示来源，旧显示不再产生
  对象。至此，对象集合才恢复正确。
- 过程中 AI 还多次分叉数据路径。项目明明已有专门的统一层，筛选、合并和字段选择
  却被分散到采集上游、投影下游和界面中。

开发者为同一个语义问题进行了多轮人工复查和纠偏，心累无比。

## 根因

1. **正确示例没有变成硬验收。** 测试没有断言最终对象数量和身份集合必须精确。
2. **主来源与补充来源混淆。** 补字段被错误实现成了扩充对象集合。
3. **替换语义没有锁死。** AI 默认保留旧路径，采用看似保守、实则产生双重事实源
   的兼容合并。
4. **参考旧代码没有读透。** 只参考了接口和字段，没有复现旧代码的过滤边界及原因。
5. **验证只检查“无错误、能显示”。** 没有核对对象是否多了、少了或重复了。
6. **统一层没有成为架构门。** 上下游仍能各自改变最终对象集合。

## 今后的强制规则

- 每类业务对象只能有一个对象集合所有者，本项目中应由既定统一层负责。
- 主采集来源决定“有哪些对象”；其它来源只能按可靠身份补字段，不能新增同类对象。
- 上游保存原始事实，下游只消费统一结果。UI、报告、缓存和导出不得重新合并或过滤
  原始对象。
- 计划必须明确选择“替换”还是“合并”。决定替换后，验收必须证明旧路径不再产生
  最终对象，不能只证明新路径已经存在。
- 计划示例必须转成测试：给定固定原始来源，统一后的对象数量和身份集合必须精确；
  补充来源不得增加数量；旧显示对象不得进入最终结果。
- 原生检查必须同时记录原始来源、统一层和最终显示的对象数量及身份，不能只确认
  页面能打开、能滚动、不闪退。
- 第一次修正后外部结果没有变化，应停止叠加过滤，重新画完整数据流并追踪多余对象
  的入口。
- 同一问题两次修正仍未解决，应停止试错并报告理解冲突，不能在错误架构上继续堆
  逻辑。
- Astra 写计划时必须标明对象集合所有者、字段补充来源、旧路径去留和精确验收结果；
  Sol 执行前必须读完参考旧代码的过滤与关联逻辑，并独立复核这些语义。

## 教训

自动化测试全绿、程序不报错、真实 UI 能运行，都不能证明采集对象集合正确。对采集
功能而言，对象数量、身份和来源边界本身就是产品行为。

“人类心累”不是无关紧要的情绪，而是质量信号：AI 把本应由计划、架构约束和验收
承担的语义检查，反复转嫁给了开发者。
