# Codex 采集器统一层踩坑记录：Astra 计划，Sol 执行

> 日期：2026-09-16
> 性质：Reference 文档，非当前产品规范或活动计划
> 参与方式：Astra 负责计划，Sol 负责执行，开发者负责最终人工验收
> 主题：采集器对象集合、旧路径替换、统一层所有权与 AI 验收失效

## 0. 结论

这次问题表面上是“某个报告分类本应只有 7 个对象，却采出了几十个”，实际并非
一个过滤条件写错，而是整条数据链的对象集合所有权失守：AI 把多个采集器的结果
合并成同一对象列表，没有复现参考旧代码已有的过滤边界；被要求修正后，又持续
保留“旧显示 + 新显示”的兼容合并路径，只在合并结果上叠加筛选。直到开发者明确
要求新来源直接替换旧显示、旧路径不再产生对象，这个功能才真正修复。

全过程没有编译错误，自动化测试全部通过，真实图形界面检查也能正常显示。真正
暴露问题的是开发者对业务语义的人工核对：**对象能显示，不等于对象集合正确；
界面不崩溃，不等于采集边界正确。**

## 1. 事件经过

1. Astra 编制采集器实施计划，Sol 按计划执行。实现、构建、自动化测试和图形界面
   检查全程没有报告错误。
2. 开发者人工检查实际结果，发现某分类按机器事实应只有 7 个对象，界面却出现了
   几十个对象。计划中的示例结果本来只有少量正确对象，但 AI 没有把示例背后的
   “对象集合边界”识别为必须保持的不变量。
3. 追查后发现，AI 把几个采集器返回的对象直接合并，没有执行参考旧代码已有的
   过滤。多个来源原本应承担“主对象集合”和“字段补充”的不同职责，却被当成
   地位相同、可以相加的对象来源。
4. 开发者要求修正后，AI 补上了过滤逻辑。再次人工检查，结果仍然有几十个对象。
5. 继续检查发现，AI 采用的是“旧显示 + 新显示”的合并方案。新增过滤只约束了
   部分新数据，没有取消旧显示路径，因此错误对象仍能从另一条路径进入最终结果。
6. 开发者再次要求改正，AI 仍沿着合并方案继续增加筛选条件，而不是重新确认
   “合并是否应该存在”。代码变得更复杂，数据所有权仍然不清楚。
7. 开发者最终明确要求采用替换方案：新统一结果成为唯一显示来源，旧显示不再
   产生对象。修改后对象集合才与实际机器事实一致，功能修复结束。
8. 整个过程中，AI 还多次把路径分叉。项目明明已有专门的统一层负责对象集合、
   关联和字段选择，AI 仍让采集上游、投影下游和界面分别承担筛选、合并或字段
   修补，导致同一规则散落在多个阶段。

开发者最终感受：心累无比。这里的“心累”不是无关紧要的情绪，而是质量信号：
AI 连续把本应由架构、测试和执行自检承担的语义验证转嫁给了人类。

## 2. 为什么所有检查都没有报错

### 2.1 自动化测试验证了自洽，没有验证真实对象集合

测试能够证明代码按当前实现完成了合并、筛选和显示，却没有一个足够强的事实
断言证明“这台机器最终必须只有 7 个对象”。如果测试输入和预期输出都沿用错误的
合并模型，测试越完整，只会越稳定地证明错误实现内部自洽。

计划中的正确示例也没有转化成验收用例。示例只是文字时，AI 很容易把它理解为
展示样本；只有写成“给定这些原始来源，规范化后对象 ID 集合必须恰好等于这些值”
的断言，才能成为实现边界。

### 2.2 图形界面检查只确认了“能显示”

真实 UI 检查覆盖了页面可打开、列表可滚动、字段可见、程序不崩溃等行为，但没有
逐项核对对象数量、对象身份和来源归属。几十个对象同样可以被正常渲染，因此 UI
自动化没有技术错误可报。

采集功能的人工或自动验收不能只看页面是否工作，还必须回答：对象是否多了、少了、
重复了，是否来自允许成为主对象的来源，以及补充来源是否只补字段而没有新增对象。

### 2.3 AI 把“兼容”误当成默认安全策略

执行过程反复倾向保留旧显示，再叠加新显示和过滤。这种做法看似保守，实质上改变了
产品语义：旧路径继续拥有对象创建权，新统一层就不再是统一层。对于已经明确要替换
的路径，“两套都留着”不是兼容，而是双重事实源。

### 2.4 修补症状前没有重新画数据流

第一次过滤无效后，正确动作应是停止加条件，列出每个最终对象可能进入界面的全部
路径，确认唯一所有者，并检查旧路径是否仍在产出。实际执行却继续在既有合并逻辑上
补筛选，导致局部条件越来越多，根因越来越难看清。

## 3. 根因

1. **计划没有把示例提升为硬不变量。** “示例里只有几个正确对象”没有被写成
   对象数量、身份集合和来源边界的明确验收条件。
2. **没有区分主对象来源与字段补充来源。** 多个采集器被误认为都能创建业务对象，
   而不是一个决定对象集合、其它来源按可靠身份补充字段。
3. **替换语义没有锁死。** 计划和执行都没有明确写出“旧显示路径必须退出，禁止
   新旧对象集合并存”，给兼容合并留下了空间。
4. **没有完整复现参考旧代码的行为。** 旧代码已经包含过滤，但 AI 只吸收了接口或
   字段层面的参考，没有先总结旧代码究竟排除了哪些对象、为什么排除。
5. **统一层职责没有成为架构门。** 虽然人类已设计专门统一层，筛选、合并和字段
   选择仍然泄漏到上下游，形成多处可改变最终语义的分叉路径。
6. **验证缺少独立事实源。** 实现代码、测试预期和 UI 投影共享同一错误假设，只有
   人工知道实际机器上应为 7 个对象，因此最终仍靠人类发现。

## 4. 今后的强制规则

### 4.1 对象集合只能有一个所有者

- 每个业务对象分类必须明确一个规范对象集合的所有者；本项目中应由既定统一层负责。
- 主采集来源决定“有哪些对象”。补充来源只能按可靠身份为既有对象补字段，不能因
  为自己也返回设备记录就创建第二组业务对象。
- 上游保留原始来源事实，下游消费统一结果。界面、报告投影、缓存和导出不得重新
  合并原始对象，也不得各自发明过滤条件。
- 无法可靠关联的补充记录保留为来源证据或未知状态，不能靠名称、顺序或相似字段
  猜测后并入业务对象。

### 4.2 “替换”必须真的移除旧产出

- 计划必须明确选择 `replace` 还是 `merge`，不能让执行者自行采用“先都保留”的
  折中方案。
- 一旦决定替换，旧路径可以保留必要的原始事实采集，但不得继续向最终对象列表、
  UI、导出或缓存投影业务对象。
- 验收不仅检查新路径存在，还要反向证明旧路径不再产生结果。
- 第一次修复后数量仍异常时，禁止继续堆叠筛选；必须重新审计完整数据流和所有入口。

### 4.3 示例必须变成可执行验收

以后类似采集器至少覆盖以下断言：

1. 给定多来源且含重复、无关和补充记录的固定样本，统一结果的对象数量必须精确。
2. 统一结果的对象身份集合必须精确匹配预期，不能只断言“包含某几个对象”。
3. 补充来源可以改变允许补充的字段，但不能增加对象数量。
4. 旧显示来源即使仍有原始记录，也不能出现在最终对象集合。
5. 同一真实设备被多个来源观察时只形成一个对象；无法可靠关联时不得猜测合并。
6. 原生检查必须记录原始来源计数、统一后计数和最终显示计数，并核对三者差异有明确
   原因。不能只截图证明页面能打开。

“预期 7 个，实际几十个”这种差异应成为自动门中的直接失败，而不是留给开发者凭
肉眼发现。

### 4.4 计划与执行的交接要求

Astra 编制计划时必须写清：

- 哪个来源决定对象集合；
- 哪些来源只补字段；
- 过滤发生在哪一层，为什么只能发生在那里；
- 旧路径是保留原始证据、完全退出，还是确有依据地参与合并；
- 预期对象 ID 集合、数量和至少一个反例样本；
- 禁止下游再次筛选、合并或创建同类对象的围栏。

Sol 执行前必须完整读取参考旧代码中与对象集合相关的过滤和关联逻辑，并用自己的
话写出“旧实现保留什么、排除什么、原因是什么”。执行完成后，要沿一条真实样本
逐层列出原始对象、统一对象和显示对象，证明没有额外路径。不能以“计划已由另一
模型编制”为理由跳过语义复核。

## 5. 出现人工反例后的正确动作

当人工指出对象数量明显错误时，执行者应立即：

1. 暂停继续补过滤条件，不先猜一个局部修复。
2. 输出完整数据流：每个采集器、原始记录、统一层、持久化、投影和 UI。
3. 标出每一层是否拥有创建、删除、合并或补字段的权力。
4. 用实际对象身份逐项追踪多出来的记录从哪条路径进入。
5. 与开发者确认本次语义是替换还是合并；收到“替换”后删除最终结果中的旧产出。
6. 增加能复现这次几十个对象反例的测试，再进行真实 UI 数量与身份核对。

如果同一问题经两次修正仍未改变外部结果，应停止继续试错并报告理解冲突。第三次
在错误架构上叠加逻辑，通常只会增加人类后续清理成本。

## 6. 最终教训

- 正确的对象数量和身份集合是产品语义，不是 UI 细节。
- 多来源采集不等于多来源都能创建对象；“补字段”和“扩集合”必须严格分开。
- 已有统一层时，任何上下游筛选、合并和字段裁决都应被视为架构警报。
- 替换方案最重要的验收不是“新的出来了”，而是“旧的确实没有了”。
- 自动测试全绿和真实 UI 可运行，都不能替代对真实对象集合的独立核对。
- AI 连续依赖人类指出同一语义错误，说明验收设计失败，而不只是实现偶然出错。

这次功能最终修好，但代价是开发者多轮人工复查、反复解释同一架构意图，并亲自把
方案从“继续合并”拉回“统一替换”。以后必须让计划、架构断言和验收数据共同承担
这部分工作，不能再把最后一道也是唯一一道语义检查留给已经心累的人类。
