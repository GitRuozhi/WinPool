# AI Agent Harness 项目管理架构参考

> 提炼来源：`D:\Coding\VisualStandards` 与 `D:\Coding\Lolite` 的 README、AGENTS、Product、Development、Quality、Plan、CHANGELOG 与 Archive。
> 整理日期：2026-08-10。
> 用途：作为后续新项目的管理架构、Agent 启动协议、阶段推进和验收设计参考；不是两个现有项目或 WinPool 当前需求的替代规范。WinPool 仅按其技术栈和 V0.3 计划选择性借鉴。

## 1. 核心结论

这两个项目形成了一套适合单人开发、AI Agent 深度参与的轻量管控模型：

1. **稳定约束、当前计划、历史结果分离**：长期规则不跟着每个阶段反复改，当前范围只有一个入口，完成后冻结归档。
2. **所有扩展先过边界，再谈实现**：Agent 只完成当前阶段的最小闭环，不因“以后可能需要”提前建设框架、数据库、API、任务系统或部署设施。
3. **测试证据与设计判断分离**：代码门负责确定性事实，视觉门负责设计意图；截图相同不等于视觉正确，Agent 也不能代替用户批准视觉基线。
4. **关键状态迁移由用户授权**：进入下一阶段、提升正式版本、更新视觉基线、推送远端、部署或触碰保护目录，都需要明确授权。
5. **Git、文档和归档共同构成可追溯基线**：提交按职责拆分，发布结果写入 CHANGELOG，阶段计划进入 Archive，标签不可移动。

可以将整体架构概括为：

```text
稳定约束（AGENTS / Product / Development / Quality）
                         ↓
              唯一当前计划（Plan）
                         ↓
       实施 → 代码门 → 视觉/人工门 → 用户确认
                         ↓
       CHANGELOG + 版本标记 + Git 标签 + Archive
```

## 2. 两个项目的共性与差异

| 维度 | VisualStandards | Lolite | 对新项目的启示 |
|---|---|---|---|
| 项目类型 | 独立视觉规范 | 本地媒体产品 | 管控骨架可共用，产品边界必须项目化 |
| 主推进单位 | `Vxx` 正式版本 | `Stage X.X` + `vX.Y.Z` | 阶段与版本可以相同，也可以分开建模 |
| 当前计划 | 进入版本时建立，完成后归档 | 始终以当前 Stage 的 Plan 为唯一依据 | Harness 只能识别一个活动计划 |
| 主分支 | `main` | `master` | 不应在通用 Prompt 中写死分支名 |
| 协作模式 | 单人、直接主分支、无 PR | 单人、直接主分支、无 PR | 分支策略属于项目配置，不属于全局默认 |
| 正式结果 | 页面/文件头、README、路线图、CHANGELOG、标签 | package 版本、README、version.js、CHANGELOG、阶段归档 | 发布清单必须按项目定义 |
| 质量门 | 静态、单元、离线、浏览器、视觉 | 静态、单元、构建、浏览器、视觉、真实媒体/Edge | 共享术语，不共享测试实现 |
| 高风险边界 | V70 基线只读、页面离线独立 | 数据库分离、无上传、保护生产目录和媒体目录 | 高风险边界应直接写入 AGENTS |
| 跨项目关系 | 互相参考、不互相依赖 | 互相参考、不互相依赖 | 共享实践走人工提炼，不做运行时耦合 |

## 3. 推荐文档信息架构

每份文档只承担一种职责，避免同一事实被多个文件同时维护。

| 文件 | 读者 | 保存内容 | 不应保存 |
|---|---|---|---|
| `README.md` | 使用者、新成员 | 产品是什么、怎么运行、当前正式版本、文档导航、已知限制 | 长篇开发规范、讨论过程、详细阶段任务 |
| `AGENTS.md` | AI Agent | 环境硬约束、保护路径、授权边界、必读文件、Git 规则、禁止动作 | 临时进度、测试次数、某次方案讨论 |
| `docs/Product.md` | 产品负责人、Agent | 长期定位、非目标、产品边界、大阶段路线图 | 当前任务拆解、具体实现步骤 |
| `docs/Development.md` | 开发者、Agent | 架构、模块职责、依赖方向、环境、提交和版本流程、文档规则 | 某阶段的待办列表、测试结果快照 |
| `docs/Quality.md` | 开发者、验收者、Agent | 代码门、视觉门、测试分类、基线、例外、验收报告格式 | 当前版本状态和临时缺陷列表 |
| `docs/Plan.md` | 当前执行者 | 唯一活动阶段的目标、范围、非目标、决策、任务、完成标准、状态 | 跨版本长期规则、未确认方案、未来阶段细节 |
| `docs/CHANGELOG.md` | 使用者、维护者 | 已经发生并正式确认的版本结果、兼容性和已知限制 | 未来计划、尚未确认的工作 |
| `docs/Archive/` | 审计、回溯 | 完成阶段的冻结计划、验收、迁移矩阵、已知差异和索引 | 当前活动任务、继续修改的活文档 |

约束：

- 同一核心职责只能有一个事实源。
- 当前只允许一个 `docs/Plan.md`；额外规划文档只有用户明确要求时才创建。
- 方案确认前留在对话或临时区，不进入长期文档。
- 归档原则上只读，只允许修复失效链接和明显事实错误。
- 没有活动阶段时，可以不保留 Plan；Harness 必须按“存在则读取”处理，不能因 Plan 缺失反复失败。

## 4. 事实来源与冲突优先级

建议新项目采用以下通用优先级：

1. 用户在当前任务中的明确决定。
2. `AGENTS.md` 中的安全、权限和不可变边界。
3. `docs/Product.md` 中的产品边界与非目标。
4. 已确认的当前 `docs/Plan.md`。
5. 正式规格、接口契约和项目自身的已确认设计规则。
6. `docs/Development.md` 与 `docs/Quality.md` 的长期执行规则。
7. 当前实现与自动化测试证据。
8. 用户批准的视觉基线。
9. CHANGELOG 与 Archive 中的历史记录。

冲突处理原则：

- 当前明确决定可以改变计划，但不能静默突破高风险边界。
- Plan 描述当前意图，不自动改写长期产品方向。
- CHANGELOG 记录结果，不是需求或规格的替代品。
- 历史基线可以证明“过去是什么”，不能单独证明“现在应该是什么”。
- 外部规范只能作为参考；目标项目自己的已确认规则优先。

## 5. 阶段与版本状态机

| 状态 | 允许内容 | 进入条件 | 退出条件 |
|---|---|---|---|
| 未进入 | Product 中只写高层目标 | 无 | 用户确认阶段目标和边界 |
| 提案中 | 对话中的方案、选项和风险 | 用户提出方向 | 用户明确选择方案 |
| 已确认 | 建立或替换唯一 Plan | 目标、范围、非目标已确认 | 开始实施 |
| 进行中 | 只实现 Plan 的最小闭环 | 工作区和依赖检查完成 | 完成自动检查 |
| 待验收 | 代码门证据齐全，视觉/设备项明确 | 自动检查通过 | 用户验收或批准例外 |
| 已完成 | 更新正式状态、版本和 CHANGELOG | 用户确认完成 | 归档 Plan、创建标签 |
| 已归档 | 历史只读 | 发布动作完成 | 原则上不再迁移状态 |

推荐流转：

```text
未进入 → 对话提案 → 用户确认 → Plan → 实施 → 代码门
       → 视觉/设备/人工验收 → 用户确认 → 发布 → Archive
```

禁止事项：

- 未经确认直接进入下一阶段。
- 以“搭基础”为理由实施未来阶段内容。
- 自动检查通过后由 Agent 自行宣布产品或视觉验收完成。
- 为了赶版本而删除完成标准、弱化测试或覆盖未解决问题。

## 6. Agent 授权矩阵

| 动作 | 默认权限 | 要求 |
|---|---|---|
| 阅读、搜索、状态检查 | 允许 | 只读，遵守保护路径 |
| 诊断和报告 | 允许 | 不顺带实施修复 |
| 当前范围内本地修改 | 用户要求修改后允许 | 保留用户已有和无关改动 |
| 本地测试 | 允许 | 使用项目规定环境与命令 |
| 本地提交 | 按项目 AGENTS | 提交按职责拆分 |
| 推送远端 | 需明确授权 | 推送前 fetch 并检查远端祖先关系 |
| 进入下一阶段/提升正式版本 | 需明确授权 | 同步 Plan、路线图、CHANGELOG 和版本标记 |
| 更新正式视觉基线 | 需明确授权 | 必须来自完整审查包和用户批准记录 |
| 部署、服务、端口、防火墙 | 需明确授权 | 先确认目标环境与回退方式 |
| 删除、覆盖、移动保护数据 | 默认禁止 | 必须得到针对具体目标的授权 |

Harness 不应把“请检查”“请介绍”“请诊断”解释成写文件、提交、推送或部署授权。

## 7. Agent 每轮执行协议

### 7.1 启动检查

1. 确认仓库根目录、操作系统、Shell 和工具版本。
2. 从当前目录向上查找并完整读取 `AGENTS.md`。
3. 读取 README、Product、Development、Quality；`docs/Plan.md` 存在时读取，不存在时记录“当前无活动计划”。
4. 检查分支、工作区、远端和未提交改动；不得假设干净工作区。
5. 识别保护目录、外部仓库、真实数据和部署目标。
6. 将请求分类为：查询、诊断、修改、发布、高风险操作。

### 7.2 范围收敛

- 写出本轮目标、允许修改范围、明确非目标和验证命令。
- 新需求超出当前 Plan 时，停止扩展并请求用户确认。
- 可独立验证的修复形成最小闭环，不夹带未来架构。
- 不将临时判断立即写入 Product、Development 或 Quality。

### 7.3 实施纪律

- 优先补丁式修改，避免覆盖整文件。
- 保留工作区已有内容；重叠改动无法安全合并时停止并说明。
- 模块只有一个所有者；共享能力通过公共接口，不穿透内部文件。
- 路径移动、等价重构、新功能、视觉变化、测试和文档分别处理。
- 每次变更都能说明：改了什么、为什么属于当前范围、如何验证。

### 7.4 验证与交付

1. 先运行最小相关测试，再运行项目规定代码门。
2. 记录通过、失败、未运行和不可用条件。
3. 视觉变化只在授权后运行视觉流程；正式基线不自动重建。
4. 交付时列出结果、证据、未验证项、已知问题和需要用户决定的下一步。
5. 发布前再次检查远端状态、工作区、版本号、文档一致性和标签目标。

## 8. 推荐的 Plan 模板

建议在 Plan 顶部增加机器易读的状态块，避免 Agent 从自然语言猜测当前版本和阶段：

```yaml
---
project: ExampleProject
phase: Stage 1.2
status: confirmed       # proposed | confirmed | in_progress | awaiting_acceptance | complete
formal_version: v1.1.0
target_version: v1.2.0
branch: main
confirmed_by_user: 2026-08-10
code_gate: pending      # pending | passed | failed
visual_gate: not_required  # pending | passed | failed | not_required | unverified
---
```

正文保持以下结构：

```markdown
# 当前阶段计划

## 1. 背景与进入依据
- 谁在何时确认进入
- 当前正式版本和代码基线

## 2. 当前目标
- 3～7 项可验收结果

## 3. 实现范围
- 功能、模块、数据和页面范围

## 4. 非目标与阶段边界
- 明确不做什么
- 不进入哪些未来阶段

## 5. 已确认决策
- 只记录用户已确认选择

## 6. 实施顺序
- 每一步说明产物、验证和回退点

## 7. 完成标准
- 可观察、可测试、可人工确认

## 8. 验证矩阵
- 命令、环境、预期、当前结果、未验证项

## 9. 当前状态
- 已完成、进行中、待确认、阻塞项

## 10. 发布与归档
- 版本文件、CHANGELOG、标签、归档文件名
```

Plan 中避免使用“完善一下”“应该没问题”“后续优化”等无法验收的描述。

## 9. 质量门架构

### 9.1 代码门

代码门只验证可重复、可确定的事实：

- 静态规范和结构检查。
- 单元测试与纯逻辑测试。
- 构建或离线加载。
- Chromium 浏览器功能测试。
- 条件可用的 Firefox、真实 Edge、真实设备和真实媒体结果。
- 资源释放、生命周期、错误状态、可访问性和响应式几何。
- 已批准例外与明确的未验证项。

### 9.2 视觉门

视觉门由以下证据共同构成：

- 固定环境截图回归。
- Agent 视觉审查。
- 用户确认记录。
- 有意差异清单。
- 未解决问题及严重程度。

视觉审查输出建议统一记录：位置、预期意图、实际表现、证据、严重程度、置信度、是否阻塞、建议、用户决定。

### 9.3 严重程度

| 等级 | 含义 | 默认是否阻塞 |
|---|---|---|
| Blocker | 页面不可用、数据风险、关键功能失效 | 是 |
| Major | 明显布局、状态、流程或兼容性错误 | 是 |
| Minor | 局部偏差 | 否 |
| Advisory | 改进建议，不代表违规 | 否 |
| Undetermined | 事实来源不足 | 交给用户判断 |

### 9.4 未验证与例外

- “没有运行”不能写成“通过”。
- 环境不可用时记录 `unverified`，并说明环境、影响和是否阻塞。
- 例外必须包含：原因、范围、批准者、批准日期、风险、失效条件。
- 测试数量只作当次证据，长期文档优先记录命令和基线提交，避免数字快速过时。

## 10. Git、提交与发布规则

### 10.1 提交

推荐职责前缀：

- `docs:` 文档结构或内容。
- `refactor:` 等价重构。
- `feature:` 产品能力。
- `visual:` 有意视觉变化。
- `tests:` 测试与质量工具。
- `release:` 版本、归档和发布元数据。

避免只写 `fix`、`update`、`final` 等无法说明职责的提交信息。一个提交应能独立解释和回退。

### 10.2 推送

```text
用户明确授权推送
  → fetch 远端目标分支
  → 确认远端是本地 HEAD 的祖先
  → 检查工作区和待推送提交
  → 推送分支
  → 推送不可移动标签
  → 再次核对远端分支和标签指向
```

主分支名、是否允许 PR、是否允许本地自动提交，都必须从项目 AGENTS 读取，不能由 Harness 写死。

### 10.3 发布清单

- 当前阶段完成标准全部有证据。
- 用户确认发布或阶段完成。
- 正式版本、页面、package、运行时版本展示一致。
- README、Product 路线图、CHANGELOG 一致。
- 当前 Plan 已更新状态并移入 Archive。
- Archive 索引已更新。
- 正式标签指向正确提交，且不再移动。
- 代码门、视觉门、例外和未验证项写入交付结果。

## 11. 文档生命周期规则

### 应写入长期文档

- 已确认且跨阶段有效的产品边界。
- 稳定架构和模块所有权。
- 固定环境、安全和授权规则。
- 可重复执行的质量与验收流程。
- 已正式发生的版本结果。

### 不应写入长期文档

- 对话中的候选方案。
- 未确认的技术选型。
- 临时调试步骤和中间推理。
- “可能以后需要”的模型、接口、目录和基础设施。
- 尚未正式发布的结果性表述。

### 归档原则

- 归档保留当时真实状态，不补造不存在的验收记录。
- 阶段完成时可追加“完成结果”，但不应把历史计划改写成从一开始就完全正确。
- Archive 必须有总索引，记录阶段、状态、日期、版本/标签和文件。

## 12. 跨项目治理

VisualStandards 与 Lolite 的关系可抽象为一套“人工晋升”模型：

```text
源项目中的稳定实践
  → 列出候选变化
  → 去业务化/通用化
  → 用户确认是否值得共享
  → 在目标仓库独立实现
  → 运行目标仓库自己的质量门
  → 目标仓库独立发布
```

规则：

- 每个仓库独立版本、独立标签、独立测试、独立视觉基线。
- 不通过相对路径、子模块、共享文件复制或运行时导入形成隐式依赖。
- 修改哪个仓库，就在那个仓库按其 AGENTS 提交。
- 跨项目一致性由人工检阅，不自动同步。
- 外部项目版本号只在确有兼容意义时固定；否则使用“适用的已确认规则”，避免硬编码版本长期陈旧。

## 13. 安全边界的推荐写法

AGENTS 中应维护明确的保护表：

| 对象 | 权限 | 允许动作 | 需用户批准的动作 |
|---|---|---|---|
| 正式基线 | 只读 | 比较、校验 | 覆盖、更新、移动 |
| 用户真实数据/媒体 | 只读 | 读取测试 | 删除、重命名、修改 |
| 生产部署目录 | 禁止默认写入 | 状态检查 | 部署、覆盖、回滚 |
| 外部参考仓库 | 独立管理 | 只读参考 | 修改后在其自身仓库提交 |
| 数据库 | 按职责隔离 | 本阶段允许的迁移 | 合并物理库、破坏性迁移 |
| 服务和网络 | 默认不操作 | 本地开发启动 | 服务安装、自启、防火墙、公开访问 |

每条边界都应说明“为什么存在、何时失效、谁能批准”，减少 Agent 把偶然约束误当永久规则。

## 14. 从现有项目暴露出的 Harness 改进点

1. **Plan 缺失兼容**：VisualStandards 发布后会归档并删除当前 Plan，但 AGENTS 仍要求启动时读取 Plan。Harness 应采用 `if exists`，并明确输出“无活动计划”。
2. **阶段与版本分离**：Lolite 使用 Stage 与语义版本，VisualStandards 使用 Vxx；Harness 应分别保存 `phase`、`formal_version`、`target_version`，不能只维护一个版本字段。
3. **跳号/合并策略**：VisualStandards 的 V73 内容并入 V74。新项目应规定：跳号、取消、合并版本如何在 Product、CHANGELOG、Archive 和标签中登记。
4. **跨仓版本漂移**：Lolite 文档中的 VisualStandards 版本可能落后于实际正式版本。跨仓引用应标记“参考时间/兼容范围”，或避免无必要的精确版本绑定。
5. **CHANGELOG 的未发布记录**：现有记录会同时出现“阶段期间未提升版本”和后续正式发布。推荐顶部使用 `Unreleased` 区，发布时整体转入正式版本，减少状态矛盾。
6. **验收与发布解耦**：代码发布、视觉验收、视觉基线批准不是同一件事。状态模型应分别记录代码门、视觉门、用户发布确认和基线版本。
7. **测试数字易过时**：长期文档不应依赖“当前有 54 项”作为规则；更稳妥的是记录命令、日期、提交和结果文件，数字仅进入 CHANGELOG 或当次验收报告。
8. **分支名不可推断**：两个项目分别使用 `main` 与 `master`。Harness 必须读取项目配置或 Git 当前状态。
9. **大计划膨胀**：归档计划可以保留完整过程，但活动 Plan 应优先保存当前闭环；历史调查和长篇技术分析可在完成时压缩为结果与证据索引。

## 16. 推荐的 AGENTS 最小结构

```markdown
# 项目 Agent 工作约定

## 执行环境
- 操作系统、Shell、必需工具、禁止工具

## 开始工作前
- 必读文件；Plan 不存在时的处理
- Git 状态和保护路径检查

## 产品与数据边界
- 不可变非目标
- 数据、网络、部署和外部仓库边界

## 工作流程
- 当前 Plan 的最小闭环
- 何时必须询问用户
- 修改、测试、视觉和人工验收规则

## Git
- 主分支、PR 策略、本地提交权限、推送授权

- 破坏性操作和用户数据规则
```

AGENTS 只保存长期且高约束的规则。版本状态、测试次数和某个阶段的任务不要放入其中。

## 18. 新项目落地顺序

1. 先写 Product：明确产品是什么、非目标和阶段路线图。
2. 写 AGENTS：环境、授权、安全、保护路径和 Git 策略。
3. 写 Development：架构、模块职责、依赖方向、开发和发布流程。
4. 写 Quality：代码门、视觉门、例外和验收格式。
5. 经用户确认后建立第一个 Plan，只做最小可运行闭环。
6. 建立测试目录和根命令入口，让 Agent 不需要猜命令。
7. 完成阶段后更新 CHANGELOG、归档 Plan、建立不可移动标签。
8. 每隔若干阶段审查一次文档重复、陈旧跨仓引用和失效路径，但不要重写历史归档。
