# WinPool 开发踩坑记录

更新：2026-10-12。扩展[近期真实编辑回归](#近期真实编辑回归2026-10-09至12)，补记真实投影、重置推荐、格式化参数和拖放输入的回归教训；保留 2026-09-16 合并的布局重构、采集器和重复缺陷记录。这是历史经验，不是新的产品规范或待执行计划；当前行为、进度和验证结论分别以 [Product](../Product.md)、[Plan](../Plan.md) 和 [Quality](../Quality.md) 为准。

## 共同问题

- **理解错了，计划和测试仍能全绿。** 没读懂设计理由、参考实现和正确结果，后续实现与测试便可能互相证明同一个错误。
- **只修局部，没有追完整链路。** 统一层之外又出现筛选、合并和字段处理；旧缓存、其他入口和延迟事件继续产生错误结果。
- **反例出现后仍沿原方向打补丁。** 没有重新核对根因，甚至用较容易实现的行为替换需求，把发现错误和纠偏成本留给用户。
- **验证结论超出证据。** 编译成功、自动测试通过、界面能打开，分别不等于业务结果正确、原生交互可靠或重启后状态正确。

## 近期真实编辑回归（2026-10-09至12）

本节保留截至 `8e9b2ab` 的既有修复记录，并补充 2026-10-12 用户现场指出的问题；各项验证边界按下文证据分别说明。用户要求真实操作遵循已经设计并实现的模拟操作流程，但连续几轮修改仍由用户发现遗漏；后来“不能建池、不能改分区、频繁锁住操作”的现场又暴露了 MAX 恢复和界面解锁的缺口。不能把这些问题统称为 Windows 限制，也不能把一轮局部修复表述为真实与模拟已经全面统一。

### 1. 把后台执行机制变成了新的产品流程

**表现：** 真实模式增加准备／执行计划、额外参数和布局选择、按操作 ID 查询／停止等入口。第一轮只是将“按 ID 查询／停止”改名为“查看操作结果／停止后续步骤”，还把这些实现写入 Product，用户再次指出原设计没有这些东西。结构页另有“删除未使用 HDD 层”按钮；只修改池属性和文案，没有恢复完整建池操作。

**原因：** 从后台需要冻结、查询和恢复，推导出用户也需要操作这些技术步骤；再把已写代码当成需求依据。模拟操作被当成可参考的外观，没有被当成用户已指定的操作基准。改名不等于移除多余流程，回写设计也不能补成授权。

**修复与经验：** `aa51fe5` 移除两页额外查询／停止入口及专用代码；后续建池回到空草稿池、拖入成员、对应属性、保存／撤销／重做／放弃和原 Apply。结构 Apply 一次确认完整目标，后台按已确认范围执行。后台 Prepare、类型化计划、实时身份核验和只读恢复仍有作用，但不据此增加产品按钮。真实与模拟应共用用户语义和草稿规则；真实串行调用与模拟提交方式的必要差异，不等于要再设计一套界面。

依据：[变更记录](../CHANGELOG.md)、[Plan §10.5–10.7](../Plan.md)、[额外入口移除的限定验证](../Quality.md#2026-10-10-编辑页额外入口移除限定验证)。

### 2. 漏掉拖放建层，修复按钮后拖动仍然失效

**表现：** 新建池／编辑池的拖动反馈缺失，拖入磁盘没有按 HDD／SSD／SCM 生成对应草稿层。恢复建层后，真实 Apply 完成仍可能无法再次拖动。

**原因：** 验收只围绕字段和按钮，没有从空池开始走完整操作。AutoVD 关闭还曾错误阻止 HDD 模板生成，混淆“有层”和“自动建 VD”。另一处是 Apply 中刷新拓扑时 `_applyingRealDraft` 仍为 true，交互以禁止拖动状态重建；finally 只恢复按钮，未重建拓扑交互。

**修复与经验：** `15febce` 恢复按成员介质创建／填充草稿层，AutoVD 只控制 VD，AutoPart 独立控制分区。预览随指针移动，高亮和释放都经过 `CanDropDisk`，无效释放不改草稿。finally 清除执行标记后调用 `RefreshExecutionMode()`，恢复后续拖动。交互检查要包含操作前、操作中和操作后；按钮重新可用不能证明拖放也已恢复。

本轮真实单 HDD 的 64 GiB 创建、AutoPart 及 Apply 后拖动有原生证据；模拟 SSD 仅检查草稿并放弃，SCM 未原生检查，不能称全介质验证完成。见 [Quality 的按介质建层验收](../Quality.md#2026-10-11-按介质自动建层与原-apply限定范围验收)。

### 3. 共用模型仍然可能保留两套保存、资格和默认值规则

**表现：** 新建池另走保存入口，保存意图及撤销／重做与已有池不一致；模拟满足条件的层仍不能改列数；AutoPart 关闭仍生成分区、MSR 偏好未被执行。分区起止值格式、真实格式化属性和重置后的按钮资格也不一致。

**原因：** 模型相同，但 UI 资格、保存、意图绑定和执行末态各自判断。只检查属性是否显示或能赋值，没有追踪到草稿保存、撤销／重做、提交和最终对象。字段的显示格式与输入校验也被混在不同入口中处理。

**修复与经验：** `545de24` 修正模拟 Simple／Mirror／Parity 层列数按有效数据成员判断及参数进入草稿，起止值统一为数字在前、单位在后的准确 MiB 与自适应单位显示；`eeafc32` 让新池共用 `poolSave` 链，按 AutoPart／MSR 偏好生成末态，并修正真实文件系统、簇大小、快速格式化和重置状态。后续核对同一字段应沿“显示／资格 → 保存 → Undo／Redo → Apply → 最终事实”追踪，不能只数有多少公共类或删了几个旧方法。

验证也有区别：10 月 10 日的起止值／绑定检查主要是源码和编译；10 月 11 日的真实格式化表单未提交，模拟自动分区已实际 Apply。它们不能替代真实格式化或所有字段条件的原生验收。见 [Plan §10.5、§10.8](../Plan.md) 和 [Quality 的编辑流程审计记录](../Quality.md#2026-10-11-编辑流程审计残留修复限定验收完成)。

### 4. 混淆微软原生 MAX、明确容量试验和用户指定算法

**表现：** 先用明确 `StorageTierSizes` 的失败解释原生 MAX，又把接口失败转成让用户重新选择产品布局或接受拒绝门。诊断中的固定扣减成功值，也容易被误讲成已部署的最大容量算法。

**已确认的区别：** 本机准确 `StorageTiers + UseMaximumSize` 组合被接口拒绝；`MediaType HDD + UseMaximumSize` 返回没有实际 HDD 层的普通 VD，不能算分层 MAX 成功。**本机分层原生 MAX 失效归因于微软 Windows Storage 接口／提供程序，不是 WinPool 的容量算法问题。单 HDD 可以建立真实 HDD 容量层。** 该归因限定本机已测路径，不表示微软已公开确认缺陷或所有 Windows 版本相同。WinPool 自身把池范围强加给层、混用容量步长和采集超时，是另外的问题。

**修复与经验：** `83b9cc0` 实施用户随后明确指定的 `WINPOOL-MAX-GIB-1`：准确上界减十进制 4,000,000 bytes，取严格更小整数 GiB；模拟直接采用，真实以 1 GiB 步长找到已证明的容量边界，普通 MAX 也共用。多层同一 VD 先各取 0.5×C，再逐层搜索，最终整数 GiB。准确公式、边界和执行约束只以 [Plan §10.4](../Plan.md#104-用户指定的内置整数-gib-max-算法已验证) 为准；不能恢复旧 4 GiB 对齐、固定扣 2 GiB，或把显式容量成功说成 MAX 已验证。

普通／单 HDD 路径已有实机搜索证据，多层没有本机实测。接口结论和旧实验值的来源见[单 HDD 容量调查](../Review/Single-Hdd-Tier-Capacity-20261009.md)；已确认决定无需后续 Agent 反复询问。

### 5. 实时指纹修好了，持久化恢复仍用旧算法

**表现：** 用户默认 MAX 在 3725 GiB 被拒绝，降低到 3724 GiB 后已经创建成功并核验边界，随后却报 `real.maximum.recovery_origin_invalid`，操作变成未知，建池和分区修改一起被锁住。

**原因：** 实时核验已对物理盘 `AllocatedSize` 的易变 provider 计数做规范化，MAX 恢复却另行复算原始值。相同事实走两套指纹规则，成功结果被误判。此前还遇到 ObjectId 引号和 Returned-null 的持久化表示差异，说明内存核验通过不代表落库再加载仍能复算。

**修复与经验：** `8e9b2ab` 使实时和恢复共用 `WindowsRealStorageTopology.CanonicalComponent`，历史收据只兼容已知表示，并要求完整冻结哈希匹配；身份、关系、几何、安全状态及池／层／VD 容量继续严格核验。原现场操作通过生产只读恢复为成功，Accepted／CallIssued 和步骤表哈希未变，没有重放或清库。

指纹规则变动要一起检查实时准备、后态比较、持久化往返、旧收据恢复和篡改拒绝；只把当前入口抽成公共函数仍可能漏掉恢复入口。该误锁是 WinPool 缺陷，与上一节微软原生 MAX 问题分开。证据见 [Plan §10.9](../Plan.md#109-真实-max-核对误锁与编辑恢复修复2026-10-11) 和 [Quality](../Quality.md#2026-10-11-真实-max-核对误锁与编辑恢复限定验收)。

### 6. 后台已有终态，界面仍保留未知屏障

**表现：** 用户已开启真实编辑，操作仍不可用，提示却要求开启真实编辑；只读恢复结束后也不一定解锁。

**原因：** 恢复列表先返回旧 Unknown 并调度后台核对，下一轮操作已经终结、从未完成列表消失，App 反而没有读到终态。全局屏障与 `EditingSession.OutcomeUnknown` 又是两处状态，清掉其中一个不足以恢复提交。HelpText 先判断通用可提交条件，掩盖了具体阻塞原因。

**修复与经验：** `8e9b2ab` 保留准确操作 ID／哈希，操作从未完成列表消失后仍继续只读查询；取得权威终态、相关新采集和匹配草稿核对成功后再恢复入口。失败保留绑定和屏障，按有界退避只读重试，退出取消恢复任务；提示优先给出真实阻塞原因。恢复终态不是重新 Accept，更不能自动续写。

同时要区分误锁与真实未知：旧格式化 `76958…` 缺少完成证据，只在用户明确放弃后按开发数据处理收口为格式化 Failed／NotVerified、整体 PartiallyCompleted，保留原证据，没有冒充成功。这不是以后自动忽略未知结果的依据。见 [Quality 的旧记录收口](../Quality.md#2026-10-10-用户要求解除旧未知记录开发数据收口) 和最新恢复验收。

### 7. 同样叫“采集失败”，发生位置和根因不同

**大层查询慢：** 实际层 `GetPhysicalExtent` 返回 14,893 条记录，单方法约 42.6 秒，多次安全采集接近超时。修复是在完整新事实允许时采用严格单 HDD／唯一实际层成员关联快路径；复杂或证据不全仍走严格核验。不能靠忽略身份核验、沿用旧缓存或简单延长超时掩盖问题，也不能把方法耗时改善说成全部编辑都已提速。

**报告编码失败：** 另一次采集、合并、投影和快照保存均成功，但历史 scope 来源累积为 1,476 条，完整报告二次转义后超过 3 MiB IPC 预算。`b4ded5c` 仅淘汰被更新完整成功事实覆盖的旧证明；仍被对象／字段引用及失败、不完整、迟到来源继续保留，未增大预算或清库。采集源数量多与真实硬件对象多不是同一件事。

**诊断丢失：** 原异常被通用“采集失败”覆盖，开发者看不到代码、阶段和 provider 原因。修复透传有界错误详情至现有开发页和诊断路径。后续排查应先分清 collect、merge、project、save、encode、transport，以及写入是否已 CallIssued；写前采集失败应准确记为 NoCall，不能一律记未知。旧记录没有保留的原因不能事后编造。依据：[调查报告](../Review/Single-Hdd-Tier-Capacity-20261009.md)、[报告超限验收](../Quality.md#2026-10-10-采集报告超限与诊断丢失限定验证)。

### 8. 把“禁止新写入”错误扩大成“禁止退出”

**表现与原因：** 持久 OutcomeUnknown 和正在执行的真实调用共用退出门，旧未知记录会让 WinPool 无法正常退出。它需要阻止新写入，但并不等于后台仍有一个不能中断的活动调用。

**修复与经验：** `545de24` 区分两者：活动调用继续受退出保护，只有持久未知时允许正常退出，保留屏障和证据；托盘说明具体拒绝原因。后续恢复任务在关闭时取消，避免延迟采集继续回写界面。10 月 10 日带未知记录的原托盘退出有 App／Agent 均为 0 的证据；10 月 11 日最终修复也核对两进程正常退出及重启无自动写入。某轮只观察到进程消失、退出码未取得，就只能报告该观察，不能补成 exit 0。

### 9. 真实编辑投影把一个层概念画成了两个

**表现：** `showSourceTierTemplates: !IsSimulation` 让同一介质的 unused 池模板与 `actualVDtier` 同时显示为两层；用户已明确它们在编辑界面属于一个产品概念。

**原因与经验：** 投影按是否模拟来选来源，没有优先采用实际 VD 层来表示概念。当前投影改为 actual 优先，管理视图仍保留真实对象，编辑摘要去掉 provider 前缀。核对投影时要分别看产品表达和管理所需的底层对象，避免重复显示或误删真实对象。

### 10. 推荐重置、撤销基线和空占位被混为一谈

**表现：** Real `TierFieldChanged`／`ResetTierField` 过早返回，只允许 HDD `Size`，可编辑的新层参数没有“恢复推荐”按钮。恢复后最早的 Undo 层仍是无成员的隐藏 `Parity5` 占位，真实单 HDD 当前 `Simple1` 因而被误判为 changed。

**原因与经验：** 字段资格和新层规格参照没有排除空占位，并把恢复推荐与撤销到基线混成一个动作。当前新层参照排除空占位，保存后重新选择仍对比首次有成员的规格；恢复箭头表达恢复推荐，Undo 表达撤回编辑历史，两种语义要分开检查。

### 11. 把 64K 默认推荐误写成产品限制

**表现：** 用户的默认推荐是 64K，却被误写成下拉框、角色 validator、自动布局、后台 adapter、PowerShell 和 ReFS 探测的硬限制；只修下拉框不足以恢复其它路径。

**原因与经验：** 把旧验收范围变成产品禁令，并让各环节各自保存候选值。当前 Domain 共用候选，所选文件系统和簇大小贯穿 typed plan、哈希、preflight、`Format-Volume` 与后态；目标卷按 provider 精确匹配，新建格式化要求目标仍为 RAW，既有卷格式化不套用 RAW 前置条件。ReFS 支持 4K／64K 候选，NTFS 规则按 OS build 判断。应从选择到执行和后态核对同一选项，不能把旧验收范围固化成产品禁令。

真实 GUI 已核验一次原 Apply 创建 WDC 单 HDD `Pool01` → 64 GiB VD → NTFS4096 `Parity4K`，8 个内部操作均为 Completed／Verified；独立证明 [`ntfs4k-independent-proof.json`](../../artifacts/test-results/20261012-product-parity/ntfs4k-independent-proof.json) 的 33 项断言全部通过。随后既有分区 ReFS4096 `ParityReFS4K` 格式化操作 `b4bb9539a035441888547c6b035b0af1` 也为 Completed／Verified。这些证据证明对应的短时路径成功，不证明长期耐久。

### 12. Popup 拖动定位和自动化输入没有对准真实事件

**表现：** Popup 每次移动都重新定位，并混用 root 与 host 坐标。测试用 `SetCursorPos` 不能产生 WinUI 捕获所需的有效指针移动，失败样本无法说明产品拖放事件失败。

**原因与经验：** Popup 重定位和坐标空间混用导致画面跳动；光标位置变化也被误当成有效指针输入。当前改为同一 `XamlRoot` 内固定 overlay、用 `RenderTransform` 移动，并由 host 负责命中与释放；源卡片调整不透明度。改用绝对 `mouse_event` MOVE 后，12 帧记录中真实与模拟拖入均成功，源和目标位置固定并建出一个 HDD 层；最终版本复测真实拖入也成功。保留早先失败样本，但不把它们当成产品事件失败证据；临时诊断代码已移除。

### 验证覆盖错误为什么连续漏过

问题不只是“没有跑更多测试”，而是把不同层级的证据混称为“实测过”。用户要求实测软件界面，代码测试不能替代鼠标拖动；字段保存和取消确认不能替代接受确认后的真实执行；显式 64 GiB 成功不能证明默认 MAX 的搜索和恢复也成功。首次 Apply 成功，也不能证明后续操作已经恢复可用。

| 修改 | 当轮实际证据 | 不能据此宣称 |
| --- | --- | --- |
| `732a9d8` 建池字段与确认 | 115 项定向回归；原生字段保存、撤销／重做及总确认取消；无写入 | 拖放建层或完整 Apply 已通过 |
| `15febce` 拖放与按介质建层 | 真实单 HDD 64 GiB Apply、自动分区、Apply 后拖动；模拟 HDD、SSD 草稿 | 默认 MAX、SCM 或全部介质矩阵已通过 |
| `eeafc32` 保存和默认布局 | 47 项不同定向用例；真实草稿／重置未提交；模拟分区布局实际 Apply | 真实默认 MAX 创建、真实格式化和分区修改已通过 |
| `8e9b2ab` MAX 与恢复 | 104 项定向回归；真实默认 MAX 3724 GiB、自动分区、卷标修改、压缩及清理；16 个真实操作／23 步 Verified；正常退出／重启无续写 | 所有真实与模拟分叉、完整字段矩阵、多层实机及全部故障场景已收口 |

以上计数属于各次修复，不累计成一次全量验收。当前 V0.59／迭代 9 Plan 仍有未验项目，不能因版本提高或某轮回归全绿改写状态。最新一轮未额外注入实机未知故障；采集诊断的部分原始运行输出未留存，证据限制保留在 Quality，不为补齐报告反复重跑。

### 留给后续修改的具体经验

- 动手前从模拟系统走一遍用户指定操作，列出可见动作、默认值和末态，再对应真实执行适配；不要先搭另一套流程再对齐外观。
- 自查沿完整使用链进行：空池拖入 → 自动层／VD → 属性保存及撤销重做 → 接受原 Apply → 实际对象 → 再次拖动／分区操作 → 退出重启。只选与本次修改相关的步骤，不机械地每次全跑。
- 公共规则要追到所有消费者，包括保存意图、资格判断、默认布局、指纹恢复和延迟 UI 事件。发现同类遗漏后，重新找重复入口，而不是只补用户指出的那一个按钮。
- 对安全屏障查清准确操作、调用边界和恢复状态；修复误判、失联终态和陈旧界面状态，保留真正未核实的写入保护，不用清空记录换取可操作。
- 按用户要求做最小充分验证，把额度用在相关原生操作和真实末态上。交付直接写明草稿／取消／真实提交、明确容量／默认 MAX、模拟／实机的边界；发现失败先取证，不用反复全量测试代替定位。

## 布局重构

### 经过与结果

2026-09-04 至 09-05，执行 09-03 的统一布局引擎提案：先完成计划安装和文档移交，再以四个提交实施 TL1–TL8（引擎、面板、投影、紧凑头）。384 项自动测试通过、0 警告；人工走查却发现三个问题，三轮返修中又多次出现 `LayoutCycleException`，进程被 WinUI 布局保护终止。

两次未实机确认就宣称修复，第三次用固定宽度 170 顶替真实不换行宽度需求。最终开发者判定实现偏离单位布局思想，12 个本地提交及 1 份未提交诊断残留全部回退至 `0ef6d22`。原记录记载约耗费 5 小时和 15% 周额度；当次净产出只有复盘，不表示后续布局工作也被回退。

### 错误在计划期已经形成

原设计由根级整数 `Wunit/Hunit` 计划决定列数、换行、收缩预算、行高与复杂池的 2 单位下限，像素只负责最后映射。AI 却把“面板消费引擎结果”理解成“每个面板各自调用引擎”，用局部像素重规划架空根级预算，出现复杂池从 2W 被压成 1W。

这不是单纯写代码时跑偏：错误模型已经藏在获批计划的“两个面板改走引擎”表述中。开发者批准了抽象描述，未必能看到其背后的错误具体化。原计划有三个缺口：

- 列出引擎拥有什么，却没解释为何使用分辨率无关的单位计划、为何每个表面只做一次根级规划。
- “输出子项最终宽度”与“采用面板收到的实际宽度”合读有歧义：本意是三个表面各用宿主宽度，却被理解成嵌套面板分别规划。
- 按容量比例分配原本只适用于叶节点分区条带，却被泛化成三模式全局分配系统。

因此，当时需要澄清的不只是方法名，而是根级计划与面板消费的关系，以及紧凑头形态、不换行判定、预算不足分配三个具体边界。以上是当时设计的解释，不是所有布局需求的通用限制。

### 为什么返修仍然无效

在 `MeasureOverride` 中对子项做无约束 `Measure`，形成布局重入。随后挪到 `LayoutUpdated` 并用低优先级调度，仍未解除“度量改变期望尺寸 → 触发布局 → 再度量”的反馈环；只是改变了触发时机。此案例不能简化成“所有 Measure 都不允许”。

固定宽度 170 绕开了原目标，却没有实现三段式宽度分配和真实不换行宽度。它是未经确认的需求替换，不是原问题已经修好。托管测试没有覆盖这个原生反馈环，两次返修后开发者仍能当场复现闪退。

### 排查与验证中的具体陷阱

- 用 Python heredoc 给 C# 插桩时，`\n` 转义错误造成 8 个编译错误；未察觉构建失败，又启动了旧程序，险些把旧版本表现当成修复证据。验证需要对应实际构建成功的产物和运行路径。
- 运行程序锁住 `artifacts/Release`，导致运行树合并失败。逐项目测试可绕过部分输出冲突，但不代表完整运行树已更新；隔离输出与运行产物仍需区分。
- Git 对非 ASCII 文件名的转义显示曾导致冲突排查漏项；归档时也曾误改历史叙事，后来自查还原。文件是否齐全、历史是否原样保留，要核对实际文件和差异。
- 当时保留下来的有效排查手段是读取 `app-crash.jsonl` 和 Windows 事件日志（1000/1026），并用插桩获取真实运行数据。目标页面走查包含启动、经过欢迎窗、打开页面、观察存活以及检查是否新增崩溃日志，而非只确认进程启动。

原记录还提到页面记忆当时依赖 `MainWindow_Closed` 异步保存，后续已改为切页保存、关闭兜底；两个备份 stash 后来也已不存在。这些是历史状态，不能当成当前待修缺陷或可用恢复点。

## 协作与代码理解误判

- 开发者问“按你的看法应该怎么做”，AI 回答后直接构建、测试、启动应用，把讨论当成执行授权。
- 三个算法边界问题通过选择题组件发出，但用户实际未收到。工具返回“用户未提供答案”，AI 却把自标“推荐”的选项当成获批决定。未收到答复不能证明用户认可；这也不意味着普通局部实现都要反复请示。
- 解释关窗流程时，只看 `DetachAsync` 名称便声称会通知后台停止监控；实际方法只取消 UI 本地循环、不发送 IPC，监控继续由托盘管理。直到用户指出矛盾才阅读实现。方法名和调用点不足以证明行为，解释代码与修改代码都需要核对被调用实现。
- 反复“构建 → 启动 → 崩溃 → 再构建”却没有新增根因证据，持续消耗时间与额度。值得保留的是失败后重新取证和修正判断，而不是把原文的“两次后停止”“定位后都等批准”等措辞变成通用门槛。

## 采集对象持续多出

2026-09-15 至 09-16 记录，Astra 计划、Sol 执行。计划、实现、自动测试以及 AI 做过的真实图形界面检查均未发现问题；开发者人工检查才发现某项应有 7 个对象，实际出现几十个。计划已经经过人工检查，示例展示了少量正确对象，参考旧代码也有过滤，但这些信息没有转化成 AI 对正确集合的理解。

返修过程并非“一次补过滤就完成”：

1. AI 将几个采集器的结果合并，漏掉参考实现已有的过滤。
2. 人工指出后补了过滤，但最终仍是几十个对象；继续检查才发现旧显示与新显示又被合并。
3. 再次要求改正，AI 仍在原合并方案上增加筛选，没有重新追踪最终结果的来源。
4. 直到人工明确要求替换、取消旧显示，功能才收口。

对应提交链：`5951703` → `00dee27` → `12add48`。这是同一问题连续未修完整；7 不是设备数量上限，“替换”也不是所有需求的通用答案。已有专门统一层，AI 仍让上下游各自承担筛选、合并和字段处理，形成多个结果来源。

这里不只是缺少一次 UI 测试，而是做了界面检查仍没核对业务对象集合。人工反例出现后，也没有及时推翻原来的解释。用户最终承担了发现错误、解释预期、检查返修和指定正确方向的成本；“心累”来自工具没有减少这份负担。

## 补测试的作用与限度

`e81c116` 增强了采集事实写库/重载/报告、监控双写入路径与 CSV、即时/草稿提交对账测试；相关三个项目 196 项通过。但它没改业务实现，没验证真实 Windows 采集过滤、原生 UI 事件或完整进程重启，也没消除重复实现路径，不能称为已解决重复踩坑。
