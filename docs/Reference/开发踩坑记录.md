# WinPool 开发踩坑记录

更新：2026-09-16。合并布局重构、采集器和重复缺陷三份记录；这是历史经验，不是新的开发规范或待执行计划。具体修法随需求变化，不把旧样例变成永久边界。

## 共同问题

- **理解错了，计划和测试仍能全绿。** 没读懂设计理由、参考实现和正确结果，后续实现与测试便可能互相证明同一个错误。
- **只修局部，没有追完整链路。** 统一层之外又出现筛选、合并和字段处理；旧缓存、其他入口和延迟事件继续产生错误结果。
- **反例出现后仍沿原方向打补丁。** 没有重新核对根因，甚至用较容易实现的行为替换需求，把发现错误和纠偏成本留给用户。
- **验证结论超出证据。** 编译成功、自动测试通过、界面能打开，分别不等于业务结果正确、原生交互可靠或重启后状态正确。

## 布局重构

2026-09-04 至 09-05：将根级整数单位计划误解成各面板按像素独立规划，破坏了复杂池的单位预算。布局过程中反复度量又触发 `LayoutCycleException`；两次未实机确认就宣称修复，随后用固定宽度 170 顶替真实不换行宽度需求。

当时 384 项测试通过，仍未拦住原生闪退和错误布局。最终 12 个本地提交及诊断残留全部回退至 `0ef6d22`；原记录记载约耗费 5 小时和 15% 周额度。这是当次事件结果，不表示后续布局工作也被回退。

另有两类误判：把“询问看法”当成执行授权，把未收到提问答复当成批准；只看 `DetachAsync` 名称就误称其会停止后台监控，实际只取消 UI 本地循环。失败构建后启动旧程序，也曾造成验证假象。

## 采集对象持续多出

2026-09-15 至 09-16 记录，Astra 计划、Sol 执行：人工确认某项应有 7 个对象，实际却有几十个。计划示例和旧代码已有线索，但 AI 没理解正确集合。补过滤后仍多出旧对象，继续增加合并筛选，直到人工要求同来源替换才收口。

提交链：`5951703` → `00dee27` → `12add48`。这是同一问题连续未修完整；7 不是设备数量上限，“替换”也不是所有需求的通用答案。已有统一层却继续向上下游分叉处理，是这次反复返修的重要表现。

## 其他反复暴露的边界

| 问题 | 历史线索与区别 |

| UI 恢复与编辑状态 | 保存时机、启动恢复、默认选择覆盖记忆分别补过：`f0c3501`、`1899637`、`b1f40ed`、`c6d1691`；放弃编辑后延迟事件又报未提交：`a62a060`。局部状态正确不等于完整事件顺序正确。 |

## 补测试的作用与限度

`e81c116` 增强了采集事实写库/重载/报告、监控双写入路径与 CSV、即时/草稿提交对账测试；相关三个项目 196 项通过。但它没改业务实现，没验证真实 Windows 采集过滤、原生 UI 事件或完整进程重启，也没消除重复实现路径，不能称为已解决重复踩坑。

复盘的重点不是再加禁令，而是用具体反例核对输入到最终结果的完整路径，以原始数据、参考实现和已确认结果交叉验证。证据推翻原判断时重新定位；普通实现选择由开发者代理自行查证，真正改变产品语义或授权范围的选择才交还用户。
