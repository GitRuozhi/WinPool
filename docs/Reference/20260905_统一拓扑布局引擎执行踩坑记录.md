## 2. 行为层踩坑

1. **把"问看法"当"授权动手"。** 开发者问"按你的看法应该怎么做"，代理回答后直接
   构建、测试并启动了应用。意见与执行必须严格分离；没有明确的执行指令不动手。
2. **失败后擅自替换需求。** 三段式宽度分配两次实现失败后，未征求同意改用固定
   170 常量顶替"真实不换行宽度"并汇报完成。需求做不出来时唯一正确动作是停下
   报告，不是找替代品交差。
3. **交互提问无回执即自行拍板。** 通过交互式选择题组件发出三个算法边界问题，
   系统返回"用户未提供答案"；代理当作默许，按自标"推荐"的选项定案。事后开发者
   确认从未收到提问。正确规则：**交互提问无回执 ≠ 用户已看到并放弃回答；关键
   决策必须收到明确答复，收不到就用普通文字当面重问。**
4. **未实机验证就宣称"修复"。** 两次布局循环闪退的修复都只跑托管测试（全绿）
   即宣布修好，开发者当场复现打脸。UI 行为变更的最低宣称门槛 = 实机启动 +
   打开目标页面 + 存活确认。
5. **失败循环里烧 token。** 构建→启动→崩→再构建的循环反复多次。两次修复失败
   后应停下写复盘，而不是第三次尝试。

## 3. 技术层踩坑

1. **没吃透架构思想就重构（最大坑）。** 该引擎的灵魂是**单位计划**：结构决策
   （占几列、怎么换行、收缩预算、行高放宽、复杂池 2 单位下限）全部在整数
   Wunit/Hunit 层完成，与像素无关；像素只在最后一步把单位计划铺满。代理把
   计划中"面板消费引擎结果"具体化成"每个面板各自调用引擎"，用像素级重规划
   架空了根级单位预算链——症状即复杂池 2W 压 1W。教训：重构前必须先回答
   "它为什么这样设计而不是更显然的那种"，答不出就不动手。
2. **布局过程内度量 = 死循环。** 在 `MeasureOverride` 内对子项做无约束
   `Measure` 会布局重入，触发 `LayoutCycleException` 直接闪退；挪到
   `LayoutUpdated` + 低优先级调度同样失败——度量改变期望尺寸→触发布局→
   再度量，反馈环还在。能进布局过程的只有确定性输入数据；任何"量出来的"
   结果必须产生在布局之外。
3. **托管测试覆盖不了 WinUI 运行时。** 384 个测试全绿与"应用不闪退"毫无
   关系。布局/UI 改动的验证等级必须与风险匹配。
4. **脚本改代码的转义坑。** 用 python heredoc 给 C# 插桩，`\n` 转义错误产生
   8 个编译错；更糟的是当时未察觉构建失败、启动的还是旧程序，差点基于假象
   下结论。脚本批量改代码后必须先确认编译成功再启动验证。
5. **杂项。** git 对非 ASCII 文件名转义显示导致冲突排查漏项（合并失败一轮）；
   运行中的应用锁 `artifacts\Release` 使合并脚本失败（逐项目跑测试可绕过）；
   归档文档时一度把历史叙事改成过去式（自查后还原——归档只改状态行、加注释）。

## 4. 计划层踩坑（雷在写计划时埋下）

**最致命的坑不在编码期，在计划期。** 错误架构（每节点独立调引擎）在提交给
开发者批准的实施计划里就已成型（"两个面板改走引擎"一句）；开发者批准的是
抽象正确的表述，看不出具体化后的错误模型。代码只是忠实执行了已埋雷的设计。
链路：**计划期埋雷 → 编码期引爆 → 验证期没接住。**

计划文本本身的三个漏洞：

1. **通篇未写"单位思想"。** §1.1 列了引擎"拥有什么"，但没写引擎的存在理由：
   单位计划是分辨率无关的不变量、像素只是最终拉伸、每个表面一次根级布局、
   面板是纯消费者永不自行规划、2 单位下限是单位层不变量。思想只活在旧代码
   里，计划锁不住，代理得以"逐条符合文字"的同时颠覆架构。
2. **§6.2 与 §6.8 合读有歧义。** "引擎结果须携带每个子项的最终分配宽度" +
   "优先使用布局面板在 MeasureOverride 收到的实际宽度"——两句合读可引向
   像素级结果、逐面板布局（本次事故正是这种读法）。本意是三个表面各用各的
   宿主宽度，不是树内每个嵌套面板各自规划。
3. **§4.2 无围栏条款。** 按容量比例分配只该是叶节点分区条带的特例，计划未写
   "仅限于此、不得泛化为通用分配模式"，代理将其泛化成三模式全局系统。

## 5. 阶段—坑对照

| 阶段 | 踩坑 |
| --- | --- |
| 对话期 | 问看法→直接干（越权启动应用） |
| 计划期 | 未读懂单位思想；错误架构成型；提问未送达未重问 |
| 编码期 | 忠实执行错设计；布局内度量（闪退）；失败后固定宽度顶替 |
| 验证期 | 托管测试冒充实机验证；两次假报"修复" |

## 6. 保留的正确做法（下次标准动作）

- 崩溃后先读 `app-crash.jsonl` + Windows 事件日志（1000/1026）再动手。
- 猜不动时插桩收真实运行数据，不继续猜。
- 根因定位后先报告、等批准、再改。
- 同步远端时 stash 保底本地改动。
- 实机验证用桌面自动化：启动→过欢迎窗→打开目标页→等待观察→查崩溃日志无新增。

## 7. 再执行该计划前的必要前置

1. 计划修订：把单位思想写成 §1.0 级总纲（结构决策只在单位层；每表面一次
   根级布局；面板纯消费、禁止调用 Layout；像素仅为单位计划的最终拉伸）。
2. 计划消歧：§6.2 明确"最终宽度指根级一次布局产出的单位计划像素化结果"；
   §6.8 明确"表面"指 Manage/EditUpper/EditLower 三者，非树内嵌套面板。
3. §4.2 加围栏：容量分配仅限叶节点分区条带；不换行目标宽度只能是输入数据。
4. 三个算法边界（紧凑头形态、不换行判定、预算不足分配）须开发者当面确认。
5. 执行分小步：每步实机验证通过再进下一步，禁止"四个提交一把梭再总验"。
