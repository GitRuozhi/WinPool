# V0.44 App / Agent runtime alignment experiment

[English](V0.44-App-Agent-runtime-alignment-experiment.md) | [简体中文（仅供阅读）](V0.44-App-Agent-runtime-alignment-experiment.zh-CN.md)

## Status

- **Kind:** temporary experiment plan
- **Purpose:** verify whether App and Agent can publish compatible same-name .NET desktop runtime assets
- **Not:** a product architecture change or final distribution decision
- **Scope:** V0.44 runtime collision only

This experiment exists to test one hypothesis:

> If `WinPool.App` explicitly participates in the same WindowsDesktop / WinForms framework profile used by `WinPool.Agent`, the five current same-name runtime collisions may resolve to identical published files.

No production staging change is authorized by this experiment alone.

---

## 1. Current problem

V0.44 App and Agent self-contained publishes currently contain:

- 207 same-path files with identical SHA-256;
- 83 Agent-only files;
- 5 same-path files with different contents.

The five collisions are:

```text
Microsoft.VisualBasic.dll
System.Drawing.dll
System.CodeDom.dll
System.Diagnostics.EventLog.dll
System.Diagnostics.EventLog.Messages.dll
```

Because same-name files differ, the current flat staging merge correctly aborts.

The existing nested layout remains the control:

```text
WinPool/
├── WinPool.App.exe
└── Agent/
    └── WinPool.Agent.exe
```

---

## 2. Hypothesis

`WinPool.Agent` uses WinForms and therefore publishes against the WindowsDesktop framework profile.

`WinPool.App` does not.

The experiment will test whether adding an explicit WindowsDesktop WindowsForms framework reference to the App causes both publishes to select the same implementation for the five colliding framework assemblies.

Experimental App change:

```xml
<ItemGroup>
  <FrameworkReference Include="Microsoft.WindowsDesktop.App.WindowsForms" />
</ItemGroup>
```

Do **not** enable:

```xml
<UseWindowsForms>true</UseWindowsForms>
```

The App remains WinUI 3 and must not introduce WinForms UI code.

---

## 3. Non-goals

This experiment does not:

- merge App and Agent processes;
- remove WinForms from Agent;
- make Agent framework-dependent;
- enable trimming;
- introduce custom assembly probing;
- manually replace DLLs;
- manually delete framework files;
- change images;
- change Windows support policy;
- change the final staging layout unless the experiment succeeds and a later decision approves it.

---

## 4. Procedure

### Step 1 — Record control publishes

Create clean self-contained `win-x64` publishes for:

```text
WinPool.App
WinPool.Agent
```

Record for each relative path:

- file size;
- SHA-256;
- assembly version where applicable.

Confirm the known baseline:

```text
207 identical
5 collisions
83 Agent-only
```

---

### Step 2 — Add App framework reference

Add only:

```xml
<FrameworkReference Include="Microsoft.WindowsDesktop.App.WindowsForms" />
```

to `WinPool.App.csproj`.

Do not change Agent.

Do not change staging logic yet.

---

### Step 3 — Rebuild clean publishes

From clean output directories:

```powershell
dotnet restore
dotnet build
dotnet test
dotnet publish WinPool.App
dotnet publish WinPool.Agent
```

Both publishes remain:

```text
win-x64
self-contained
PublishTrimmed=false
```

---

### Step 4 — Compare publish trees

Run the same relative-path + SHA-256 comparison.

Record:

```text
identical count
collision count
App-only count
Agent-only count
total App size
total Agent size
combined unique-file size
```

Pay special attention to the five original collision files.

---

## 5. Success condition

The preferred successful result is:

```text
Original:
207 identical
5 collisions

Experiment:
212 identical
0 collisions
```

Equivalent results are acceptable if:

- all same-relative-path files are byte-identical;
- no new same-name collision appears;
- both applications still publish and run correctly.

If successful, a later implementation may build a single flat portable dependency union in which identical runtime files are stored once.

---

## 6. Failure conditions

The experiment fails if any of the following occurs:

- one or more of the five collisions remain;
- new same-name collisions appear;
- App publish becomes invalid;
- App startup fails;
- WinUI/XAML/PRI/XBF behavior regresses;
- Agent behavior regresses;
- the App actually begins depending on WinForms UI behavior;
- the result requires manual DLL replacement or unsupported probing configuration.

Partial reduction such as:

```text
5 collisions → 2 collisions
```

does not authorize a flat merge.

---

## 7. Runtime validation

If the collision count reaches zero, validate both executables from their experimental publish outputs before changing staging.

### App

Verify:

- cold start;
- WinUI initialization;
- XAML / PRI / XBF;
- navigation;
- theme;
- language;
- Picker;
- Agent connection.

### Agent

Verify:

- startup;
- tray icon;
- tray commands;
- inventory;
- monitoring;
- SQLite;
- IPC;
- shutdown / restart.

---

## 8. Decision after experiment

### If successful

Record the result and prepare a separate staging change that:

1. publishes App and Agent independently;
2. compares same-relative-path files by SHA-256;
3. stores identical files once;
4. fails on any different-content collision;
5. places both executables in the final shared directory;
6. updates Agent executable path handling;
7. validates the final merged staging.

### If unsuccessful

Revert the experimental App framework reference.

Keep the existing:

```text
WinPool.App.exe
Agent/WinPool.Agent.exe
```

layout.

Do not attempt:

- last-writer-wins DLL overwrite;
- custom probing paths;
- mixed parent/child runtime loading;
- private runtime loaders.

The unresolved runtime duplication remains accepted V0.44 technical debt.

## 10. Completion

This experiment is complete when one of two conclusions is established:

### A. Alignment works

> App and Agent select byte-identical same-name runtime assets and can proceed to a separately reviewed flat staging implementation.

### B. Alignment does not work

> WindowsDesktop framework alignment is insufficient; V0.44 keeps isolated App/Agent runtime directories and does not introduce unsupported runtime probing workarounds.
