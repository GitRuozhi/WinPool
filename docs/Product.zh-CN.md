## 目标

WinPool 是第三方 Windows 存储系统桌面应用。长期目标是用统一界面替代割裂的“磁盘管理”和“存储空间”图形体验，集中呈现存储拓扑、测试、监控和可审阅操作。

产品应清晰表达系统、存储池、存储层、物理磁盘、虚拟磁盘、分区、卷、网络存储与其他逻辑组之间的关系，同时不隐藏重要参数。

## 产品原则

- 同时呈现完整存储拓扑和聚焦的操作工作区。
- 所有拟执行操作必须明确、可审阅、类型化且可审计。
- 将模拟和只读发现作为一等能力。
- 集成测试、监控、比较与证据导出，但不捆绑或重新实现外部基准引擎。
- 内部契约应足以支持未来开发者和 AI Agent 使用，但目前不冻结公共 SDK、插件 API、数据库契约或线协议。
- 保持双语、主题感知、键盘可访问、高对比度和响应式桌面行为。

## 产品边界

WinPool 可以通过只读采集器检查本机、编辑持久化模拟系统、监控支持的设备，以及执行经过明确审阅的辅助动作。

真实存储结构修改在 V0.5 之前不属于产品边界。在此之前，WinPool 不得初始化、清理、格式化、创建、删除、修复或调整真实磁盘、分区、卷、存储池、存储层或虚拟磁盘。V0.5 是最早可通过经过审阅的类型化计划引入这些操作的阶段；产品并非永久只能模拟。

从 V0.5 起，每次真实修改都有两类明确授权：

- 开发 Agent 每次执行实际修改前，必须立即向开发者请求批准，明确说明操作和目标；先前、宽泛或隐含的批准均不适用。
- 产品用户在当前会话显式选择“本机真实修改”选项，即授权执行 V0.5 的受控真实操作。UAC 提权或 Real 模式本身不构成同意，且同意不得预选或持久化。

真实修改路径必须保留类型化操作、目标校验、操作预览和审计记录。模拟仍为默认路径，自由形式存储命令仍不属于产品边界。

## WinPool 1.x 范围

WinPool 1.0 及整个 1.x 产品线聚焦存储拓扑、管理与编辑、监控、设置、数据安全和达到发布质量的交付。“测试”和“开发”标签页继续作为可见导航入口存在，但各自只显示简短路线说明。完整用户界面、登记目录测试工作流、开发者工作区和 AI Agent 功能不属于任何 1.x 版本，计划作为 WinPool 2.0 功能推出。

磁盘测试、外部工具和开发/AI 诊断子系统已从 1.0 发布路径移除，推迟到 1.x/2.0；它们不属于受支持的 1.x 产品表面。

## 架构线

V0.4 产品线保留已接受的 V0.13 视觉基线和 V0.2 多进程重写，并收缩为 1.0 发布路径所需的两个进程：

- 一个无打包 WinUI 3 App；
- 一个可见的每用户托盘 Agent 和 SQLite 写入者；
- 类型化命名管道 IPC 和默认拒绝执行策略。

项目版本在新产品线采用 `Va.b`，同一产品线的非零迭代可采用 `Va.bc`。架构里程碑写到 `Va.b`；数据库 schema 修订号、算法 ID 和 IPC 兼容标识属于内部契约，不构成额外项目版本。

## 已确认开发路线

用户于 2026-08-12 确认以下产品路线。它定义的是各阶段目标，并不授权绕过产品边界、替代活动 Plan，也不表示某阶段已完成。

| 阶段 | 目标 | 约束 |
| --- | --- | --- |
| V0.1 | 交付最小原型，确定基本前端视觉方向。 | 已完成的历史基础。 |
| V0.2 | 完整重构代码，确定基础架构和开发规则。 | 已完成的历史基础。 |
| V0.3 | 修复代码缺陷，保证正常运行。 | 已完成的历史基础。版本确认不会把剩余原生或人工证据写成通过。 |
| V0.4 | 补完美术与视觉打磨，完善已有功能和基本交互。 | 保持可访问性和已接受的结构基线。 |
| V0.5 | 交付 1.0 存储管理产品所必需的最小管理和编辑闭环。 | 首个允许在开发者和产品用户显式授权模型下引入选定受控真实存储结构操作的阶段；1.0 不要求覆盖全部操作。 |
| V0.6 | 补完 1.0 所需的监控和存储健康体验。 | 排除测试执行和完整测试工作区；监控仍须使用显式目标、有界持久化和真实诊断。 |
| V0.7 | 冻结 1.0 功能范围，关闭管理、监控、设置和数据处理之间剩余的集成缺口。 | 测试、开发者和 AI Agent 工作区继续作为占位页；不再引入新的功能家族。 |
| V0.8 | 关闭已知的发布阻断缺陷和质量缺口，并在保留便携式的同时开始签名 MSIX 打包路径。 | 工作限制在已冻结的 1.0 范围内；未来未知缺陷不能预先宣称已经修复。 |
| V0.9 | 进入内测，在定义好的受支持 Windows 平台矩阵上测试并修复问题。 | 在明确矩阵上验证便携式与 MSIX 的安装、升级、卸载、启动和数据位置行为。 |
| V1.0 | 发布正式版。 | 必须通过已批准的 V0.9 发布就绪门；V1.0 完成后才开始 Microsoft Store 上架。tag、二进制上传和 GitHub Release 仍需分别明确授权。 |
| V1.x | 以兼容性、可靠性、安全性以及范围狭窄且已批准的管理或监控修正维护 1.0 产品线。 | 整个 1.x 期间，“测试”和“开发”标签页继续作为路线占位页。 |
| V2.0 | 推出完整测试工作区，以及完整开发者与 AI Agent 工作区。 | 外部引擎继续通过独立类型化适配器接入；公共或自动化契约必须另行确认产品设计。 |

每个实施阶段都需要各自确认的 `docs/Plan.md`。默认拒绝执行器、存储编辑模拟优先、只读盘点和数据脱敏边界在整个路线中持续生效；V0.5 的真实修改是对“只允许模拟”规则已定义且须明确授权的例外。

## 安装方式路线

WinPool 当前仅交付无打包、自包含的 Windows x64 便携式应用。目前没有已发布的 MSIX
安装包，也没有 Microsoft Store 页面。文档写明未来路线，不代表对应安装包已经存在。

| 方式 | 可用阶段 | 预期行为 |
| --- | --- | --- |
| 便携式 | 当前已实现并长期保留 | 用户管理完整的自包含程序目录。数据默认位于 `%LocalAppData%\WinPool`；用户明确选择且程序旁目录可写时，仍可使用程序旁 `Data`。 |
| 签名 MSIX | 计划在 V0.8～V0.9 | 开发并验证签名、身份、安装、升级、卸载、启动注册、数据路径、恢复和受支持 Windows 矩阵；便携式继续提供。 |
| Microsoft Store | 计划在 V1.0 完成后 | 正式 V1.0 产品及发布证据完成后，才准备身份、隐私、支持、认证、安装包和商店页面材料；上架不是 V1.0 的完成前置条件。 |

三种方式必须保持相同的安全边界。安装方式不得额外授予存储修改权限、把 Agent 改成
Windows 服务，或绕过显式目标校验。创建账户、保留产品名、上传安装包和正式发布都必须在
当时分别取得明确授权。
