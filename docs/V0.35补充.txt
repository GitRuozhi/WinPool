# WinPool V0.35 代码缺陷收口计划

## 0. 状态与基线

* **目标版本**：V0.35
* **版本迭代**：`c=5`
* **基线版本**：V0.34
* **基线提交**：`5cc676b4873c29e7b00af9fd48e689627eb1dad4`
* **性质**：V0.34 后续缺陷收口与一致性硬化
* **新增产品功能**：无
* **新增项目**：无
* **IPC protocol**：默认保持 `3`
* **SQLite schema**：默认保持 `12`
* **V0.34 Archive**：冻结，不回写历史
* **V0.34 manual/native evidence**：保持原状
* **remote_gate**：`not_required`
* **Push / Tag / GitHub Release / Binary Upload / Deployment**：未经本轮新的明确授权不得执行

V0.35 不进行新的架构重构，只修复 V0.34 验收后确认的剩余缺陷。

# 1. 缺陷清单

| ID        | 优先级 | 缺陷                                                           |
| --------- | --- | ------------------------------------------------------------ |
| V35-P1-01 | P1  | Comparison-first 场景仍会重复创建 Local `SystemId`                   |
| V35-P1-02 | P1  | 一个慢的 client event watcher 可以阻塞全部事件读取与 reconnect              |
| V35-P2-01 | P2  | `worker_processes` terminal state 可被迟到 callback 写回非 terminal |
| V35-P2-02 | P2  | shutdown timeout 仍依赖被调用方主动响应 cancellation                    |
| V35-P2-03 | P2  | schema version=12 时没有验证数据库真实结构                               |
| V35-P2-04 | P2  | Main App shutdown 存活检查仍可能被 PID reuse 干扰                      |

# 2. V0.35 必须建立的不变量

## INV-01 Local identity authority

同一 machine binding 的 Local system：

```text
Manage capture
Native capture
Legacy capture
Comparison capture
App restart
Agent restart
```

必须始终解析为同一个：

```text
SystemId
```

不能依赖：

```text
local_inventory_document 是否已经存在
```

来决定 identity。

---

## INV-02 Local capture serialization

两个并发 Local capture 不得执行：

```text
resolve: none
→ create A

resolve: none
→ create B
```

首次 Local identity 建立过程必须串行化。

---

## INV-03 Watcher isolation

任何一个 App-side event watcher：

```text
停止消费
消费过慢
忘记 Dispose
```

都不得阻塞：

```text
Agent event pipe reader
其他 watcher
transport disconnect detection
reconnect
snapshot reseed
```

---

## INV-04 Terminal persistence is absorbing

一旦某个 `ProcessInstanceId` 持久化为：

```text
Exited
Failed
```

之后任何迟到 callback 都不得将其恢复为：

```text
Starting
Running
Stopping
Unresponsive
```

---

## INV-05 Timeout means bounded caller progress

声明：

```text
step timeout = 15s
```

必须意味着 workflow 在 timeout 后可以继续。

不能只意味着：

```text
15s 后 CancellationToken 被取消
```

但仍无限：

```text
await operation
```

---

## INV-06 Timed-out operation cannot commit late terminal effects

shutdown step 超时以后，其迟到完成不得随后：

```text
关闭 control pipe
隐藏 tray
退出 Agent
```

从而使已经进入 `ShutdownPending` 的 Agent 突然退出。

---

## INV-07 Current schema means actual current schema

数据库：

```text
schema_info.schema_version = 12
```

不等价于：

```text
数据库结构正确
```

只有 version 和当前最低结构合同同时满足才能正常打开。

---

## INV-08 Process incarnation is used until lifecycle end

Main App lifecycle 从：

```text
handshake
```

直到：

```text
shutdown/reap
```

都必须使用：

```text
ProcessInstanceId
PID
executable identity
OS process-start witness
```

不能在 shutdown 最后一段重新退化成只判断 PID。

# 3. V35-P1-01 — Local `SystemId` 最终收口

## 3.1 问题

当前 canonical Local identity resolver 主要依赖：

```text
local_inventory_document
```

如果 Local document 尚未建立，则返回新的：

```text
SystemId.New()
```

Comparison capture 本身又不会建立 Local document。

因此 fresh database 下：

```text
Comparison #1 → A
Comparison #2 → B
Comparison #3 → C
```

仍然可能创建多个 Local system row。

---

## 3.2 修复决策

**Local document 不再作为 Local identity authority。**

新的 authority 应来自：

```text
Agent-owned persisted Local system records
+
machine binding
```

不新增新的数据库表，不提升 schema version。

---

## 3.3 实施结构

增加一个聚焦的小型组件，例如：

```text
LocalSystemIdentityResolver
```

它可以位于：

```text
WinPool.Infrastructure.Sqlite
```

或作为 `InventorySnapshotRepository` 的一个明确接口。

不要将 identity 查询重新放回 UI/App。

---

## 3.4 Resolution algorithm

输入：

```text
machineBinding
```

转换为与 `systems.machine_binding_hash` 当前持久化格式完全相同的 canonical binding key。

然后查询：

```text
systems
WHERE
    kind = Local
    AND machine_binding_hash = expected
```

### 0 个结果

创建一个新的：

```text
SystemId
```

并作为当前 capture 的 canonical identity。

### 1 个结果

直接复用。

### 多个结果

这表示历史上已经发生过 identity fragmentation。

V0.35 不删除、不 merge、不修改旧 snapshot evidence。

选择未来 canonical ID 的规则必须确定性。

优先级：

1. 如果当前 `local_inventory_document` 指向其中一个匹配 system，则采用其 `SystemId`。
2. 否则采用最早创建的 Local system。
3. `created_at` 相同则以 `system_id` 做稳定排序。

同时产生内部 diagnostic：

```text
agent.inventory.local_identity_fragmented
```

但以后所有新 capture 统一使用选定 ID。

---

## 3.5 Capture gate

在 `AgentInventoryCoordinator` 增加专用：

```text
SemaphoreSlim localCaptureGate
```

以下两个入口都必须进入该 gate：

```text
CaptureManageAsync
CaptureComparisonAsync
```

gate 至少覆盖：

```text
capture completed
→ machine binding resolved
→ canonical SystemId resolved
→ snapshot persistence completed
→ Local document persistence completed when applicable
```

避免首次采集并发创建两个 ID。

---

## 3.6 Comparison flow

Comparison provider 内部临时 `SystemId` 可以继续存在，仅作为 collector 内部临时 namespace。

但在任何 persistence/comparison 输出之前必须：

```text
Rebind(canonicalSystemId)
```

最终 persisted native/legacy snapshot 不得包含 provisional ID。

---

## 3.7 Manage persistence

Manage capture 必须验证：

```text
decoded document.SystemId
==
projected snapshot.SystemId
==
persisted snapshot.SystemId
```

如果不一致：

```text
fail closed
```

不得继续写 Local document。

进一步建议将：

```text
InventorySnapshot
+
LocalInventoryDocument
```

封装为一个专用 persistence operation，使同一次 Manage capture 的两个持久化结果具有单一 transaction boundary。

如果本轮不建立跨 repository transaction，则至少保证：

> Local document 写入失败不能造成下一次 capture 创建新的 Local identity。

---

# 4. V35-P1-02 — Client event watcher backpressure isolation

## 4.1 问题

当前 client fanout 对每个 watcher 使用 bounded channel，并在 publish 时逐个：

```text
await WriteAsync
```

一个 watcher 满后会阻塞唯一 transport reader。

这会进一步阻止：

```text
读取下一 event frame
发现 server disconnect
启动 reconnect
发布 snapshot reseed
```

---

## 4.2 修复原则

transport reader 不等待 watcher queue 腾空间。

client fanout 应改为：

```text
TryWrite
```

语义：

```text
一个 watcher overflow
!=
整个 transport reader overflow
```

---

## 4.3 Fanout API

建议由：

```text
Task PublishAsync(...)
```

调整为类似：

```text
AgentClientFanoutPublishResult Publish(...)
```

结果至少包含：

```text
Delivered
OverflowedSubscriberCount
HasGap
```

---

## 4.4 Watcher overflow

对每个 watcher：

```text
TryWrite(event)
```

失败：

1. 从 fanout 中移除该 watcher。
2. complete 该 watcher channel。
3. 不等待其恢复。
4. 将本次 publish 标记为 local event gap。

其他 watcher 继续收到当前事件。

---

## 4.5 Overflow 后 authoritative recovery

因为被删除 watcher 已经丢事件，因此 client 必须建立 recovery boundary。

transport supervisor 收到：

```text
HasGap = true
```

后：

```text
disconnect current event transport
→ reconnect
→ GetAgentSnapshot
→ cache authoritative snapshot
→ publish AgentStateReseedEvent to remaining watchers
```

这与 server overflow 使用同一恢复语义。

---

## 4.6 Dropped watcher resubscribe

当原 watcher 重新调用：

```text
WatchAsync
```

新的 subscription 必须首先获得：

```text
latest cached AgentStateReseedEvent
```

然后再接收后续 delta。

---

## 4.7 禁止模式

V0.35 后 transport reader 路径中不得出现：

```text
await watcher.Writer.WriteAsync(...)
```

也不得重新使用：

```text
DropOldest
```

---

## 4.8 Tests

### V35-T-EVT-01

创建：

```text
Watcher A: 不读取
Watcher B: 正常读取
capacity = small
```

发送超过容量的事件。

要求：

```text
A completed
B continues
Publish returns
transport reader not blocked
```

---

### V35-T-EVT-02

A overflow 后：

```text
event transport reconnect
snapshot reseed delivered to B
```

---

### V35-T-EVT-03

A 重新订阅：

首个 state-bearing event 必须是 authoritative reseed。

---

### V35-T-EVT-04

两个 slow watcher 不得阻塞 transport recovery。

---

### V35-T-EVT-05

server overflow 与 client watcher overflow 都进入相同：

```text
gap → reconnect → reseed
```

状态机。

---

### V35-T-EVT-06

连续多次 overflow/reconnect 不得产生：

```text
两个并行 event reader
重复 event stream
旧 stream 重新写入
```

# 5. V35-P2-01 — Worker terminal persistence 单调性

## 5.1 问题

当前 registry 内存状态已经按 `ProcessInstanceId` 管理得较严格。

但 SQLite repository 的 upsert 仍允许：

```text
Exited → Running
Failed → Starting
```

数据库 evidence 与内存 registry 可能因此分叉。

---

## 5.2 明确状态机

允许至少以下 transition：

```text
Starting
→ Running
→ Stopping
→ Exited

Starting
→ Failed

Running
→ Unresponsive
→ Running

Running
→ Failed

Stopping
→ Failed
```

terminal：

```text
Exited
Failed
```

为 absorbing states。

---

## 5.3 Repository policy

新增统一：

```text
ProcessStateTransitionPolicy
```

例如：

```text
CanTransition(current, incoming)
```

repository 自身必须执行检查。

不能仅依赖调用方。

---

## 5.4 SQLite write

选择以下任一方案：

### 方案 A：transaction read + validate + update

```text
SELECT current state
→ validate transition
→ UPDATE
```

优点是语义最清晰。

### 方案 B：SQL guarded UPSERT

通过 `WHERE` 明确限制 transition。

如果使用 SQL guard，不允许只写：

```text
current NOT terminal
```

还应防止：

```text
Stopping → Running
```

等明显逆向 transition。

---

## 5.5 Late callback

callback timeout 后允许其 Task 最终自然完成，但它后续发起的 stale persistence：

```text
Running
Starting
```

必须被 repository 拒绝/no-op。

不得覆盖 terminal evidence。

---

## 5.6 Tests

### V35-T-PROC-01

```text
Starting
→ Running
→ Exited
→ Running
```

最终 DB：

```text
Exited
```

---

### V35-T-PROC-02

```text
Running
→ Failed
→ Starting
```

最终：

```text
Failed
```

---

### V35-T-PROC-03

验证合法：

```text
Running → Unresponsive → Running
```

---

### V35-T-PROC-04

迟到 callback 在 process 已 terminal 后完成。

验证：

```text
registry terminal
DB terminal
```

一致。

# 6. V35-P2-02 — Shutdown hard timeout

## 6.1 问题

当前：

```text
CancellationTokenSource(stepTimeout)
await operation(token)
```

仅能约束愿意响应 token 的 operation。

---

## 6.2 Bounded await

建立：

```text
RunBoundedShutdownStepAsync
```

核心：

```text
operationTask = operation(token)
await operationTask.WaitAsync(deadlineToken)
```

timeout 时：

1. cancel operation token；
2. 记录该 step failed；
3. workflow 继续；
4. observation continuation 必须消费 operationTask 后续 exception，避免 unobserved fault；
5. operation late completion 不得修改 workflow result。

---

## 6.3 Late-effect contract

所有 shutdown action 必须分类审计。

### 可重复 safety actions

例如：

```text
StopMonitoring
RequestTestCancellation
RestoreTemporarySystemState
```

必须 idempotent。

late completion 可以被允许，但不得把 lifecycle state 从 Pending 改成 Stopped。

### Terminal actions

```text
CloseNamedPipes
RemoveTrayIcon
ExitAgent
```

必须在执行不可逆动作之前：

```text
cancellationToken.ThrowIfCancellationRequested()
```

一旦 deadline 已过，不得在后台继续 commit terminal effect。

---

## 6.4 ExitAgent 特别要求

顺序应保证：

```text
cancel background source
→ bounded wait
→ check shutdown-step token
→ ExitAgentThread
```

如果 bounded wait timeout：

```text
不得稍后自动执行 ExitAgentThread
```

---

## 6.5 Tests

### V35-T-SD-01

fake operation 完全忽略 CancellationToken 且永不完成。

验证 workflow 仍在 bounded deadline 后进入下一 step。

---

### V35-T-SD-02

operation timeout 后稍后完成。

验证 lifecycle 仍由当前 shutdown execution 决定。

---

### V35-T-SD-03

模拟 `ExitAgent` timeout。

timeout 后 fake operation later completion 不得调用 exit commit。

---

### V35-T-SD-04

两个 shutdown retry 继续保持 serialization。

```text

```

## 7.2 修复原则

```text

```

```text
CurrentSchemaVerifier
```

---

## 7.3 最低检查项

### Required tables

至少验证所有程序直接依赖的 current tables。

worker_processes.process_instance_id

---

至少检查：

# 8. V35-P2-04 — Main App shutdown process witness 收口

## 8.1 问题

handshake/registry 已经使用：

```text
ProcessInstanceId
PID
executable
StartedAtUtc
```

但是 `CloseMainApplicationAsync` 的 wait loop 仍主要判断：

```text
IsProcessLive(PID)
```

PID reuse 后会把无关新进程当成旧 App 仍然存活。

---

## 8.2 统一 process witness service

避免 control server 和 shutdown 各自实现不同规则。

引入小型 internal abstraction，例如：

```text
IProcessIncarnationVerifier
```

能力：

```text
ReadWitness(pid)
Matches(registration, expectedExecutable)
```

Witness 至少：

```text
PID
normalized executable path
start time UTC
```

---

## 8.3 Handshake

继续使用现有严格规则。

不改变 IPC contract。

---

## 8.4 Shutdown wait

每轮检查 registration：

### PID 不存在

```text
old process exited
→ terminalize registration
```

### PID 存在且 witness 完全一致

```text
same App process still alive
```

继续等待。

### PID 存在但 start witness 不同

解释为：

```text
PID reused
```

旧 registration terminalize。

禁止等待新进程。

### executable 不匹配

同样：

```text
stale old registration
```

不得终止无关 PID。

---

## 8.5 安全原则

V0.35 不因为 witness mismatch 去 kill process。

语义只有：

```text
not the process we own
```

因此将旧 registration 清理为 stale/terminal。

---

## 8.6 Tests

### V35-T-INC-01

same PID + same start + same image：

仍认为 App live。

### V35-T-INC-02

same PID + different start：

旧 App registration terminalized。

### V35-T-INC-03

same PID + different image：

不操作新 process。

### V35-T-INC-04

PID no longer exists：

正常 exited。

### V35-T-INC-05

PID reuse 不再导致 shutdown 永久 Pending。

# 10. IPC / SQLite 决策

## IPC

V0.35 默认：

```text
IpcProtocol.CurrentVersion = 3
```

六个缺陷均可在现有 contract 内解决。

如果实现过程中发现必须修改 wire contract：

> 停止，重新评估。

不得为了内部实现方便随意 bump 到 4。

---

## SQLite

V0.35 默认：

```text
CurrentSchemaVersion = 12
```

Local identity 优先通过现有：

```text
systems
machine_binding_hash
```

建立 authority。

schema verification 也只是读取验证。

因此默认不增加：

```text
schema 13
```

如果最终发现必须新增 column/table/index 才能保证 correctness，则必须作为独立设计决策重新评审，而不是静默修改 schema。

---

# 19. 最终验收重点

V0.35 review 重点不再看“是否改了相关代码”，而看下面六个问题能否被确定性证明。

### A. Comparison-first

在没有 Local document 的情况下，Local identity 是否仍稳定？

### B. Slow watcher

一个坏 watcher 是否仍能拖死整个 App event pipeline？

### C. Late callback

process 已经 Exited 后，迟到 callback 是否还能复活 SQLite 状态？

### D. Fake timeout

一个完全不响应 cancellation 的 shutdown operation 是否还能卡死 workflow？

### E. Fake schema 12

一个只修改版本号、实际缺表的数据库是否还能通过启动检查？

### F. PID reuse

旧 App 已退出且 PID 被复用后，Agent 是否能正确认出“这已经不是原来的 App”？

只有上述六项全部回答为正确行为，V0.35 才视为完成本轮缺陷收口。
