# WinPool V0.33 补充重构与生命周期硬化计划

```yaml
project: WinPool
phase: V0.3
architecture_version: V0.3
status: proposed
branch: main
scope: architecture-convergence-and-hardening
```

## 1. 阶段定位

V0.33 是 V0.3 架构线上的补充重构版本。

本阶段不扩大产品能力边界，而是完成 V0.2/V0.3 大规模架构迁移后仍未收口的内部模型、进程生命周期、IPC、配置所有权和数据迁移问题。

V0.33 的核心原则是：

> 不继续增加架构层，而是减少兼容层、减少状态所有者、减少隐式生命周期，并让已有四进程架构在失败场景下能够确定地终止、恢复或报告状态。

V0.33 完成后，WinPool 应从“已经形成正确架构，但仍保留迁移兼容层”进入“内部模型单一、进程生命周期封闭、失败路径可测试”的状态。

V0.33 是项目版本，不自动创建 Git tag、GitHub Release 或二进制正式发布。

# 2. 本阶段目标

## G-01：彻底消除双领域模型

V0.33 完成时：

* `WinPool.Core` 项目从 solution 删除；
* 仓库不存在 `using WinPool.Core`；
* 仓库不存在以 `WinPool.Core.*` 为运行时依赖的兼容代码；
* `ExecutionMode`、`PrivilegeState`、Preferences、StorageLocationMode 等概念只保留一个权威定义；
* 旧 `StorageSnapshot`、`StorageSystemDocument`、`StorageUnitRef`、`TopologyNode`、`WorkspaceSelection` 不作为第二套领域模型继续存在；
* App、Simulation、Inventory、Manage 使用同一套新的对象身份和 inventory/document 模型；
* `LegacyManage*Projector` 和 `LegacySimulationEditCoordinator` 不再作为正常运行路径。

## G-02：关闭本轮代码审查发现的全部 P1/P2 缺陷

必须关闭以下问题：

1. incomplete shutdown 将 Agent 永久锁死在 `ShuttingDown`；
2. TestWorker 返回 Completed 后不退出导致 Agent 无限等待；
3. ElevatedBroker 返回结果后不退出导致 Agent 无限等待；
4. TestWorker 在 tool process 启动前存在取消死区；
5. malformed control connection 可终止整个 Agent control server；
6. portable mode 下 App/Agent 使用不同 `tool-paths.json`；
7. `ToolOutputEncoding` 契约未在解析链真正生效；
8. PID tombstone 导致 PID reuse 后无法注册新进程，同时 live registry 无限增长；
9. Storage migration 会把旧 target 内容与 source 静默合并；
10. Agent event pipe 断开后客户端静默永久停止接收事件。

任何一项不得通过“记录为 debt”完成 V0.33。

## G-03：强化 Agent 生命周期模型

所有 Agent 管理的进程必须具有：

* 明确身份；
* 明确开始状态；
* 明确 terminal 状态；
* 明确 timeout；
* 明确 cancellation；
* 明确 kill fallback；
* 明确持久化证据；
* 明确 shutdown 行为。

任何子进程都不能依靠无限 `WaitForExitAsync(CancellationToken.None)` 完成生命周期。

## G-04：统一正常运行时的数据与配置所有权

正常模式：

* App 不直接修改 Agent-owned persistent configuration；
* Agent 是 SQLite 和共享工具配置的正常写入 owner；
* portable/standard mode 不产生两个活动配置副本；
* 数据位置切换必须产生目标根的精确副本，而不是 merge。

开发 fallback 可以保留，但必须明确标记为 no-Agent development path，不能与正常路径共享模糊所有权。

## G-05：适度拆分 Agent 内部超级 Runtime

不增加新的项目。

只把 `DesktopAgentRuntime` 中最重的三个独立状态域拆成内部 coordinator：

* Test；
* System Support；
* Inventory。

`DesktopAgentRuntime` 最终主要承担：

* `IAgentRequestOperations` facade；
* shutdown adapter；
* 各 coordinator 的请求路由；
* 少量跨域 snapshot 聚合。

不把每个 request 拆成独立 handler，不引入 MediatR、service bus、actor framework、通用 command framework 或额外 DI 容器。

# 5. 权威模型划分

## 5.1 Domain

`WinPool.Domain` 只拥有真正跨 use-case 的纯模型：

* `SystemId`
* `EnvironmentId`
* `StorageObjectId`
* `StorageObjectKind`
* `OperationId`
* `SessionId`
* `ExecutionMode`
* `PrivilegeState`
* Preferences
* StorageLocationMode
* 纯 storage math
* 纯 identity / algorithm confidence 规则

Domain 不接收旧 `StorageSnapshot` 整体迁入。

## 5.2 Application

Application 是应用内部的权威 use-case 数据语言：

* `InventorySnapshot`
* `StorageObjectView`
* `StorageRelationshipView`
* Manage projections
* Workspace state
* Simulation edit contracts
* Agent request/response
* process coordination contracts
* Tool contracts
* Monitoring contracts
* Testing contracts

如果 App 仍需要一个“当前存储系统文档”聚合，应在 Application 定义唯一的 typed document，以：

```text
Document identity
Source kind
Display name
InventorySnapshot
Revision
UpdatedAt
```

为核心。

旧 Core `StorageSystemDocument` 不得直接移动到 Domain。

## 5.3 Execution

只处理：

* plan；
* authorization；
* risk；
* precondition；
* simulation execution；
* deny-by-default policy；
* replay/evidence。

## 5.4 App

App 只保留 presentation-specific 内容：

* Observable UI state；
* notification presentation；
* startup argument parsing；
* UI layout calculation；
* localization；
* file/folder picker；
* WinUI-specific adapters。

## 5.5 Infrastructure

Windows/SQLite 实现只能将平台数据映射到 Application/Domain 权威模型。

不得重新定义另一套等价业务模型。

# 9. V33-02：重做 Agent shutdown 状态机

## 9.1 新状态

建议将：

```text
Running
ShuttingDown
Stopped
```

改为：

```text
Running
    ↓
ShuttingDown
    ├── complete ─────────→ Stopped
    └── incomplete ───────→ ShutdownPending
                                │
                                ├── retry
                                └── final cleanup
                                     ↓
                                   Stopped
```

## 9.2 ShutdownPending 语义

`ShutdownPending` 表示：

* Agent 已经开始关闭；
* 部分 capability 可能已停止；
* 不得恢复普通业务请求；
* 但必须允许观察和恢复关闭流程。

允许的请求至少包括：

```text
GetAgentSnapshot
GetDevelopmentDiagnostics
RequestAgentShutdown
```

禁止：

```text
StartTest
StartMonitoring
SaveSimulation
InstallTool
其他新业务操作
```

## 9.3 重试

第二次 shutdown 不得因为：

```text
state != Running
```

直接拒绝。

应继续完成：

* 失败步骤；
* 尚未完成步骤；
* 因 live child process 被延后的最后退出步骤。

不要简单恢复为 `Running`，因为之前的 shutdown 可能已经停止 monitoring 或 flush/close 部分资源。

## 9.4 Tray 行为

Tray 显示 `Shutdown incomplete` 后，再次 Exit 必须确实可以继续 shutdown。

UI 状态和 Coordinator 状态不得分裂。

## 必须新增测试

```text
IncompleteShutdownTransitionsToShutdownPending
ShutdownPendingRejectsNewBusinessRequests
ShutdownPendingAllowsSnapshot
ShutdownPendingAllowsShutdownRetry
RetryCompletesAfterChildProcessExits
TrayRetryDoesNotTargetDeadCoordinatorState
StorageLocationShutdownCanRetryAfterTransientFailure
```

# 10. V33-03：统一 Worker/Broker 子进程生命周期

## 10.1 禁止 terminal response 后无限 WaitForExit

以下模式禁止：

```csharp
await process.WaitForExitAsync(CancellationToken.None);
```

如果它位于已收到 Worker/Broker terminal response 后。

统一规则：

```text
terminal IPC response
↓
short exit grace
↓
process exits?
 ├─ yes → normal completion
 └─ no  → kill process tree
           ↓
         bounded WaitForExit
```

建议建立一个 Agent 内部的非常小的：

```text
ChildProcessExitPolicy
```

只负责：

* grace deadline；
* kill fallback；
* final exit wait；
* exit outcome。

不要做成通用 process framework。

## 10.2 TestWorker

覆盖：

* normal completion；
* cancellation；
* malformed Worker response；
* Worker crash；
* Worker Completed-but-hangs；
* Worker Failed-but-hangs；
* output limit failure；
* Agent shutdown。

## 10.3 Broker

覆盖：

* UAC cancel；
* handshake timeout；
* execution timeout；
* Completed-but-hangs；
* Rejected-but-hangs；
* Broker crash；
* Agent cancellation。

45 秒 execution deadline 必须覆盖 Broker **整个生命周期**，不能只覆盖 IPC request/response。

## 必须新增 fault helper

测试辅助 Worker/Broker 必须能够按参数执行：

```text
--hang-before-start
--complete-then-hang
--reject-then-hang
--exit-without-terminal-message
--malformed-terminal-message
```

正式发布不得包含这些 test helper。

# 11. V33-04：关闭 TestWorker pre-start cancellation dead zone

当前取消不能依赖：

```text
tool.process.started
```

才能生效。

建立两个明确阶段：

```text
Worker started
↓
Authenticated
↓
Start command sent
↓
Tool process started
```

### Tool 尚未启动

收到取消时：

1. 向 Worker 发送 typed cancel/abort；
2. 等待短 grace；
3. Worker 不响应则直接终止 Worker process tree。

### Tool 已启动

1. 发送 typed `CancelToolProcessCommand`；
2. Worker 请求 graceful termination；
3. 超时后 Job Object kill；
4. 返回 cancellation audit。

任何阶段都不得因为：

```text
ReadAsync(... CancellationToken.None)
```

而使 caller cancellation 永久失效。

## 测试

```text
CancelBeforeWorkerConnect
CancelAfterHandshakeBeforeToolStart
CancelWhileWorkerPreparingTool
CancelAfterToolStarted
CancelWhileWorkerStopsResponding
```

# 12. V33-05：Agent control IPC fault containment

Control server 的基本原则改为：

```text
one bad client connection != dead Agent server
```

Accept loop：

```text
while Agent is serving:
    create pipe
    wait connection
    try
        authenticate
        serve
    catch expected per-connection protocol/io/auth failure
        record diagnostic
        dispose connection
        continue accepting
```

只有以下情况可以结束主 server loop：

* Agent shutdown token；
* server 自身无法继续创建/监听 pipe；
* 明确不可恢复平台错误。

必须隔离：

* invalid frame length；
* malformed JSON；
* wrong message type；
* invalid handshake；
* EOF in handshake；
* client disconnect；
* unsupported request payload。

## 测试

```text
MalformedHandshakeDoesNotStopControlServer
OversizedFrameDoesNotStopControlServer
TruncatedFrameDoesNotStopControlServer
DisconnectedClientDoesNotStopControlServer
ValidClientCanConnectAfterMalformedClient
```

# 13. V33-06：Event IPC 显式断线与自动恢复

目标不是在 V0.33 建立 durable event bus。

目标是解决：

```text
event stream dead
→ WatchAsync 永久等待
→ App 不知道
```

## 13.1 客户端状态

Event reader 退出必须产生明确 transport state：

```text
Connected
EventStreamDisconnected
Reconnecting
Reconnected
```

可以采用本地 client event，不要求进入 Agent wire contract。

## 13.2 自动恢复

Event pipe 断开时：

1. 标记 event stream unavailable；
2. 不静默终止 public watch channel；
3. 在 event reader task 外启动恢复；
4. 重新建立完整 Agent connection；
5. 建立新的 event endpoint；
6. 获取 Agent snapshot；
7. 用 snapshot 重新 seed App 可恢复状态；
8. 发布明确的 event-gap/reconnected indication。

必须避免：

```text
eventReaderTask
→ ReconnectAsync
→ DisposeStreamAsync
→ await eventReaderTask
```

形成 self-await deadlock。

## 13.3 明确不做

V0.33 不实现 durable replay。

如果断线期间丢事件：

```text
必须报告 gap
不能假装完整
```

后续 DEBT-11 再考虑 sequence/replay。

## 测试

```text
EventDisconnectIsObservable
EventDisconnectDoesNotSilentlyEndWatch
EventStreamReconnects
ReconnectDoesNotDeadlockEventReader
ConcurrentRequestAndEventReconnectAreSerializedSafely
SnapshotReseedsStateAfterReconnect
EventGapIsExplicit
```

# 14. V33-07：进程身份从 PID 升级为 process incarnation

PID 只用于 OS 查询，不再作为 Agent 的永久 identity。

增加：

```text
ProcessInstanceId
```

建议为 Guid。

进程注册模型：

```text
ProcessInstanceId
ProcessId
Kind
CorrelationId
StartedAtUtc
LastHeartbeatUtc
State
OwnsJobObject
ShutdownDeadlineUtc
```

## 14.1 Registry

live registry 使用：

```text
Dictionary<ProcessInstanceId, AgentManagedProcess>
```

同时维护：

```text
PID → live ProcessInstanceId
```

PID 索引只允许一个活跃 incarnation。

进程进入：

```text
Exited
Failed
```

后：

* 从 live PID index 删除；
* 从 live registry 删除或移入有上限的近期诊断缓存；
* 不允许 live snapshot 无限积累历史 tombstone。

## 14.2 SQLite

将数据库升级到下一 schema revision。

`worker_processes` 不再使用 `process_id` 作为唯一历史身份。

建议：

```text
process_instance_id TEXT PRIMARY KEY
process_id INTEGER NOT NULL
agent_session_id TEXT NOT NULL
...
```

为：

```text
agent_session_id
process_id
started_at
```

建立查询索引。

旧数据迁移：

* 保留历史行；
* 为旧行生成唯一 process instance ID；
* 不因为 PID 重复覆盖旧 evidence。

## 测试

```text
CorrelationId
```

Agent 负责：

1. ToolId 必须登记；
2. path 必须 fully-qualified；
3. filename 必须属于该 ToolDescriptor；
4. 写入当前 active data root；
5. 重新 detect；
6. persistence；
7. 返回新的 `ToolState`。

App 选择文件后：

```text
picker
→ Agent request
→ ToolState response
```

而不是：

```text
picker
→ App writes JSON
→ Agent independently reads another JSON
```

## 15.2 no-Agent developer fallback

只有明确的 no-Agent development mode 可以直接使用：

```text
StorageDataLocations.CurrentRoot/tool-paths.json
```

不得硬编码 `%LocalAppData%\WinPool`。

# 16. V33-09：落实 ToolOutputEncoding

原始输出仍应作为 evidence 保存，不能为了方便 parser 把所有原始 bytes 改写掉。

正确链路：

```text
external process bytes
        │
        ├── raw evidence remains raw
        │
        └── parser receives bytes + explicit ToolOutputEncoding
```

`ToolProcessStreams` 或等价 parser input 必须携带：

```text
ToolOutputEncoding
```

明确支持：

* UTF-8；
* UTF-16 LE；
* Windows ANSI；
* Windows OEM。

禁止：

```text
no BOM => UTF-8
```

这种隐式策略覆盖所有工具。

RoboCopy 使用其声明的 OEM semantics。

## 测试

使用固定 byte fixture，不依赖测试机控制台语言：

```text

```

# 17. V33-10：Storage migration 改成精确目标事务

迁移完成后的 invariant：

```text
Target managed payload
==
Source manifest
```

不允许：

```text
target = source + historical extras
```

## 17.1 推荐事务

### Phase A：Plan

继续生成：

* source manifest；
* file count；
* total bytes；
* per-file hash；
* manifest hash。

同时捕获 target 当前状态。

### Phase B：Stage

在 target 的 sibling 路径建立：

```text
.winpool-migration-stage-{guid}
```

把 source 完整复制到 staging。

验证：

* path；
* size；
* SHA-256；
* SQLite logical identity；
* reparse policy。

此时 active target 尚未修改。

### Phase C：Quiesce

停止所有写入并 flush。

再次 snapshot source。

如果 source 改变：

```text
plan stale
→ abort
```

### Phase D：Replace target payload

建立 sibling rollback：

```text
.winpool-migration-rollback-{guid}
```

对于目标根中的 WinPool-managed payload：

1. `storage-location.json` 仍由 location manager 独立管理；
2. 旧 target payload 移入 rollback；
3. staged payload 移入 target；
4. 对 target 重新计算 manifest；
5. target manifest 必须与 source 完全一致；
6. 不允许普通 stale file 留在目标根。

### Phase E：Commit pointer

只有 target 完整验证后才 atomic commit：

```text
storage-location.json
```

### Phase F：Cleanup

pointer commit 成功后：

* rollback 可以删除；
* source 按现有策略继续保留；
* cleanup 失败只记录 cleanup warning，不能把已成功 commit 的迁移伪装成未发生。

## 17.2 失败回滚

pointer commit 前任何失败：

```text
restore old target payload
remove stage
remove partial replacement
keep old pointer
```

旧 active root 必须继续有效。


# 22. IPC 版本策略

V0.3 没有冻结 wire compatibility。

如果 V0.33 修改：

* `ProcessRegistration` wire shape；
* event transport semantics；
* handshake-required fields；

```text

```

不要建立：


App、Agent、Worker、Broker 作为同一产品 staging 必须使用匹配协议。

# 23. SQLite 策略

只有 process identity 修复需要 schema 变化时才升级 schema。

* 不依赖“直接创建最新 schema”测试来替代 upgrade test。

# 31. V0.33 完成后的理想状态

V0.33 后的 WinPool 不应再被描述为：

> 一个旧 WinUI Core 模型外面包了一套新的 Domain/Application/Agent 架构。

而应该是：

```text
Domain
  ↓
Application
  ↓
Execution / Inventory / Testing / Monitoring
  ↓
Agent
  ↓
Worker / Broker / Infrastructure

App
  ↓
Application projections + Agent client
```

旧模型已经消失。

Agent 仍然是复杂的 orchestration process，但复杂度按 Test、System Support、Inventory 三个真实状态域划分，而不是继续集中在一个超级 Runtime。

任何正常业务状态都有一个明确 owner。

任何子进程都有一个确定 terminal path。

任何 IPC 故障都有明确可观察结果。

任何存储位置迁移都有精确数据语义。

任何共享配置都只有一个正常写入 owner。

这就是 V0.33 的完成标准。
