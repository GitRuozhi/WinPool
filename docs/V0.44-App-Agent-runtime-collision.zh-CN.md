## V0.44 计划当时的假设

V0.44 计划把 App/Agent 运行时重复当作主要结构性体积问题。它预期会有大量
**内容完全相同** 的 self-contained 文件：

- 继续保持两个进程：`WinPool.App.exe` 和 `WinPool.Agent.exe`
- 每个进程保留自己的 apphost、`.deps.json`、`.runtimeconfig.json`
- 字节完全相同的公共文件只存一份
- 同名但字节不同则 staging 合并失败
- 禁止 last-writer-wins
- 不得合进程、不得删除 WinForms、不得靠 trimming 强迫变瘦

这个假设没有错。合并时确实发现了大量相同文件。停下来是因为有一小撮同名文件
**并不相同**。

## 为什么一个产品会打出两份同名文件

WinPool 对外是一个 portable 目录，但 restore/publish 仍然生成 **两套
self-contained 闭包**：

```text
WinPool.App.exe
    WinUI、Microsoft.NETCore.App、Windows App SDK

WinPool.Agent.exe
    WinForms、Microsoft.NETCore.App、Microsoft.WindowsDesktop.App
```

每次 `dotnet publish` 只复制 **该进程** 需要的框架文件。两套共享框架都会安装
一些历史文件名（`System.Drawing.dll`、`Microsoft.VisualBasic.dll` 等）。名字一样，
载荷不一样：

- App 常常拿到小的兼容/门面程序集
- Agent 常常拿到 WinForms 要加载的完整 Windows Desktop 实现

这不是 WinPool 工程同时引用了同一 NuGet 包的两个版本，而是两个可执行文件、两套
框架包、同一个输出文件名。

单进程应用会在编译期必须选出一份。双进程、两次 publish 把冲突推迟到两个输出
目录合并时才出现。

## V0.44 做了和没做的

做了：

- 保持双进程
- 保持 WinForms 托盘
- 保持 `PublishTrimmed=false`
- 扁平合并失败
- 保留 `WinPool.App.exe` + `Agent\WinPool.Agent.exe`

没做：

- 覆盖这五个文件
- 把 App 和 Agent 合成一个进程
- 删除 WinForms
- 启用 trimming
- 改图片

V0.44 在其余瘦身之后的 portable staging：779 个文件，338.40 MiB；V0.43 基线为
853 个文件 / 380.44 MiB。那 207 个相同文件 / 约 81 MiB 的重复仍留在磁盘上，因为
五个冲突挡住了单一共享目录。

## 本次分析的未决问题

这些是问题，不是决定：

1. Agent 的五份是否严格为 WinForms 托盘、EventLog 或绘图所需，App 的五份是否
   严格为 WinUI 所需？
2. 若两个进程使用不同探测路径，能否加载不同实现？混合布局（相同文件共享，冲突
   件只放进很小的 Agent 目录）是否可接受？
3. 以后替换 WinForms，是否比继续携带约 81 MiB 完全重复的 runtime 更便宜？
4. 把 Agent 改成 framework-dependent，或让 App 和 Agent 共用一个框架包，会不会
   改变这五个冲突，以及会不会打破当前 unpackaged self-contained portable 承诺？

在开发者确认后续 Plan 之前，本文档不派生任何实施。
