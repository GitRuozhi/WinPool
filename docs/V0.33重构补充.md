# V0.33 重构补充约束与验收说明

> 本文件是 `docs/V0.33重构.md` 的补充文档。
> 它不重新定义 V0.33 的整体目标，不重新编排原计划中的 M01～M10，也不以另一套阶段计划替换原计划。
> 本文件只处理评审后发现的架构未决项、实施前置条件、状态机/传输语义、编码契约、Core 迁移验收，以及 V0.33 最终版本和 Git 生命周期。
>
> 当本文件与原 V0.33 重构方案在本文明确涉及的事项上存在冲突时，应先解决本文列出的约束，不得以“先实现、再根据编译错误调整模型”的方式绕过这些前置决定。

---

## 1. 补充文档的适用范围

本补充说明覆盖以下五类问题：

1. Storage System 的权威运行时模型、document identity 和 persistence payload 边界尚未完整确定；
2. `ShutdownPending` 缺少真正可工作的 Control transport 语义；
3. `ToolOutputEncoding` 的问题需要按实际代码链重新定义，并补足 code page 和流式 decoder 设计；
4. V0.33 缺少最终版本切换、文档归档和 Git remote gate；
5. `WinPool.Core` retirement 的影响范围远大于普通项目引用迁移，原人工验收门不足。

除此之外，原 V0.33 计划中的其他目标、缺陷修复顺序和 M01～M10 默认保持不变。

---

# 2. Storage System identity 与 document 模型补充决策

## 2.1 已确认的身份决定

以下决定从现在起视为 V0.33 的已确认架构约束：

### Local → Simulation 必须产生新的 `SystemId`

当本机 Local storage system：

* 被复制为 Simulation；
* 被转换为 Simulation；
* 被用作 Simulation 初始模板；
* 被导出后重新导入为一个新的可编辑 Simulation；

新的 Simulation 必须获得一个新的 `SystemId`。

Local 与 Simulation 不因为来源关系而共享同一个 `SystemId`。

因此：

```text
Local SystemId
    │
    └── clone / convert / create simulation from local
            │
            └── New Simulation SystemId
```

来源关系可以通过独立 provenance metadata 表达，但不能通过复用 `SystemId` 表达。

### 直接影响

因此以下状态不能从 Local 原样继承给新 Simulation：

* workspace remembered selection；
* selected object identity；
* highlighted topology object identity；
* monitoring identity；
* Local inventory version；
* Local runtime lifecycle state。

如果需要把某个 Local object 映射到 Simulation 中对应的新对象，必须显式建立 clone/import mapping，而不能依赖两个系统具有相同 `SystemId`。

---

## 2.2 必须区分的五种语义

V0.33 不得继续把以下概念隐式合并：

### `SystemId`

逻辑 Storage System 的 identity namespace。

所有 `StorageObjectId` 都属于某个 `SystemId`。

Local 与从它创建的 Simulation 使用不同 `SystemId`。

### Document identity

仅表示某个可持久化 document/artifact 本身的身份。

Document identity 不等于 `SystemId`，也不得继续仅因为实现方便就由 document identifier 隐式派生全部 system identity。

### Revision

Revision 表示**可编辑 document 的并发版本**。

它主要服务于：

* optimistic concurrency；
* save conflict；
* edit commit；
* reload；
* history/evidence。

不得为了让 Local 与 Simulation 字段形式一致，就给不可编辑 Local inventory 人为制造同类 revision。

### Inventory Version

Inventory Version 表示某个 Storage System state/snapshot 的版本。

它属于 inventory/state 语义，而不是 persistence document revision。

以下两个条件可以同时成立：

```text
Document Revision = 8
Inventory Version = X
```

二者不是同一个计数器。

### Source Kind

`Local`、`Simulation`、`Import`、`Replay` 等 source kind 用于表达来源和行为能力。

Source Kind 不参与 identity equality。

# 3. 权威运行时 document 模型：实施前必须先关闭的设计门

## 3.1 V0.33 不再预设必须存在一个统一 `Application.StorageSystemDocument`

原计划中任何类似：

```text
InventorySnapshot
    ↓
Application.StorageSystemDocument
    ↓
Manage Projection
```

的强制目标链，在本补充文档生效后不得直接视为既定实现。

在开始相关 Core migration 前，必须先明确是否真的存在需要 Application-level aggregate document 的不变量。

不得因为：

* Manage UI 需要统一显示；
* Local 和 Simulation 都代表 Storage System；
* 两者拥有类似 topology；

就推导出二者必须共享同一个 mutable runtime document。

---

## 3.2 当前默认架构方向

除非后续通过明确设计评审证明统一 aggregate 有必要，V0.33 默认采用：

```text
共享 identity / storage object language
但不强制共享同一个 document lifecycle
```

即：

### Local

以 inventory/capture lifecycle 为主：

```text
Windows inventory
    ↓
InventorySnapshot / typed inventory state
    ↓
Application query / Manage projection
```

Local system 是：

* read-only；
* capture based；
* replace/update snapshot；
* 可比较；
* 不承担 Simulation edit revision lifecycle。

### Simulation

以 editable document lifecycle 为主：

```text
Persisted simulation payload
    ↓
Typed simulation runtime state
    ↓
Edit
    ↓
New revision
    ↓
Persist
```

Simulation system 是：

* editable；
* revisioned；
* conflict checked；
* reloadable；
* 可产生 operation/evidence history。

### App

App 可以消费统一的：

* `SystemId`；
* storage object identity；
* source kind；
* Manage/query projection；

但这不意味着 App 必须持有一个统一 mutable Storage System document。

现有 `StorageSystemView` 或其 V0.33 后继 read model 可以继续承担“统一读取视图”的职责。

---

## 3.3 在实现前必须明确记录的内容

开始删除 Legacy `StorageSystemDocument` 依赖之前，必须在 V0.33 执行记录中写明：

* 是否最终需要 Application aggregate document；
* 如果需要，其准确类型名；
* 类型全部字段；
* 哪些字段参与 identity；
* 哪些字段参与 equality；
* revision 的拥有者；
* source kind 的语义；
* Local 与 Simulation 是否使用同一 runtime 类型；
* persistence payload 与 runtime object 的转换位置；
* import/replay 是否使用 Simulation document，还是独立 document 类型；
* clone Local → Simulation 时如何产生新 `SystemId` 和 object identity mapping。

上述内容未关闭前：

**不得创建一个临时 `Application.StorageSystemDocument` 再通过编译错误逐步决定它应该包含什么。**

# 4. Persistence payload 与 runtime object 边界

V0.33 必须明确区分：

```text
Runtime typed object
Persistence/IPC payload
SQLite representation
```

推荐边界为：

```text
typed runtime state
    ↕ explicit mapper / serializer
payload
    ↕ repository
SQLite
```

`SanitizedJson`、SHA-256、schema version 等字段属于：

* persistence；
* transport；
* integrity；
* redaction；

边界的一部分。

它们不得反过来成为 Application/runtime storage model 的事实来源。

特别禁止出现：

```text
UI / business logic
    ↓
直接读取 SanitizedJson 判断 topology
```

如果 payload schema 与 runtime schema 不完全一致，必须通过显式 mapper/codec 转换。

---

# 5. `ShutdownPending` 必须具有完整 Control transport 语义

## 5.1 状态机

V0.33 至少明确以下 lifecycle state：

```text
Running
   ↓
ShuttingDown
   ↓
   ├── Stopped
   │
   └── ShutdownPending
           ↓ retry
        ShuttingDown
           ↓
        Stopped / ShutdownPending
```

### `ShuttingDown`

表示一个 shutdown workflow 当前正在执行。

### `ShutdownPending`

表示最近一次 shutdown workflow 已经结束，但仍有阻止 Agent 最终退出的条件，例如：

* supervised process 尚存活；
* temporary system state 未恢复；
* terminal cleanup 未成功。

`ShutdownPending` 不是 terminal state。

---

# 6. Control listener 生命周期不得再与 `Running` 状态绑定

Control transport 的生命周期必须与业务 lifecycle state 分开。

最低要求：

### `Running`

正常 Control request 可用。

### `ShuttingDown`

Control listener 继续存在。

不得启动第二个并发 shutdown workflow。

shutdown/status 类请求应：

* 返回当前 shutdown operation 状态；
* 或 join/observe 当前 shutdown；
* 但不能启动并发清理过程。

### `ShutdownPending`

Control listener 必须继续存在。

至少允许：

* Agent snapshot/status；
* shutdown status；
* shutdown retry。

其他会重新启动正常业务的 request 默认拒绝。

### `Stopped`

此时才允许 Control listener 完全关闭。

---

# 7. Shutdown workflow 中 `CloseNamedPipes` 的位置必须重新定义

当前 shutdown 顺序不能在确认 Agent 可以真正 terminal exit 之前关闭用于恢复和 retry 的 Control pipe。

V0.33 必须区分：

```text
quiesce phase
terminal exit phase
```

## Quiesce phase

可以包括：

* notify clients；
* request test cancellation；
* terminate external tool jobs；
* stop monitoring；
* restore temporary system state；
* flush SQLite；
* stop/close main App；
* stop supervised processes。

如果 quiesce 后仍有 blocker：

```text
→ ShutdownPending
```

此时 Control transport 仍然必须工作。

## Terminal exit phase

只有在确认：

* required temporary state 已恢复；
* required queues 已 flush；
* 没有必须继续监督的 live process；
* 没有其他 terminal blocker；

之后，才进入：

* close remaining IPC；
* remove tray；
* exit Agent。

不得再次产生：

```text
进入 ShutdownPending
但 retry 所需 pipe 已被上一轮 shutdown 关闭
```

的状态。

---

# 8. Shutdown retry 的并发语义

必须保证同一时间最多存在一个真实 shutdown workflow。

推荐使用明确的 shutdown operation/gate。

行为要求：

### `Running + ShutdownRequest`

启动新的 shutdown operation。

### `ShuttingDown + ShutdownRequest`

不得启动第二个 workflow。

返回：

* 当前 operation id；
* 当前 lifecycle state；
* 当前 progress/status；

或等待当前 operation 的确定结果。

### `ShutdownPending + ShutdownRequest`

允许启动 retry。

retry 可以重新运行具有幂等性的 cleanup step，但不得：

* 重复执行不可安全重复的 mutation；
* 丢失上一轮 failed/remaining evidence；
* 因重复 cleanup 导致新资源泄漏。

---

# 9. Shutdown snapshot/status 最低字段

为了使 Pending 状态可以被 UI 和测试正确判断，snapshot/status 至少应能表达：

* lifecycle state；
* current/last shutdown operation id；
* shutdown reason；
* completed steps；
* failed steps；
* remaining supervised process identities；
* temporary state restoration result；
* SQLite flush result；
* 是否允许 retry；
* 最后状态更新时间。

是否实现 supervised process 自动退出后的自动 finalization，可以单独决定。

但 V0.33 的**最低完成标准**是：

> 当 blocker 消失后，新的 shutdown retry 必须能够通过仍然工作的 Control transport 完成最终退出。

---

# 10. `ToolOutputEncoding` 缺陷的正确问题定义

V0.33 不再把此问题描述为：

> `ToolOutputEncoding` 没有传到 parser。

正确描述应为：

> External tool output 当前存在至少两条解码路径。Native progress 路径已经收到 `ToolOutputEncoding` family，但 ANSI/OEM 等值仍按 UTF-8 处理；final structured parsing 路径则没有使用与 invocation 相同的完整 encoding resolution，主要依赖 BOM/UTF-8 推断。因此两条路径的 encoding contract 不完整且不一致。

---

# 11. Encoding family 与 concrete code page

`ToolOutputEncoding` 中的：

```text
Utf8
Utf16LittleEndian
SystemAnsi
Oem
```

表示 encoding family / policy。

其中 `SystemAnsi` 和 `Oem` 本身不足以成为可重现的最终编码身份。

Worker 在真正准备运行 external tool 时，应解析出本次运行使用的 concrete encoding，例如：

```text
Family: Oem
CodePage: <resolved numeric code page>
```

或者等价的强类型结构。

此 resolved encoding 应在同一次 run 中保持固定。

不得在：

* progress parser；
* final parser；
* evidence exporter；

三个位置分别重新读取当前机器 locale/code page 并自行推断。

---

# 12. 测试必须支持固定 code page 注入

Encoding 单元测试不得依赖测试机当前：

* Windows display language；
* ANSI code page；
* OEM code page；
* console code page。

必须提供可注入的 encoding/code-page resolver。

测试 fixture 直接声明：

```text
encoding family
resolved code page
raw bytes
expected text / metrics
```

因此相同测试应在不同系统语言上得到同样结果。

如 .NET 运行时需要注册额外 code-page provider，应在固定的 infrastructure/test boundary 完成，不应散落在 adapter 中。

---

# 13. 必须使用有状态 `Decoder`

External tool stdout/stderr 是 byte stream，不是互相独立的完整字符串 chunk。

因此不得继续假设：

```text
1 Worker event == 1 complete text character sequence
```

每个 output stream 必须持有自己的 stateful decoder：

```text
stdout → Decoder A
stderr → Decoder B
```

同一个 decoder 持续接收多个 chunk。

EOF 时执行 final flush。

---

# 14. 必须增加 chunk-boundary regression

至少覆盖：

* UTF-8 多字节字符跨 chunk；
* UTF-16 code unit / surrogate 边界；
* ANSI/OEM DBCS 字符跨 chunk；
* 中文本地化 RoboCopy 文本；
* stdout 与 stderr 交错；
* stdout 和 stderr 同时存在各自未完成字符；
* 最后一个 chunk 在 EOF 时才完成字符；
* invalid byte sequence 的确定 fallback 行为。

特别应构造类似：

```text
chunk 1: character byte prefix
chunk 2: remaining bytes
```

的 fixture。

如果最终 parser 的结果与把完整原始 bytes 一次性解码得到的结果不同，则测试必须失败。

---

# 15. Progress 与 final parser 必须使用同一次 encoding resolution

禁止形成：

```text
progress: OEM code page 936
final: UTF-8 fallback
```

这样的双重语义。

Worker/Agent 应保留本次 tool invocation 的 resolved encoding metadata，并使：

* live progress；
* final structured parser；
* human-readable evidence；

使用相同的 encoding resolution。

原始 stdout/stderr bytes 仍应作为原始 evidence 保存。

解析后的字符串不能替代 raw evidence。

---

# 16. V0.33 Core retirement 必须成为独立 Acceptance Class

删除 `WinPool.Core` 不应只以：

```text

tests pass

```

作为完成依据。

Core retirement 必须拥有单独的：

```text

```

# 17. Manage semantic parity gate

在删除 Legacy projector 前，应尽可能使用同一组固定 storage fixtures 对比 Legacy 与新实现的结构化输出。

至少比较：

* system identity；
* object identity；
* parent/child relationship；
* topology；
* category；
* ordering；
* display name；
* selectability；
* navigation target；
* details fields；
* comparison rows；

不要求新旧内部类型完全相同。

要求的是用户可见 storage semantics 保持一致，除非原计划明确要求行为改变。

# 23. Core retirement 最终结构门

只有同时满足以下条件时，才能宣称 Core retirement 完成：

* production project 不再引用 `WinPool.Core`；
* test project 不再依赖 Legacy Core model，除非测试正在验证明确的迁移兼容 fixture；
* `WorkspaceViewModel` 等 production UI 不再直接依赖 Legacy Core projector/model；
* Legacy Manage projector replacement 已完成；
* Legacy Simulation coordinator replacement 已完成；
* startup/preferences/layout 所属层已经明确；
* solution 中不再需要 `WinPool.Core` project；
* architecture tests 已更新并验证新的 ownership；
* automatic semantic parity gate 完成；
* required native/manual gate 有真实结果。

未实际执行的人工项继续记录：

```text
unverified
```

不得因为 automatic tests 通过而写成 passed。

# 27. 与原 M01～M10 的关系

本补充文档不修改原 M01～M10 编号。

执行时采用“附加 gate”方式：

### 在开始 Storage/Core model 大规模迁移前

必须关闭：

**V33-SUP-A — Storage identity/document model gate**

包括：

* Local → Simulation 新 `SystemId` 已确认；

# 28. 执行停止条件

以下任一情况出现时，不允许继续通过“先改代码再看测试”推进：

* Simulation runtime document 类型仍未确定；
* `SystemId` 与 document identity 又被实现为同义字段；
* Local 与 Simulation 被迫共享 mutable revision lifecycle；
* `ShutdownPending` 后 Control pipe 不可连接；
* shutdown retry 会启动两个并发 workflow；
* ANSI/OEM 仍依赖测试机器当前 locale 才能通过测试；
* stdout/stderr 仍按独立 chunk 无状态解码；
* Core project 已删除但 Manage/Simulation 行为尚未有 parity evidence；
* V0.33 version metadata 和文档显示不一致；
* 未获授权却准备 push/tag/release。

出现上述情况应返回设计/实现阶段修正，而不是降低 gate。

# 29. V0.33 补充完成判定

本补充文档本身不代表 V0.33 完成。

V0.33 只有在：

```text
原 V0.33 计划完成条件
+
V33-SUP-A
+
V33-SUP-B
+
V33-SUP-C
+
V33-SUP-D
+
V33-SUP-E
```

全部满足其应有状态后，才具备版本评审条件。

其中 human/native gate 如未执行，应如实记录 `unverified`；是否仍接受该版本，由用户最终决定。

自动验证、静态分析或代码审查不得替用户完成任何 human/native evidence。
