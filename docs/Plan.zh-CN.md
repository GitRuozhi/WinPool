## 1. 已确认决定

这些决定约束本阶段，优先于现有编辑页布局实现。

### 1.1 唯一拓扑布局引擎

WinPool 只有一个拓扑布局引擎：

`TopologyLayoutEngine`

管理页、编辑页上半区、编辑页下半区都使用该引擎完成拓扑测量、行生成、
最小宽度计算、可用宽度处理、子项宽度分配和最终布局规划。

三个区域可以提供不同的拓扑树和少量布局或呈现选项，但不得拥有独立的布局算法。

特别地：

- 管理页保持行为与视觉基准。
- 编辑页上半区是受限的磁盘/分区投影。
- 编辑页下半区是受限的池投影。
- `AdaptiveFlowPanel`、`WeightedPoolPanel` 或替代面板可以作为 WinUI
  measure/arrange 适配器保留，但不得实现相互竞争的布局算法。
- 等分填充、加权填充、容量填充、换行和最小宽度规则归 `TopologyLayoutEngine` 所有。
- 面板只消费引擎结果，做机械性的 WinUI 测量与排列。
- 不得引入第二个编辑页专用布局引擎。
- 不得在核心算法里引入页面名判断，如 `if (Manage)` 或 `if (EditUpper)`。
  所需差异必须是显式的布局输入或策略数据。

实现必须保持这三个区域所需的最小闭环。不得构建通用公共布局框架。

### 1.2 管理页是参照行为

管理页拓扑在功能和视觉上与当前管理页实现保持等价。

其投影继续按当前 `TopologyProjector` 展示完整逻辑拓扑。

管理页既有规则——系统根、池、层、物理磁盘、虚拟磁盘、分区、网络及其他分组、
Stack / Flow / WeightedFlow 关系、兄弟装包、行高放宽、拓扑选择、展开、
节点最小宽度——保持为参照行为。

本阶段可以重构产生该结果的内部实现，但不得故意重新设计管理页拓扑。

管理页布局回归测试因此是统一引擎的兼容性参照。

## 2. 编辑页下半区拓扑

### 2.1 结构

编辑页下半区拓扑在未列出编辑页专用规则的处处，使用与管理页相同的
面向池的结构和布局行为。

只显示内部池，包括原始池。

现有编辑页工作副本、拖动、模拟执行、创建、修改和解散行为不在本阶段重做。

### 2.2 原始池

原始池显示其物理磁盘。

编辑页下半区拓扑中，原始池内的物理磁盘**不**显示分区。

这只是下半区投影规则，不改变管理页投影。

概念上：

```text
Primordial
├─ Physical Disk
├─ Physical Disk
└─ Physical Disk
```

而不是：

```text
Primordial
└─ Physical Disk
   └─ Partition
```

### 2.3 已有池

非原始池保持当前下半区逻辑内容，除非本计划明确改变。

既有层、物理磁盘、虚拟磁盘和虚拟磁盘分区的表示保持可用。

本计划不改变池编辑语义或模拟操作。

### 2.4 合成加号池

合成加号池仍是下半区添加池的入口。

它：

- 视觉上是池的同位项；
- 逻辑上是合成的；
- 始终排在真实池之后；
- 因此池行装得下时是最右的池；
- 需要多行装包时排在所有真实池和草稿池之后。

概念上：

```text
Primordial | Pool A | Pool B | +
```

加号池只创建现有的本地草稿池工作状态，不创建真实存储。

### 2.5 布局

下半区使用与管理页相同的加权池布局规则，除非上述下半区规则改变了投影子项。

没有单独的下半区装包算法。

## 3. 编辑页上半区拓扑

### 3.1 只有两级

上半区拓扑只包含分区管理所需的磁盘/分区工作区。

可见逻辑层级是：

```text
Disk
└─ Partition / Unallocated
```

上半区拓扑不显示：

- 系统；
- 存储池；
- 存储层；
- 池分组；
- 直连磁盘分组；
- 虚拟磁盘分组；
- 网络分组；
- 其他拓扑分组容器。

为喂给统一引擎所需的任何不可见根节点仅用于布局，不构成可见第三级。

### 3.2 只显示合格磁盘

只投影能通过现有分区管理策略管理的磁盘。

继续使用现有可分区策略，不在页面里复制资格规则。

当前产品行为保持：

- 合格的系统盘/启动盘可以显示；
- 既有操作限制仍然生效；
- 可分区的虚拟磁盘可以显示；
- 被非原始池占用的物理磁盘不再单独显示为可分区裸盘；
- 网络映射盘不显示。

本计划不扩大允许操作的磁盘集合。

### 3.3 磁盘排列

上半区所有磁盘竖排。

概念上：

```text
Disk 0
Disk 1
Disk 2
Disk 3
```

一个磁盘不与其他磁盘共享横向行。

统一引擎应将其表示为纵向/Stack 关系，而不是依赖无关的页面专用布局算法。

### 3.4 分区排列

一个磁盘内的分区和可见未分配区按磁盘偏移顺序排成一条横向条带。

概念上：

```text
Disk 0
[Partition 1][Unallocated][Partition 2][Partition 3]
```

一个磁盘的子项不换行到第二条逻辑分区行。

当最小总宽度超过可用拓扑宽度时，行保持子项最小宽度，横向比视口更宽。
由现有拓扑滚动面处理溢出。

这保持磁盘图的空间连贯，而不是把后面的分区挪到无关的第二行。

### 3.5 未分配区域

未分配区域的既有编辑页行为保持：

- 盘头空隙是独立节点；
- 中间空隙是独立节点；
- 盘尾空隙是独立节点；
- 顺序跟随磁盘偏移；
- 既有的分区空隙忽略阈值仍决定哪些空隙可见。

可见未分配节点用该空隙的实际大小参与按容量的宽度分配。

低于配置阈值的隐藏空隙不获得可见布局槽位。

## 4. 按容量比例的分区宽度

本计划中所有宽度均为 WinUI 设备无关单位（DIP），不是物理像素。

### 4.1 最小宽度

每个可见分区或未分配子项以拓扑叶子最小宽度起步：

`112 DIP`

除非在另行批准的阶段有意更改共享引擎最小值。

本计划不更改管理页最小宽度。

### 4.2 剩余宽度分配

仅对上半区分区条带：在保留全部最小宽度和兄弟间距后，剩余宽度按每个
可见子项代表的存储大小分配。

对子项 `i`：

```text
分配宽度
    = 最小宽度
    + 剩余宽度 × 子项容量 / 可见子项总容量
```

分区和可见未分配区都用实际字节数作为容量权重。

因此该分配是空间性的，不是等分填充。

示例：

```text
分区 A = 100 GiB
分区 B = 200 GiB

最小：
A = 112 DIP
B = 112 DIP

剩余宽度 = 333 DIP

A 额外 = 333 × 100 / 300 = 111 DIP
B 额外 = 333 × 200 / 300 = 222 DIP

最终：
A = 223 DIP
B = 334 DIP
```

实现可以使用浮点布局宽度。任何最终取整必须是确定性的，最后一个子项吸收
舍入残差，使规划行宽保持一致。

### 4.3 无剩余宽度

若：

```text
可用宽度 <= 最小宽度之和 + 间距
```

不做负向比例调整。

每个子项保持至少最小宽度，必要时横向条带溢出视口。

### 4.4 比例缩放的范围

按容量比例的剩余宽度分配只适用于上半区磁盘的分区/未分配行。

它不替代管理页既有的加权拓扑规则，也不改变下半区池的加权。

统一引擎因此支持不同的额外空间分布，但所选分布作为布局输入提供，而不是
由单独的面板或引擎实现。

## 5. 上半区磁盘呈现

上半区可见磁盘节点使用紧凑横向头部，而不是标准多行拓扑卡片头。

正常磁盘卡片约三行文字的信息尽可能横向排布。

概念上：

```text
Disk 0    Samsung SSD ...    GPT    1.82 TiB
```

确切分隔符和截断是呈现细节，但结果必须：

- 保持一个紧凑磁盘头；
- 保留识别磁盘所需的信息；
- 保留辅助功能名称；
- 保留选择和交互行为；
- 长设备名只在可用宽度迫使时才修剪或换行。

该紧凑呈现只适用于上半区磁盘节点。

管理页拓扑卡片仍是参照呈现，不因本需求改变。

下半区卡片保持正常拓扑呈现，除非另行指定。

实现应为共享 `TopologyNodeControl` 增加最小的显式呈现变体，而不是创建
第二套磁盘控件树。

## 6. 实施映射

本节把已确认需求映射到当前实现，不增加产品范围。

### 6.1 Application 布局引擎

主要所有者：

`src/WinPool.Application/TopologyLayoutEngine.cs`

重构当前引擎，使其结果足以让面板完成最终排列，而不用发明另一套宽度分配算法。

引擎拥有：

- 自然子树测量；
- 叶子最小宽度；
- 祖先装饰；
- 兄弟间距；
- Stack 布局；
- Flow 布局；
- WeightedFlow 布局；
- 兄弟行生成；
- 收缩决策；
- 行高放宽；
- 最终子项宽度指派；
- 额外空间分布；
- 上半区所需的不换行横向条带行为。

既有管理页计算保持为基准。

如需要，添加最小布局输入元数据以区分：

- 既有正常额外空间分配；
- 按容量比例的额外空间分配;
- 换行与不换行的子项行。

不得把页面名写进 `TopologyLayoutEngine`。

### 6.2 布局结果

引擎结果必须携带足够信息，让 WinUI 面板知道每个子项的最终行成员关系和
最终分配宽度。

不得把最终加权或容量拉伸计算留在某个具体 WinUI 面板里。

最终结果可以在既有 `TopologyLayoutResult` 上扩展显式行槽宽度信息，或用
等价表示。

确切数据类型是实现选择；所有权边界不是。

### 6.3 WinUI 拓扑面板

当前相关控件包括：

- `AdaptiveFlowPanel`
- `WeightedPoolPanel`
- `TopologyNodeControl`

本阶段后，任何保留的布局面板都是 `TopologyLayoutEngine` 的薄适配器。

它们可以：

- 取得实际可用 WinUI 宽度；
- 把节点 ViewModel 转换为引擎输入；
- 调用引擎；
- 按引擎分配的宽度测量子项；
- 按引擎的行和槽位排列子项。

它们不得独立决定：

- 能装下多少子项；
- 等分填充还是加权填充；
- 容量比例；
- 行装包策略；
- 收缩优先级。

如果单个通用拓扑面板能干净地同时替换 `AdaptiveFlowPanel` 和
`WeightedPoolPanel`，允许替换。

本计划授权移除的确切过时候选是：

- `src/WinPool.App/Controls/AdaptiveFlowPanel.cs`
- `src/WinPool.App/Controls/WeightedPoolPanel.cs`

只有满足以下条件才可删除：

1. 通用替代已存在；
2. 全部代码引用已迁移；
3. 全部 XAML 使用点（包括 `MainPage.xaml` 和 `EditPage.xaml`）不再引用
   被移除的面板类型；
4. 管理页回归测试通过；
5. 上半区和下半区目标布局测试通过。

不为架构整洁而必须删除。若保留薄适配器是更小的闭环变更，可以保留。

### 6.4 管理页投影

主要所有者：

`src/WinPool.Application/Topology.cs`

不重新设计 `TopologyProjector.Project`。

为给统一引擎提供布局元数据所需的任何更改，必须保持管理页投影拓扑和
当前顺序不变。

### 6.5 编辑页投影

主要所有者：

`src/WinPool.Application/EditWorkspace.cs`

#### 上半区

`ProjectPartitionWorkspace` 继续负责选择可分区磁盘并构建可见磁盘、分区和
未分配节点。

更改其布局元数据，使统一引擎收到：

- 纵向磁盘集合；
- 每磁盘一条不换行的横向分区条带；
- 实际分区/空隙容量作为拉伸权重。

不得在 `EditWorkspace` 内复制布局算术。

#### 下半区

`ProjectPoolWorkspace` / `ProjectPoolWorkspaceRoot` 继续负责下半区池子集和
合成加号池。

确保：

- 原始池物理磁盘在下半区投影中没有分区子节点；
- 真实池保持既定内容；
- 加号池排在最后；
- 树使用与管理页相同的加权布局语义。

### 6.6 ViewModel 转换

`TopologyNodeViewModel` 保持共享呈现模型。

应用层布局节点到 ViewModel 的映射必须保留统一引擎所需的布局元数据。

当前 App 侧转换位于
`src/WinPool.App/Services/TopologyLayoutMapper.cs`；更新该映射以携带引擎
布局元数据属于本阶段工作。

不得为管理页/编辑页创建分开的拓扑 ViewModel 层级。

### 6.7 上半区紧凑头部

主要所有者：

- `src/WinPool.App/Controls/TopologyNodeControl.xaml`
- `src/WinPool.App/Controls/TopologyNodeControl.xaml.cs`

为上半区紧凑磁盘头添加所需的最小显式呈现模式。

同一控件继续拥有：

- 选择；
- 适用处的展开；
- 键盘交互；
- 辅助功能；
- 拖放钩子；
- 正常拓扑卡片渲染。

不得把这些行为复制进编辑页专用磁盘控件。

### 6.8 视口所有权

上半区和下半区不得覆写会影响管理页布局的单个共享全局拓扑视口宽度。

优先使用 `MeasureOverride` / `ArrangeOverride` 期间提供给 WinUI 布局面板的
实际宽度。

在 WinUI 无限宽度测量需要时可以保留回退视口状态，但每个拓扑面必须使用
自己的宿主宽度。

上半区、下半区和管理页因此不得竞争设置同一个共享 `TopologyViewportWidth`。

- Flow 行为仍符合既有管理页期望；
- WeightedFlow 行为仍符合当前管理页期望；
- 不换行横向条带不产生第二行；
- 不换行最小宽度超过视口时保持最小宽度；
- 进入或离开编辑页、或调整任一编辑半区大小，不改变管理页布局输入
  （共享视口隔离）。

### 8.2 容量分配

必需的确定性用例：

#### 用例 A

```text
容量：100 GiB、200 GiB

```

#### 用例 B

```text
100 GiB 分区
50 GiB 未分配
200 GiB 分区
```

剩余宽度按以下比例分配：

```text
100 : 50 : 200
```

#### 用例 C

无额外宽度：

所有子项保持最小宽度，行可以超出视口。

#### 用例 D

低于配置阈值的隐藏未分配空隙不获得布局槽位和可见容量份额。

## 12. 验收门槛

实现完成仅当：

- 三个拓扑区域都使用 `TopologyLayoutEngine` 作为唯一布局算法权威；
- 没有编辑页专用面板独立做等分/加权/容量填充布局决策；
- 管理页行为保持等价；
- 下半区原始池磁盘不显示分区；
- 下半区加号池是最后一个池项；
- 上半区只包含合格磁盘 → 分区/未分配拓扑；
- 上半区磁盘竖排；
- 一个磁盘内的分区形成单条不换行横向条带；
- 富余横向宽度按分区/未分配容量分配；
- 100 GiB / 200 GiB / 333 DIP 算例产出 223 DIP / 334 DIP；
- 上半区磁盘卡片使用紧凑横向呈现；
- 共享视口状态不再允许上半区/下半区缩放改变管理页布局；
- 目标自动测试 `passed`；
- 原生视觉点选在实际执行前保持 `unverified`。

实现达到该状态后，不自动开始正式验收。询问开发者是否进入正式测试。
