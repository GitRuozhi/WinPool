## 1. 已确认决定

这些决定约束本阶段，优先于现有编辑页布局实现。

### 1.0 引擎不变量

这些不变量说明引擎为什么这样设计。它们是规范性的：满足其余全部章节但
违反其中任一条的实现，即视为不满足本计划。

1. **结构决策只存在于单位层。** 行成组、列预算、收缩决策、行高放宽、
   最小单位宽（含复杂池兄弟的 2 单位下限）全部在整数 Wunit/Hunit 空间
   决定。它们是布局计划中与分辨率无关的不变量。
2. **每个表面一次根级布局。** 每个表面（管理页、编辑上半区、编辑下半区）
   每轮布局只在自身的根适配器处以该表面自己的宿主宽度调用引擎一次。
   嵌套面板绝不调用引擎，也绝不重新规划任何祖先或兄弟的预算。
3. **面板是机械消费者。** 面板获取 WinUI 提供的宽度（WinUI 无限宽测量时
   使用各表面自己的回退值）；在根处把节点 ViewModel 树转换为引擎输入；
   按引擎分配的槽位宽度执行 Measure/Arrange。面板绝不决定放得下几个
   子项、等分还是加权、容量比例、行打包或收缩优先级。
4. **像素只做拉伸。** 像素值只把已完成的单位计划像素化。任何以像素量出
   的值不得回流进单位层决策。
5. **布局纯度与幂等。** 只有确定性输入数据——静态快照数据和 WinUI 提供
   的宽度——可以进入布局。任何由度量子元素得出的值不得影响布局决策
   （度量重入是已知 `LayoutCycleException` 的触发条件）。相同输入产生
   相同输出；小于 1 DIP 的宽度变化不重新规划。

### 1.1 唯一拓扑布局引擎

WinPool 只有一个拓扑布局引擎：

`TopologyLayoutEngine`

管理页、编辑上半区、编辑下半区都使用该引擎完成拓扑测量、行生成、最小
宽度计算、可用宽度处理、子项宽度分配和最终布局规划。

三个区域可以提供不同的拓扑树和少量布局或呈现选项，但不得拥有独立的布局
算法。

特别地：

- 管理页保持行为与视觉基准。
- 编辑上半区是受限的磁盘/分区投影。
- 编辑下半区是受限的池投影。
- `AdaptiveFlowPanel`、`WeightedPoolPanel` 或替代面板可作为 WinUI
  measure/arrange 适配器保留，但不得实现相互竞争的布局算法。
- 等分、加权、容量分配、换行与最小宽度规则属于 `TopologyLayoutEngine`。
- 面板只消费引擎结果，只做机械的 WinUI 度量与排列。
- 不得引入第二个编辑页专用布局引擎。
- 不得在核心算法中引入页面名判断（如 `if (Manage)`、`if (EditUpper)`）。
  所需差异一律以显式布局输入或策略数据表达。

实现必须保持三个区域所需的最小闭环。不得构建通用公共布局框架。

### 1.2 管理页是参照行为

管理页拓扑在功能与视觉上与当前管理页实现保持等价。

其投影继续按当前 `TopologyProjector` 展示完整逻辑拓扑。

管理页现有规则：

- 系统根；
- 池；
- 层；
- 物理盘；
- 虚拟盘；
- 分区；
- 网络与其他分组；
- Stack / Flow / WeightedFlow 关系；
- 兄弟打包；
- 行高放宽；
- 拓扑选择；
- 展开；
- 最小节点宽；

均为参照行为。

本阶段可以重构产出该结果的内部实现，但不得有意重新设计管理页拓扑。

管理页布局回归测试因此是统一引擎的兼容性参照。

## 2. 分配模型

本节记录开发者确认的最终子项宽度分配设计（2026-09-05 对话）。它取代
任何把"容量分配"读作新的通用或默认引擎模式的理解。

### 2.1 可选，而非默认

通过分配元数据实现的"同行不同宽度"是**可选的**。节点未声明分配元数据
时的默认行为是当前管理页行为，对每种布局逐位保留：

- Flow 子项保持现有等分填充（行内等宽）。
- WeightedFlow 行保持现有的按单位比例拉伸（`WeightedPoolPanel.AllocateRows`
  算术，不变）。
- Stack 子项不受影响。
- 默认情况下任何地方都不存在字节容量权重。

2026-09-05 记录的开发者澄清：在现状管理页行为中，Flow 子项是等宽的，
而 WeightedFlow 池行的富余宽度按单位数比例拉伸。两者都是"现状行为"，
本阶段均不改变。把池行改成严格等宽属于管理页行为变更，不在本计划内。

引擎只在对该条带声明了分配元数据（§2.2–§2.3）且仅限编辑上半区叶级条带
（§2.5）时，才执行声明权重分配。

### 2.2 权重来源

- 节点可以在布局输入元数据中声明可选的**容量权重**。
- 声明权重即为该条带启用三段式分配（§2.4）。
- 不存在其他权重来源。引擎中没有分配模式枚举，没有页面名分支。
- 管理页兼容：管理页不声明任何权重；其行渲染与今天完全一致，现有回归
  期望继续有效。

### 2.3 容量权重换算

仅对编辑上半区分区条带：

```text
weight_i = 子项 i 的字节数，以 double 表示
```

- 权重不做归一化、不做舍入。`double` 在 2^53 以下精确表示整数，大于
  任何真实分区尺寸，因此权重比例精确等于字节比例。
- 若权重字段最终为整数类型，允许 GCD 约分；默认选择 `double`，完全
  不需要换算。
- 分区与可见未分配区都使用其实际字节数。
- 低于配置阈值的隐藏间隙不投影、不占布局槽、不带权重。

换算是快照数据的纯函数，运行在投影层、任何布局过程之外。

### 2.4 三段式条带分配（规范性）

对一条启用分配的条带行，`n` 个可见子项、间距 `s`（6 DIP）、叶子最小宽
`m`（112 DIP）、等宽增长阈值 `t`（命名变量，§2.7）、声明权重
`w_i`：

```text
W1 = n × m + s × (n − 1)     行最小宽度
W2 = n × t + s × (n − 1)     行无换行宽度（等宽增长边界）
```

**第 1 段 —— `available ≤ W1`（宽度不足）：**

```text
width_i = m
```

每个子项保持最小宽度。不做负向调整；条带溢出视口（§4.4）。

**第 2 段 —— `W1 < available ≤ W2`（共同增长）：**

所有子项以相同的绝对增量一起增长：

```text
g = (available − W1) / n
width_i = m + g
```

最小宽相等时，行内每个子项宽度相同。

**第 3 段 —— `available > W2`（容量分配）：**

每个子项先达到 `t`，再按容量分配剩余宽度：

```text
width_i = t + (available − W2) × w_i / Σw        用于子项 1 … n−1
width_n = available − s × (n − 1) − Σ_{i<n} width_i，钳制 ≥ t
```

必需性质：

- **连续性：** `available = W1` 处第 1→2 段一致（`g = 0`）；
  `available = W2` 处第 2→3 段一致（每个子项恰为 `t`）。跨过阈值不产生
  视觉跳变。
- 行内**最后一个子项确定性地吸收舍入残差**（第 2、3 段均适用）。
- 零权重子项停在第 1–2 段的 `m` 或第 3 段的 `t`。
- 若 `Σw ≤ 0`，第 3 段改为按子项数等分剩余宽度。
- `t` 是输入数据（命名常量，§2.7），绝不是布局期间量出的值。标签在
  磁贴内仍可能换行；标签是否恰好放行是呈现问题，以截图确认，不是布局
  输入。

算例（指示性，假设 `t = 200 DIP`；以确认值重算）：

```text
n = 2, m = 112, s = 6, t = 200, 权重 100 GiB : 200 GiB
W1 = 230, W2 = 406

available = 320  → 第 2 段：两个子项均为 112 + 45 = 157 DIP
available = 563  → 第 3 段：A = 200 + 157 × 100/300 = 252.33 DIP
                              B = 563 − 6 − 252.33   = 304.67 DIP
```

### 2.5 围栏

声明容量分配只允许出现在编辑上半区的叶级分区/未分配条带上。引擎不含
字节或容量概念。本阶段不得把容量权重泛化到池、层或任何其他节点，不得
引入第二条分配公式，也不得让"同行不同宽度"在任何地方成为默认。

### 2.6 尺寸变化行为

调整尺寸是一串相互独立的单遍计算：宽度变化 → 引擎算一次 →
`ApplyLayout` → 面板按新槽位排列。引擎是"不可变输入记录 + 一个宽度"
上的纯函数；它不碰任何 UIElement，也绝不为决策去度量子项。`ApplyLayout`
回写只使排列失效，不得写任何影响宽度的属性。小于 1 DIP 的宽度变化不
重新规划（幂等保护，§1.0 第 5 条）。段间转换连续（§2.4），拖动跨过
`W1`/`W2` 不产生跳变。

### 2.7 命名阈值变量

所有布局阈值都是命名变量，且只有一个归属。面板与页面中不出现任何宽度
字面量。

| 变量 | 归属 | 取值 |
| --- | --- | --- |
| 叶子最小宽 `m` | `TopologyLayoutEngine` | 112 DIP（不变） |
| 兄弟间距 `s` | `TopologyLayoutEngine` | 6 DIP（不变） |
| 祖先边框宽 | `TopologyLayoutEngine` | 26 DIP（不变） |
| 等宽增长阈值 `t` | `TopologyLayoutEngine` | 实施时以截图确认；指示值 200 DIP |
| 单行磁盘头阈值 | `TopologyNodeControl` 呈现层 | 实施时以截图确认 |
| 各表面回退视口宽度 | 各表面自己的状态 | 按表面命名；取代内联的 1400 |

本阶段消除的现有内联字面量：`1400`（面板回退与 ViewModel 默认视口）、
`320` 与 `20`（页面 `SizeChanged` 处理器）、`150`
（`EqualFillFlowLayout` / `WeightedPoolLayout` 默认参数）。它们改为命名
变量或随其宿主一起消失。现有引擎常量（112/6/26）的数值在本阶段不变。

命名变量是有唯一归属的代码常量，不是用户可见设置；设置仍属范围外
（§12）。

## 3. 编辑下半区拓扑

### 3.1 结构

编辑下半区拓扑在下文未列出的方面使用与管理页相同的池导向结构与布局
行为。

它只显示内部池，包括原始池。

本阶段不重新设计现有的编辑工作副本、拖拽、模拟 Execute、创建、修改与
解散行为。

### 3.2 原始池

原始池显示其物理盘。

原始池内的物理盘在编辑下半区拓扑中**不**显示分区。

这是仅作用于编辑下半区的投影规则，不改变管理页投影。

概念上：

```text
Primordial
├─ Physical Disk
├─ Physical Disk
└─ Physical Disk
```

而不是：

```text
Primordial
└─ Physical Disk
   └─ Partition
```

### 3.3 现有池

非原始池保持当前编辑下半区的逻辑内容，本计划未明确改变者不变。

现有的层、物理盘、虚拟盘与虚拟盘分区表示保持可用。

本计划不改变池编辑语义或模拟操作。

### 3.4 合成加号池

合成加号池仍是编辑下半区添加池的入口。

它是：

- 视觉上与池平级；
- 逻辑上是合成的；
- 永远排在真实池之后；
- 因此池行单行放下时是最右侧的池；
- 打包需要多行时排在全部真实池与草稿池之后。

概念上：

```text
Primordial | Pool A | Pool B | +
```

加号池继续只创建现有的本地草稿池工作状态，不创建真实存储。

### 3.5 布局

编辑下半区使用与管理页相同的加权池布局规则，除非上文编辑下半区规则
改变了投影子项。

不存在单独的编辑下半区打包算法。

## 4. 编辑上半区拓扑

### 4.1 只有两级

编辑上半区拓扑只包含分区管理所需的磁盘/分区工作区。

可见逻辑层级为：

```text
Disk
└─ Partition / Unallocated
```

编辑上半区拓扑不显示：

- 系统；
- 存储池；
- 存储层；
- 池分组；
- 直连盘分组；
- 虚拟盘分组；
- 网络分组；
- 其他拓扑分组容器。

为喂给统一引擎所需的任何不可见根节点仅用于布局，不构成可见第三级。

### 4.2 只显示合格磁盘

只投影能通过现有分区管理策略管理的磁盘。

继续使用现有的可分区策略，不在页面里复制资格规则。

当前产品行为保持：

- 合格的系统/启动盘可以显示；
- 现有操作限制仍然适用；
- 可分区的虚拟盘可以显示；
- 被非原始池占用的物理盘不再单独作为可分区裸盘显示；
- 网络映射驱动器不显示。

本计划不扩大允许操作的磁盘集合。

### 4.3 磁盘排列

编辑上半区所有磁盘竖向排列。

概念上：

```text
Disk 0
Disk 1
Disk 2
Disk 3
```

一块磁盘不与其他磁盘共享水平行。

统一引擎应把这表达为竖向/Stack 关系，而不是依赖页面专用的布局算法
（现有 XAML `ItemsPanel` StackPanel 由引擎 Stack 通道取代）。

### 4.4 分区排列

一块磁盘内的分区与可见未分配区按磁盘偏移排成一条水平条带。

概念上：

```text
Disk 0
[Partition 1][Unallocated][Partition 2][Partition 3]
```

一块磁盘的子项不换到第二条逻辑分区行。

不换行规则（开发者 2026-09-05 确认）：

- 条带恒为单行；
- 每个可见子项至少保持其最小宽度；
- 可用宽度不大于行最小宽 `W1` 时，子项保持最小宽度，行横向宽于视口；
  由现有拓扑滚动面处理溢出（第 1 段，§2.4）；
- 条带的目标宽度只能是输入数据；布局期间量出的任何值不得成为目标宽度。

这使磁盘图保持空间连贯，而不是把后面的分区挪到无关的第二行。

### 4.5 未分配区

未分配区的现有编辑行为保持：

- 前导间隙是独立节点；
- 内部间隙是独立节点；
- 尾部间隙是独立节点；
- 顺序跟随磁盘偏移；
- 已配置的分区间隙忽略阈值仍决定哪些间隙可见。

可见未分配节点以该间隙的确切大小作为容量权重参与宽度分配（§2.3）。

低于配置阈值的隐藏间隙不获得可见布局槽。

## 5. 编辑上半区条带宽度分配

本计划中所有宽度均为 WinUI 设备无关单位（DIP），不是物理像素。

分配本身在 §2.4 中规范定义。本节记录其范围与验收用例。

### 5.1 最小宽度

每个可见分区或未分配子项以拓扑叶子最小宽度起步：`112 DIP`。

本计划不改变管理页最小宽度。

### 5.2 范围

三段式分配（§2.4）只作用于编辑上半区磁盘的分区/未分配条带，且仅因这些
条带声明了容量权重。

它不取代管理页现有布局规则（§2.1），也不改变编辑下半区池权重。

### 5.3 验收用例

以下数值假设指示值 `t = 200 DIP`；以确认值重算。`m = 112`，`s = 6`。

#### 用例 A1 —— 第 1 段（宽度不足）

```text
n = 2, available = 200（< W1 = 230）
期望：两个子项均为 112 DIP；行溢出视口
```

#### 用例 A2 —— 第 2 段（共同增长）

```text
n = 2, available = 320, W1 = 230, W2 = 406
期望：两个子项均为 112 + 45 = 157 DIP（等宽）
```

#### 用例 A3 —— 第 3 段（容量分配）

```text
n = 2, 权重 100 GiB : 200 GiB, available = 563, W2 = 406
期望：A = 200 + 157 × 100/300 = 252.33 DIP
      B = 563 − 6 − 252.33   = 304.67 DIP（吸收残差）
```

#### 用例 A4 —— 连续性

`available = W2` 处，第 2 段与第 3 段公式都给每个子项 `t`。

#### 用例 B —— 三个子项含未分配（第 3 段）

```text
100 GiB 分区、50 GiB 未分配、200 GiB 分区
```

超出 `t` 的宽度按 `100 : 50 : 200` 分配；最后一个子项吸收残差。

#### 用例 C —— 隐藏间隙

低于配置阈值的隐藏未分配间隙不获得布局槽，也不获得可见容量份额。

### 5.4 确定性

任何最终舍入都是确定性的；行内最后一个子项吸收残差，使规划的行宽保持
一致（§2.4）。

## 6. 编辑上半区磁盘呈现（宽度自适应）

编辑上半区磁盘头是**宽度自适应**的：

- 当磁盘节点的引擎分配宽度达到命名单行阈值（§2.7）时，普通磁盘卡约三行
  文字合并为一行紧凑的水平线；
- 宽度不足时，保持当前标准多行呈现。

概念上（宽时）：

```text
Disk 0    Samsung SSD ...    GPT    1.82 TiB
```

结果必须：

- 由引擎分配的槽位宽度驱动（确定性的渲染期输入），而不是由量出的文字
  宽度驱动；
- 使用命名阈值变量（§2.7），不用字面量；
- 保留识别磁盘所需的信息；
- 保留无障碍名称；
- 保留选择与交互行为；
- 仍是共享 `TopologyNodeControl` 的显式呈现模式；不得创建第二套磁盘
  控件树。

管理页拓扑卡片仍是参照呈现，不因本要求改变。

编辑下半区卡片保持正常拓扑呈现，除非另行规定。

单行排布细节、阈值取值、等宽增长 `t` 在实施时以同一张截图一起确认。

## 7. 实施映射

本节把已确认的需求映射到当前实现，不新增产品范围。

### 7.1 应用层布局引擎

主要归属：

`src/WinPool.Application/TopologyLayoutEngine.cs`

重构现有引擎，使其结果足以让面板完成最终排列，而无需再发明宽度分配
算法。

引擎拥有：

- 自然子树测量；
- 叶子最小宽；
- 祖先边框宽；
- 兄弟间距；
- Stack 布局；
- Flow 布局；
- WeightedFlow 布局；
- 兄弟行成组；
- 收缩决策；
- 行高放宽；
- 最终子项宽度指派：默认行为逐位保留（§2.1），声明条带实施三段式分配
  （§2.4）；
- 编辑上半区所需的不换行水平条带行为（§4.4）；
- 命名阈值变量（§2.7）。

现有管理页计算保持基准；单位规划阶段不做重新设计，默认行的输出必须与
今天逐位一致。

如确有必要，添加最小布局输入元数据：

- 可选容量权重（§2.2–§2.3）；
- 子行换行与否。

不得把页面名编入 `TopologyLayoutEngine`。

### 7.2 布局结果

引擎结果必须携带最终行成组与每个子项的最终分配宽度。

"最终分配宽度"指从该表面唯一一次根级布局结果像素化出的槽位宽度
（§1.0 第 2 条），**不是**各嵌套面板独立算出的宽度。

不得把最终加权或容量拉伸计算留在某个具体的 WinUI 面板里。

最终结果可以在现有 `TopologyLayoutResult` 上扩展显式行槽位宽度信息或
等价表示。

确切数据类型是实现选择；所有权边界不是。

### 7.3 WinUI 拓扑面板

当前相关控件包括：

- `AdaptiveFlowPanel`
- `WeightedPoolPanel`
- `TopologyNodeControl`

本阶段之后，任何保留的布局面板都是围绕 `TopologyLayoutEngine` 的薄
适配器。

每个表面有一个根适配器，以该表面的宿主宽度调用引擎一次。根适配器可以：

- 获取 WinUI 实际可用宽度；
- 在根处把节点 ViewModel 树转换为引擎输入；
- 调用引擎；
- 按引擎分配的宽度度量子项；
- 按引擎行与槽位排列子项。

根适配器之下的嵌套面板只消费已存储的槽位。

它们不得：

- 调用 `TopologyLayoutEngine`；
- 爬可视树寻找宿主并重新规划；
- 决定放得下几个子项；
- 选择等分还是加权；
- 选择容量比例；
- 选择行打包策略；
- 选择收缩优先级；
- 包含宽度字面量（§2.7）。

若单个通用拓扑面板能干净地同时替代 `AdaptiveFlowPanel` 与
`WeightedPoolPanel`，允许该替代。

本计划授权移除的确切过时候选是：

- `src/WinPool.App/Controls/AdaptiveFlowPanel.cs`
- `src/WinPool.App/Controls/WeightedPoolPanel.cs`

仅当以下条件全部满足后才可删除：

1. 通用替代已存在；
2. 全部代码引用已迁移；
3. 全部 XAML 使用点（含 `MainPage.xaml` 与 `EditPage.xaml`）不再引用
   被移除的面板类型；
4. 管理页回归测试通过；
5. 编辑上半区与下半区定向布局测试通过。

仅为架构整洁而删除不是必需的。若保留薄适配器是更小的闭环变更，可以
保留。

### 7.4 管理页投影

主要归属：

`src/WinPool.Application/Topology.cs`

不重新设计 `TopologyProjector.Project`。

为统一引擎提供布局元数据所需的任何变更，必须保持管理页投影拓扑与当前
排序不变。

### 7.5 编辑投影

主要归属：

`src/WinPool.Application/EditWorkspace.cs`

#### 上半区

`ProjectPartitionWorkspace` 继续负责选择可分区磁盘并构建可见的磁盘、
分区与未分配节点。

修改其布局元数据，使统一引擎收到：

- 竖向磁盘集合（Stack）；
- 每盘一条不换行水平分区条带；
- 分区/间隙的真实字节数作为声明容量权重（§2.3）。

`EditWorkspace` 中唯一允许的算术是赋值 `weight = 字节数`；一切分配

#### 下半区

`ProjectPoolWorkspace` / `ProjectPoolWorkspaceRoot` 继续负责编辑下半区

确保：

  测试钉住）；

- 加号池排在最后（已如此；保持并用测试钉住）；

### 7.6 ViewModel 转换

`TopologyNodeViewModel` 仍是共享呈现模型。

应用布局节点到 ViewModel 的映射必须保留统一引擎所需的布局元数据，
包括可选容量权重。

当前 App 侧转换位于
`src/WinPool.App/Services/TopologyLayoutMapper.cs`；更新该映射以携带
引擎布局元数据属于本阶段工作。

`TopologyLayoutInput` 增加可选容量权重；权重缺失时引擎内部保持当前
默认行为（§2.1）。

不得为管理页/编辑页创建分离的拓扑 ViewModel 层级。

### 7.7 编辑上半区自适应头

主要归属：

- `src/WinPool.App/Controls/TopologyNodeControl.xaml`
- `src/WinPool.App/Controls/TopologyNodeControl.xaml.cs`

为单行编辑上半区磁盘头添加所需的最小显式呈现模式，按引擎分配宽度与
命名阈值（§6、§2.7）切换。

同一控件继续拥有：

- 选择；
- 适用处的展开；
- 键盘交互；
- 无障碍；
- 拖放钩子；
- 正常拓扑卡片渲染。

不得把这些行为复制进编辑页专用磁盘控件。

### 7.8 视口所有权

"表面"指恰好三个区域：管理页拓扑、编辑上半区拓扑、编辑下半区拓扑。
表面内部的嵌套面板不是表面。

编辑上半区与下半区不得覆写可能影响管理页布局的单一共享全局拓扑视口
宽度。

优先使用 `MeasureOverride` / `ArrangeOverride` 期间 WinUI 布局面板收
到的实际宽度。

在 WinUI 无限宽测量需要处可保留回退视口状态，但每个表面必须使用自己的
宿主宽度与自己的命名回退值（§2.7）；内联的 `1400` 消失。

因此编辑上半区、下半区与管理页不得竞写同一个共享 `TopologyViewportWidth`；
移除该共享状态、替换为每表面状态，并配套自动视口隔离回归测试。

- **需求无法满足时停下报告。** 以其他行为顶替（例如用固定宽度常量顶替
  真实不换行宽度）是被禁止的。
- **交互提问无回执不是同意。** 决定前用普通文字重问。
- **崩溃后**先读崩溃日志与 Windows 事件日志（1000/1026）再改代码；
  优先插桩收集真实数据而不是猜；先报告根因、等批准再修。
- **脚本改代码**必须先确认编译成功，再用于验证的任何启动。

## 13. 安全

现有默认拒绝的执行边界保持不变。

- 本阶段所有存储结构变更保持仅模拟。
- 不授权真实磁盘、分区、卷、池、层或虚拟盘变更。
- UAC 提权或真实模式不是授权。
- 硬件数据保持在现有脱敏边界之后。
- 清单 PowerShell 保持嵌入式只读。
- 本计划下真实硬件变更不是可接受的测试方法。

## 14. 验收门

仅当以下全部成立时实施才算完成：

- 三个拓扑区域均以 `TopologyLayoutEngine` 为唯一布局算法权威；
- 每个表面恰好运行一次根级引擎布局；没有任何嵌套面板调用引擎或重新
  规划预算；
- 未声明分配元数据的行渲染与今天完全一致；默认情况下任何地方都不出现
  基于权重的宽度差异；
- 引擎实现声明条带的三段式分配（§2.4），且在 `W1`、`W2` 处连续；
- 第 1 段保持最小宽度并无负向调整地溢出；第 2 段所有子项等量增长；
  第 3 段超出 `t` 的宽度按声明容量权重分配，最后一个子项吸收舍入残差；
- 没有任何编辑页专用面板独立做出等分、加权或容量分配决策；
- 管理页行为保持等价；
- 编辑下半区原始盘不显示分区；
- 编辑下半区加号池是最后一个池项；
- 编辑上半区只包含合格磁盘 → 分区/未分配拓扑；
- 编辑上半区磁盘经引擎 Stack 通道竖向堆叠；
- 一块磁盘内的分区构成一条水平不换行条带；
- 等宽增长阈值 `t` 与单行头阈值是有确认取值的命名变量；
- 面板与页面中不再有任何宽度字面量（§2.7）；
- 编辑上半区磁盘卡片在分配宽度达到命名阈值时使用单行呈现，不足时使用
  标准呈现；
- 共享视口状态不再允许编辑半区缩放改变管理页布局；
- 定向自动测试 `passed`；
- 每个已实施 TL 条目均记录其实机验证证据；
- 原生视觉点击走查在实际执行前保持 `unverified`。

实施达到该状态后，不得自动开始正式验收。询问开发者是否进入正式测试。
