## 1. 已确认决定

这些决定约束本阶段，优先于现有编辑页布局实现。

### 1.0 引擎不变量

这些不变量说明引擎为什么这样设计。它们是规范性的：满足其余全部章节但
违反其中任一条的实现，即视为不满足本计划。

1. **结构决策只存在于单位层。** 行成组、列预算、收缩决策、行高放宽、
   最小单位宽（含复杂池兄弟的 2 单位下限）全部在整数 Wunit/Hunit 空间
   决定。它们是布局计划中与分辨率无关的不变量。
2. **每个表面一次根级布局。** 每个表面（管理页、编辑上半区、编辑下半区）
   每轮布局只在自身的根适配器处以该表面自己的宿主宽度调用引擎一次。
   嵌套面板绝不调用引擎，也绝不重新规划任何祖先或兄弟的预算。
3. **面板是机械消费者。** 面板获取 WinUI 提供的宽度（WinUI 无限宽测量时
   使用各表面自己的回退值）；在根处把节点 ViewModel 树转换为引擎输入；
   按引擎分配的槽位宽度执行 Measure/Arrange。面板绝不决定放得下几个
   子项、等分还是加权、容量比例、行打包或收缩优先级。
4. **像素只做拉伸。** 像素值只把已完成的单位计划像素化。任何以像素量出
   的值不得回流进单位层决策。
5. **布局纯度与幂等。** 只有确定性输入数据——静态快照数据和 WinUI 提供
   的宽度——可以进入布局。任何由度量子元素得出的值不得影响布局决策
   （度量重入是已知 `LayoutCycleException` 的触发条件）。相同输入产生
   相同输出；小于 1 DIP 的宽度变化不重新规划。

### 1.1 唯一拓扑布局引擎

WinPool 只有一个拓扑布局引擎：

`TopologyLayoutEngine`

管理页、编辑上半区、编辑下半区都使用该引擎完成拓扑测量、行生成、最小
宽度计算、可用宽度处理、子项宽度分配和最终布局规划。

三个区域可以提供不同的拓扑树和少量布局或呈现选项，但不得拥有独立的布局
算法。

特别地：

- 管理页保持行为与视觉基准。
- 编辑上半区是受限的磁盘/分区投影。
- 编辑下半区是受限的池投影。
- `AdaptiveFlowPanel`、`WeightedPoolPanel` 或替代面板可作为 WinUI
  measure/arrange 适配器保留，但不得实现相互竞争的布局算法。
- 等分、加权、容量分配、换行与最小宽度规则属于 `TopologyLayoutEngine`。
- 面板只消费引擎结果，只做机械的 WinUI 度量与排列。
- 不得引入第二个编辑页专用布局引擎。
- 不得在核心算法中引入页面名判断（如 `if (Manage)`、`if (EditUpper)`）。
  所需差异一律以显式布局输入或策略数据表达。

实现必须保持三个区域所需的最小闭环。不得构建通用公共布局框架。

### 1.2 管理页是参照行为

管理页拓扑在功能与视觉上与当前管理页实现保持等价。

其投影继续按当前 `TopologyProjector` 展示完整逻辑拓扑。

管理页现有规则：

- 系统根；
- 池；
- 层；
- 物理盘;
- 虚拟盘；
- 分区;
- 网络与其他分组;
- Stack / Flow / WeightedFlow 关系;
- 兄弟打包;
- 行高放宽;
- 拓扑选择;
- 展开;
- 最小节点宽;

均为参照行为。

本阶段可以重构产出该结果的内部实现，但不得有意重新设计管理页拓扑。

管理页布局回归测试因此是统一引擎的兼容性参照。

## 2. 分配模型

本节是开发者确认的最终子项宽度分配设计（2026-09-05）。它取代任何把
"容量分配"读作引擎新模式的理解。

### 2.1 唯一分配规则

引擎通过恰好一条规则拥有最终槽位宽度分配：行内每个子项获得其自然最小
宽度，加上该行剩余宽度按比例分得的一份：

```text
width_i = minimum_i + extra × weight_i / Σ weight
```

权重按节点解析（§2.2）。引擎中没有其他权重来源、没有分配模式枚举、没有
页面名分支。

### 2.2 权重来源与回退

- 节点可以在布局输入元数据中声明可选的**分配权重**。
- 未声明权重时，引擎使用该节点测得的 **UnitWidth**。
- 管理页兼容：管理页节点不声明权重。UnitWidth 回退必须逐位复现当前
  `WeightedPoolPanel.AllocateRows` 的算术，使管理页输出不变、现有回归
  期望继续有效。
- 编辑上半区分区条带声明容量权重（§2.3）。

### 2.3 容量权重换算

仅对编辑上半区分区条带：

```text
weight_i = 子项 i 的字节数，以 double 表示
```

- 权重不做归一化、不做舍入。`double` 在 2^53 以下精确表示整数，大于
  任何真实分区尺寸，因此权重比例精确等于字节比例。
- 若权重字段最终为整数类型，允许 GCD 约分；默认选择 `double`，完全
  不需要换算。
- 分区与可见未分配区都使用其实际字节数。
- 低于配置阈值的隐藏间隙不投影、不占布局槽、不带权重。

换算是快照数据的纯函数，运行在投影层、任何布局过程之外。

### 2.4 规范性行分配

对一行 `n` 个可见子项、间距 `s`（6 DIP）、各子项最小宽 `minimum_i`
（叶子最小 112 DIP）：

```text
reserved = Σ minimum_i + s × (n − 1)
extra    = 可用宽度 − reserved
```

- 若 `extra ≤ 0`：每个子项保持 `minimum_i`。不做负向调整；必要时条带
  溢出视口。
- 若 `extra > 0`：子项 `1 … n−1` 获得
  `minimum_i + extra × weight_i / Σ weight`。允许小数 DIP 宽度；整数
  变体取 floor。
- 行内**最后一个子项确定性地吸收舍入残差**：

```text
width_n = 可用宽度 − s × (n − 1) − Σ_{i<n} width_i，钳制 ≥ minimum_n
```

- 零权重子项保持最小宽度。
- 若 `Σ weight ≤ 0`（无正权重），改为按子项数等分剩余宽度。
- 吸收者必须恒为"行内最后一个子项"；不得改为最大子项，否则每次重算
  可能跳变。

### 2.5 围栏

容量权重只允许出现在编辑上半区的叶级分区/未分配条带上。引擎不含字节或
容量概念。本阶段不得把容量权重泛化到池、层或任何其他节点，也不得引入
第二条分配公式。

### 2.6 尺寸变化行为

调整尺寸是一串相互独立的单遍计算：宽度变化 → 引擎算一次 →
`ApplyLayout` → 面板按新槽位排列。引擎是"不可变输入记录 + 一个宽度"
上的纯函数；它不碰任何 UIElement，也绝不为决策去度量子项。`ApplyLayout`
回写只使排列失效，不得写任何影响宽度的属性。小于 1 DIP 的宽度变化不
重新规划（幂等保护，§1.0 第 5 条）。

算例（同时是验收用例，§14）：

```text
分区 A = 100 GiB，分区 B = 200 GiB，剩余宽度 = 333 DIP
A = 112 + 333 × 100/300 = 223 DIP
B = 112 + 333 × 200/300 = 334 DIP
```

## 3. 编辑下半区拓扑

### 3.1 结构

编辑下半区拓扑在下文未列出的方面使用与管理页相同的池导向结构与布局
行为。

它只显示内部池，包括原始池。

本阶段不重新设计现有的编辑工作副本、拖拽、模拟 Execute、创建、修改与
解散行为。

### 3.2 原始池

原始池显示其物理盘。

原始池内的物理盘在编辑下半区拓扑中**不**显示分区。

这是仅作用于编辑下半区的投影规则，不改变管理页投影。

概念上：

```text
Primordial
├─ Physical Disk
├─ Physical Disk
└─ Physical Disk
```

而不是：

```text
Primordial
└─ Physical Disk
   └─ Partition
```

### 3.3 现有池

非原始池保持当前编辑下半区的逻辑内容，本计划未明确改变者不变。

现有的层、物理盘、虚拟盘与虚拟盘分区表示保持可用。

本计划不改变池编辑语义或模拟操作。

### 3.4 合成加号池

合成加号池仍是编辑下半区添加池的入口。

它是：

- 视觉上与池平级；
- 逻辑上是合成的；
- 永远排在真实池之后；
- 因此池行单行放下时是最右侧的池；
- 打包需要多行时排在全部真实池与草稿池之后。

概念上：

```text
Primordial | Pool A | Pool B | +
```

加号池继续只创建现有的本地草稿池工作状态，不创建真实存储。

### 3.5 布局

编辑下半区使用与管理页相同的加权池布局规则，除非上文编辑下半区规则
改变了投影子项。

不存在单独的编辑下半区打包算法。

## 4. 编辑上半区拓扑

### 4.1 只有两级

编辑上半区拓扑只包含分区管理所需的磁盘/分区工作区。

可见逻辑层级为：

```text
Disk
└─ Partition / Unallocated
```

编辑上半区拓扑不显示：

- 系统；
- 存储池；
- 存储层；
- 池分组；
- 直连盘分组；
- 虚拟盘分组；
- 网络分组；
- 其他拓扑分组容器。

为喂给统一引擎所需的任何不可见根节点仅用于布局，不构成可见第三级。

### 4.2 只显示合格磁盘

只投影能通过现有分区管理策略管理的磁盘。

继续使用现有的可分区策略，不在页面里复制资格规则。

当前产品行为保持：

- 合格的系统/启动盘可以显示；
- 现有操作限制仍然适用；
- 可分区的虚拟盘可以显示；
- 被非原始池占用的物理盘不再单独作为可分区裸盘显示；
- 网络映射驱动器不显示。

本计划不扩大允许操作的磁盘集合。

### 4.3 磁盘排列

编辑上半区所有磁盘竖向排列。

概念上：

```text
Disk 0
Disk 1
Disk 2
Disk 3
```

一块磁盘不与其他磁盘共享水平行。

统一引擎应把这表达为竖向/Stack 关系，而不是依赖页面专用的布局算法
（现有 XAML `ItemsPanel` StackPanel 由引擎 Stack 通道取代）。

### 4.4 分区排列

一块磁盘内的分区与可见未分配区按磁盘偏移排成一条水平条带。

概念上：

```text
Disk 0
[Partition 1][Unallocated][Partition 2][Partition 3]
```

一块磁盘的子项不换到第二条逻辑分区行。

不换行规则（开发者 2026-09-05 确认）：

- 条带恒为单行；
- 每个可见子项至少保持其最小宽度；
- 最小总宽超过可用拓扑宽度时，行保持最小宽度并横向宽于视口；由现有
  拓扑滚动面处理溢出（§2.4 的 `extra ≤ 0` 分支）；
- 条带的目标宽度只能是输入数据；布局期间量出的任何值不得成为目标宽度。

这使磁盘图保持空间连贯，而不是把后面的分区挪到无关的第二行。

### 4.5 未分配区

未分配区的现有编辑行为保持：

- 前导间隙是独立节点；
- 内部间隙是独立节点；
- 尾部间隙是独立节点；
- 顺序跟随磁盘偏移；
- 已配置的分区间隙忽略阈值仍决定哪些间隙可见。

可见未分配节点以该间隙的确切大小作为容量权重参与宽度分配（§2.3）。

低于配置阈值的隐藏间隙不获得可见布局槽。

## 5. 容量比例分区宽度

本计划中所有宽度均为 WinUI 设备无关单位（DIP），不是物理像素。

分配本身在 §2 中规范定义。本节记录其范围与验收数值。

### 5.1 最小宽度

每个可见分区或未分配子项以拓扑叶子最小宽度起步：`112 DIP`。

本计划不改变管理页最小宽度。

### 5.2 范围

容量比例剩余宽度分配只作用于编辑上半区磁盘的分区/未分配行。

它不取代管理页现有的加权拓扑规则（§2.2 回退），也不改变编辑下半区
池权重。

分配以布局输入（声明权重）提供，绝不以单独的面板或引擎模式提供
（§2.5）。

### 5.3 验收算例

```text
分区 A = 100 GiB
分区 B = 200 GiB

最小宽：A = 112 DIP，B = 112 DIP
剩余宽度 = 333 DIP

A 额外 = 333 × 100 / 300 = 111 DIP
B 额外 = 333 × 200 / 300 = 222 DIP

最终：A = 223 DIP，B = 334 DIP
```

实现可以使用浮点布局宽度。任何最终舍入必须是确定性的，且最后一个子项
必须吸收全部舍入残差，使规划的行宽保持一致（§2.4）。

### 5.4 无剩余宽度

若：

```text
可用宽度 ≤ 最小宽度之和 + 间距
```

不做负向比例调整。

每个子项至少保持最小宽度，必要时水平条带溢出视口。

## 6. 编辑上半区磁盘呈现

可见的编辑上半区磁盘节点使用紧凑的水平头部，而不是标准多行拓扑卡片头。

当前分布在普通磁盘卡片约三行文字中的信息，在可行处水平排列。

概念上：

```text
Disk 0    Samsung SSD ...    GPT    1.82 TiB
```

确切的分隔符与截断是呈现细节，实施时以截图确认（踩坑记录 §7 第 4 项）。
结果必须：

- 保持为单个紧凑磁盘头；
- 保留识别磁盘所需的信息；
- 保留无障碍名称；
- 保留选择与交互行为；
- 允许长设备名仅在可用宽度使其不可避免时截断或换行。

此紧凑呈现只作用于编辑上半区磁盘节点。

管理页拓扑卡片仍是参照呈现，不因本要求改变。

编辑下半区卡片保持正常拓扑呈现，除非另行规定。

实现应为共享的 `TopologyNodeControl` 扩展一个最小的显式呈现变体，而不是
创建第二套磁盘控件树。

## 7. 实施映射

### 7.1 应用层布局引擎

主要归属：

`src/WinPool.Application/TopologyLayoutEngine.cs`

重构现有引擎，使其结果足以让面板完成最终排列，而无需再发明宽度分配
算法。

引擎拥有：

- 自然子树测量；
- 叶子最小宽；
- 祖先边框宽；
- 兄弟间距；
- Stack 布局;
- Flow 布局;
- WeightedFlow 布局;
- 兄弟行成组;
- 收缩决策;
- 行高放宽;
- 通过唯一分配规则完成的最终子项宽度指派（§2.1）；
- 按声明权重、UnitWidth 回退的剩余空间分配（§2.2）；
- 编辑上半区所需的不换行水平条带行为（§4.4）。

现有管理页计算保持基准；单位规划阶段不做重新设计，UnitWidth 回退必须
逐位复现当前 `WeightedPoolPanel.AllocateRows` 的算术。

如确有必要，添加最小布局输入元数据：

- 可选分配权重（§2.2）；
- 子行换行与否。

不得把页面名编入 `TopologyLayoutEngine`。

### 7.2 布局结果

引擎结果必须携带最终行成组与每个子项的最终分配宽度。

"最终分配宽度"指从该表面唯一一次根级布局结果像素化出的槽位宽度
（§1.0 第 2 条），**不是**各嵌套面板独立算出的宽度。

不得把最终加权或容量拉伸计算留在某个具体的 WinUI 面板里。

最终结果可以在现有 `TopologyLayoutResult` 上扩展显式行槽位宽度信息或
等价表示。

确切数据类型是实现选择；所有权边界不是。

### 7.3 WinUI 拓扑面板

当前相关控件包括：

- `AdaptiveFlowPanel`
- `WeightedPoolPanel`
- `TopologyNodeControl`

本阶段之后，任何保留的布局面板都是围绕 `TopologyLayoutEngine` 的薄
适配器。

每个表面有一个根适配器，以该表面的宿主宽度调用引擎一次。根适配器可以：

- 获取 WinUI 实际可用宽度；
- 在根处把节点 ViewModel 树转换为引擎输入；
- 调用引擎；
- 按引擎分配的宽度度量子项；
- 按引擎行与槽位排列子项。

根适配器之下的嵌套面板只消费已存储的槽位。

它们不得：

- 调用 `TopologyLayoutEngine`；
- 爬可视树寻找宿主并重新规划；
- 决定放得下几个子项；
- 选择等分还是加权；
- 选择容量比例；
- 选择行打包策略；
- 选择收缩优先级。

若单个通用拓扑面板能干净地同时替代 `AdaptiveFlowPanel` 与
`WeightedPoolPanel`，允许该替代。

本计划授权移除的确切过时候选是：

- `src/WinPool.App/Controls/AdaptiveFlowPanel.cs`
- `src/WinPool.App/Controls/WeightedPoolPanel.cs`

仅当以下条件全部满足后才可删除：

1. 通用替代已存在；
2. 全部代码引用已迁移；
3. 全部 XAML 使用点（含 `MainPage.xaml` 与 `EditPage.xaml`）不再引用
   被移除的面板类型；
4. 管理页回归测试通过；
5. 编辑上半区与下半区定向布局测试通过。

仅为架构整洁而删除不是必需的。若保留薄适配器是更小的闭环变更，可以
保留。

### 7.8 视口所有权

"表面"指恰好三个区域：管理页拓扑、编辑上半区拓扑、编辑下半区拓扑。
表面内部的嵌套面板不是表面。

编辑上半区与下半区不得覆写可能影响管理页布局的单一共享全局拓扑视口
宽度。

优先使用 `MeasureOverride` / `ArrangeOverride` 期间 WinUI 布局面板收
到的实际宽度。

在 WinUI 无限宽测量需要处可保留回退视口状态，但每个表面必须使用自己的
宿主宽度与自己的回退值。

因此编辑上半区、下半区与管理页不得竞写同一个共享 `TopologyViewportWidth`；
移除该共享状态、替换为每表面状态，并配套自动视口隔离回归测试。
